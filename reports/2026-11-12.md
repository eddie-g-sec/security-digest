# Security Digest — 2026-11-12

## Cloud Security

No CISA KEV-confirmed entries appear in today's data, so nothing here carries a confirmed-exploitation mandate — but two Docker-delivered services sit at CVSS 10.0. The single most urgent item is **CVE-2026-40281 in Gotenberg** (10.0 CRITICAL): an *unauthenticated* newline injection into ExifTool metadata values lets a remote caller rename or move arbitrary files inside the processing container, and it is a working bypass of the incomplete fix shipped in v8.30.1. It ties on score with **CVE-2026-33587** (Open Notebook SSTI, 10.0), which ranks just below it because it requires an authenticated application user. Gotenberg is the dominant theme of the day: five separate advisories (three critical, two high) covering unauthenticated RCE, SSRF to cloud metadata endpoints, and arbitrary file manipulation — treat the whole deployment as needing upgrade to 8.32.0 or later rather than patching individual CVEs. Kubernetes contributes a 9.9 Traefik Gateway API tenant-isolation bypass and a Kyverno RBAC bypass, both multi-tenancy boundary breaks. Note that the Kubernetes and Docker lists are each at the 10-entry cap, so they are not guaranteed complete.

### Formal Vulnerabilities

#### Docker (Gotenberg) — CVE-2026-40281 (CVSS 10.0 CRITICAL)
**Summary:** Gotenberg's metadata write endpoint validates metadata *keys* for control characters but leaves *values* unsanitized. A newline in a value splits the ExifTool stdin stream into a second argument, letting an unauthenticated remote caller inject ExifTool pseudo-tags such as `-FileName`, `-Directory`, `-SymLink`, and `-HardLink`, and thereby rename or move any PDF being processed to an arbitrary path inside the container. This is a bypass of the incomplete key-sanitization fix introduced in v8.30.1.

**Affected Features / Interoperability:** The PDF metadata write API (ExifTool-backed) in Gotenberg versions 8.30.1 and earlier. Downstream impact is on any service that exposes Gotenberg as a shared PDF endpoint and any file the container process can reach — including files staged for other tenants or jobs. The data does not state whether the container's own filesystem is the full blast radius or whether mounted volumes are affected.

**Source:** https://github.com/gotenberg/gotenberg/commit/405f1069c026bb08f319fb5a44e5c67c33208318 · https://github.com/gotenberg/gotenberg/security/advisories/GHSA-q7r4-hc83-hf2q

**Actions:**
- Fix: No fixed version is stated in the provided data. Track advisory GHSA-q7r4-hc83-hf2q; the referenced commit indicates the corrective change.
- Workaround: Disable or block the metadata write endpoint at the ingress/reverse proxy, and run Gotenberg in a read-only, non-root container with no host or shared-volume mounts.
- Tradeoff: Metadata writing is unavailable to callers, and read-only rootfs may break Gotenberg's internal temp-file handling unless a scoped writable tmpfs is provided.

#### Docker (Open Notebook) — CVE-2026-33587 (CVSS 10.0 CRITICAL)
**Summary:** Open Notebook v1.8.3 fails to sanitize user input in user-created transformations, allowing Server-Side Template Injection. An application user can escalate that SSTI to Python execution and then OS command execution inside the Docker container.

**Affected Features / Interoperability:** The user-created "transformations" feature of Open Notebook. Downstream exposure is whatever the container can reach — mounted note/document volumes, environment-supplied credentials, and the Docker host if the socket is mounted. The data does not enumerate which template engine or which container mounts are reachable.

**Source:** https://github.com/lfnovo/open-notebook/security/advisories/GHSA-f35w-wx37-26q7

**Actions:**
- Fix: No fixed version is stated in the provided data; the advisory is the only reference given.
- Workaround: Remove or restrict the transformations feature, require admin approval for transformation authoring, and run the container as non-root with no Docker socket and no host bind mounts.
- Tradeoff: Transformations become unusable or bottlenecked on an administrator, and non-root operation may break any workflow that assumes write access to the default data paths.

#### Docker (Portabase) — CVE-2026-67449 (CVSS 9.8 CRITICAL)
**Summary:** A path traversal in Portabase's TUS upload webhook handler (`app/api/tus/hooks/route.ts`) lets an unauthenticated attacker overwrite arbitrary files under the private data directory, including `/data/private/keys/master_key.bin`, the AES-256-GCM master key. Overwriting the master key compromises the confidentiality of every encrypted backup the tool manages.

**Affected Features / Interoperability:** The TUS resumable-upload webhook in Portabase prior to 1.21.2. Because Portabase backs up PostgreSQL, MySQL, MsSQL, MariaDB, Firebird, SQLite, MongoDB, Redis, files, and Docker volumes, the master key is the root of trust for all of those backup sets — its loss affects restore integrity and every downstream retention copy.

**Source:** https://github.com/Portabase/portabase/commit/8dcb406790728fbdbf758ec88bf000af79498fc1 · https://github.com/Portabase/portabase/pull/355 · https://github.com/Portabase/portabase/releases/tag/1.21.2

**Actions:**
- Fix: Upgrade to Portabase 1.21.2.
- Workaround: Block the TUS webhook path at the reverse proxy and restrict Portabase's network exposure to trusted backup clients only.
- Tradeoff: Resumable uploads through the webhook stop working, so large or interrupted backup uploads may fail and need to be restarted whole.

#### Docker (Gotenberg) — CVE-2026-42589 (CVSS 9.8 CRITICAL)
**Summary:** Prior to 8.31.0, Gotenberg's `/forms/pdfengines/metadata/write` endpoint passes JSON metadata keys straight to ExifTool with no character validation. A `\n` embedded in a key splits the ExifTool stdin stream into a new argument line, allowing injection of arbitrary ExifTool flags including `-if`, which evaluates Perl expressions — unauthenticated OS command execution in a single HTTP request that returns HTTP 200 with a valid PDF.

**Affected Features / Interoperability:** The PDF Engines metadata write endpoint and its `go-exiftool` integration. Any orchestration, workflow engine, or application that calls Gotenberg's metadata API is an entry point; the silent HTTP 200 means exploitation leaves no obvious error signal in caller logs.

**Source:** https://github.com/gotenberg/gotenberg/security/advisories/GHSA-rqgh-gxv4-6657

**Actions:**
- Fix: Upgrade to Gotenberg 8.31.0 or later.
- Workaround: Block the metadata write endpoint at the proxy layer and run Gotenberg with a read-only root filesystem, dropped capabilities, and no host mounts.
- Tradeoff: Callers lose metadata writing; read-only rootfs requires a scoped writable temp directory for PDF processing.

#### Docker (blueprintUE Self-Hosted) — CVE-2026-126812 (CVSS 9.8 CRITICAL)
**Summary:** The Docker Compose examples in blueprintUE Self-Hosted Edition before 4.3.7 set `MYSQL_ALLOW_EMPTY_PASSWORD=yes` in `database.env` and publish MariaDB on port 3306. Any unauthenticated attacker who can reach the Docker host on 3306 logs in as root with no password and can read, modify, or delete user accounts, blueprints, and all databases.

**Affected Features / Interoperability:** The bundled MariaDB service as defined in `docker-examples/database.env` and `docker-compose-smtp.yml`. This is a deployment-default flaw rather than a code flaw, so it also affects anyone who copied the example compose file into a production or internet-reachable host. Downstream: the entire blueprintUE data model and its user/identity store.

**Source:** https://github.com/blueprintue/blueprintue-self-hosted-edition/blob/v4.3.6/docker-examples/database.env · https://github.com/blueprintue/blueprintue-self-hosted-edition/blob/v4.3.6/docker-examples/docker-compose-smtp.yml#L14-L24 · https://github.com/blueprintue/blueprintue-self-hosted-edition/commit/e6a6e1d4c2f22efbbabf9fb31ec479544405b469

**Actions:**
- Fix: Upgrade to blueprintUE Self-Hosted Edition 4.3.7 and regenerate configuration from the corrected examples.
- Workaround: Set a MariaDB root password, remove the `3306` host port publication so the database is reachable only on the internal compose network, and add firewall rules denying 3306 from untrusted sources.
- Tradeoff: External database clients, admin GUI tools, and any out-of-cluster reporting job that connects over published 3306 will stop working until moved onto the internal network or given an explicit allowlist.

#### Docker (Gotenberg) — CVE-2026-42596 (CVSS 9.4 CRITICAL)
**Summary:** Gotenberg's default deny-lists for the `downloadFrom` and webhook features are regex-based and case-sensitive, so an unauthenticated attacker can supply URLs such as `http://[::ffff:127.0.0.1]:...` and reach loopback or private HTTP services the deny-list is meant to block. This lets an external caller force the server to make outbound requests to internal-only targets.

**Affected Features / Interoperability:** The `downloadFrom` remote-fetch feature and the webhook feature in versions prior to 8.31.0. In cloud deployments this is the classic SSRF path to the instance metadata service and to internal service meshes, so IAM role credentials and internal admin APIs are in scope even though the data does not name a specific metadata endpoint.

**Source:** https://github.com/gotenberg/gotenberg/security/advisories/GHSA-4vmc-gm8v-m35h

**Actions:**
- Fix: Upgrade to Gotenberg 8.31.0 or later.
- Workaround: Force egress through a proxy that resolves and rejects loopback, link-local, RFC 1918, and metadata addresses; block `downloadFrom` and webhook use for untrusted callers at the ingress.
- Tradeoff: Legitimate remote-fetch and webhook callbacks to internal services break, and an egress proxy adds latency plus one more component to operate.

#### Docker (Heym) — CVE-2026-67543 (CVSS 8.8 HIGH)
**Summary:** Heym hardens its Python tool executor with a mandatory Docker sandbox (no network, read-only filesystem, non-root, no Docker socket) but its sibling skill executor runs skill Python via a local backend subprocess with only a 512 MB RLIMIT and a 7-key environment denylist. A skill therefore executes directly inside the backend execution context with the backend's privileges.

**Affected Features / Interoperability:** The skill Python executor (`skill_python_executor.py`) in Heym prior to 0.0.70, contrasted with `python_tool_executor.py`. Any skill authored or imported into the platform is an untrusted-code path into the backend host; the data does not specify which host credentials or mounted paths the backend context holds.

**Source:** https://github.com/heymrun/heym/commit/2155057f4153a1e3a7b789d104f7fa96e92964e5 · https://github.com/heymrun/heym/commit/28bb2901e4dea128ac493f67ee9478d230b7a3d7 · https://github.com/heymrun/heym/releases/tag/0.0.70

**Actions:**
- Fix: Upgrade to Heym 0.0.70.
- Workaround: Restrict skill authoring and installation to trusted principals, and run the Heym backend itself inside a constrained container with a dedicated low-privilege service account.
- Tradeoff: Skill development becomes a privileged, gated activity rather than something any workspace member can do, and skills that need network or filesystem access may fail under a tighter backend sandbox.

#### Docker (Heym) — CVE-2026-67544 (CVSS 8.8 HIGH)
**Summary:** Heym's workflow engine accepts an arbitrary Python string in the `playwrightCode` field of a Playwright node, writes it to a temporary `.py` file, and executes it via `subprocess.Popen([sys.executable, script_path])` with no sandboxing, AST validation, or role gate. Any authenticated user — including a freshly registered account — achieves remote code execution on the backend host as the service process user.

**Affected Features / Interoperability:** The Playwright node of the Heym workflow engine, prior to 0.0.71. Because the code runs as the backend service user, everything that user can reach is exposed: workflow definitions, stored credentials for other nodes, and the host filesystem. The data does not state whether self-registration is enabled by default.

**Source:** https://github.com/heymrun/heym/commit/d2fd46c07754c4ed3e80b521aa54cc276039849b · https://github.com/heymrun/heym/releases/tag/0.0.71 · https://github.com/heymrun/heym/security/advisories/GHSA-mp23-7m6r-jfw4

**Actions:**
- Fix: Upgrade to Heym 0.0.71.
- Workaround: Disable open self-registration, gate workflow create/edit behind an admin role, and run the backend as an unprivileged user in a container with no host mounts.
- Tradeoff: Authoring Playwright-based workflows becomes an administrative task, and reduced backend privileges may break workflows that legitimately touch host resources.

#### Docker (Gotenberg) — CVE-2026-42595 (CVSS 8.6 HIGH)
**Summary:** Prior to 8.32.0, Gotenberg's Chromium URL-to-PDF endpoint (`/forms/chromium/convert/url`) has no default SSRF protection — the default deny-list regex blocks only `file://` URIs. An unauthenticated attacker can point Chromium at loopback, RFC 1918 ranges, or cloud metadata endpoints and receive the response rendered as a PDF, and even a configured custom deny-list is bypassed because Chromium follows 302 redirects.

**Affected Features / Interoperability:** The Chromium URL-to-PDF conversion endpoint. This is a credential-theft path in cloud environments: rendered metadata responses hand IAM role credentials to an external caller. Any integration that accepts user-supplied URLs for PDF rendering inherits the exposure.

**Source:** https://github.com/gotenberg/gotenberg/security/advisories/GHSA-chwh-f6gm-r836

**Actions:**
- Fix: Upgrade to Gotenberg 8.32.0 or later.
- Workaround: Require IMDSv2 with a hop limit of 1 on the host, block link-local `169.254.169.254` at the network layer, and disable the URL conversion endpoint for untrusted callers.
- Tradeoff: Hop limit 1 breaks any legitimate container or sidecar that retrieves credentials through the host, and disabling URL conversion removes a core Gotenberg feature.

#### Docker (Gotenberg) — CVE-2026-40893 (CVSS 8.2 HIGH)
**Summary:** Prior to 8.31.0, Gotenberg checks only whether an ExifTool tag is exactly `FileName`, so `System:FileName` passes the filter and ExifTool renames the file. Remote attackers can move, rename, and change permissions on arbitrary files reachable by the Gotenberg process.

**Affected Features / Interoperability:** The same metadata write path as the two Gotenberg RCE issues, using the `System:FileName` tag variant. Impact is bounded by the container's filesystem and the permissions of the Gotenberg process.

**Source:** https://github.com/gotenberg/gotenberg/security/advisories/GHSA-62p3-hvxx-fxg4

**Actions:**
- Fix: Upgrade to Gotenberg 8.31.0 or later.
- Workaround: Block the metadata write endpoint at the proxy and run Gotenberg non-root with a read-only root filesystem.
- Tradeoff: Metadata writing is lost; read-only rootfs needs a scoped writable temp path for processing.

#### Kubernetes (Traefik) — CVE-2026-44774 (CVSS 9.9 CRITICAL)
**Summary:** Traefik's Kubernetes Gateway API provider accepts any `TraefikService` backend reference whose name ends in `@internal`, so a tenant holding only HTTPRoute creation permissions can route traffic to `rest@internal` in addition to the intended `api@internal`. That exposes the REST provider handler and bypasses the `providers.rest.insecure=false` setting, handing a low-privileged actor live dynamic configuration control in shared Gateway deployments where the REST provider is enabled.

**Affected Features / Interoperability:** The Kubernetes Gateway API provider and `TraefikService` `@internal` backend resolution in Traefik prior to 2.11.46, 3.6.17, and 3.7.1. Downstream, live dynamic configuration means an attacker can alter routing, middleware, and TLS behavior for every route Traefik serves — so ingress, mTLS termination, and any auth middleware chained at the edge are all in scope. Multi-tenant clusters sharing one Gateway are the exposed topology.

**Source:** https://github.com/traefik/traefik/releases/tag/v2.11.46 · https://github.com/traefik/traefik/releases/tag/v3.6.17 · https://github.com/traefik/traefik/releases/tag/v3.7.1

**Actions:**
- Fix: Upgrade to Traefik 2.11.46, 3.6.17, or 3.7.1.
- Workaround: Disable the REST provider entirely (`providers.rest.enabled=false`), or move to dedicated Traefik/Gateway instances per tenant, and remove broad HTTPRoute/TraefikService create permissions from tenant roles.
- Tradeoff: Disabling the REST provider removes the dynamic configuration API used for GitOps and external config pushes; per-tenant Gateways multiply control-plane and certificate-management overhead.

#### Kubernetes (Kyverno) — CVE-2026-41068 (CVSS 7.7 HIGH)
**Summary:** The fix for CVE-2026-22039 validated the `URLPath` field of Kyverno's `apiCall` context but left the ConfigMap context loader with the identical flaw: `configMap.namespace` accepts any namespace with no validation. A namespace admin can read ConfigMaps from any namespace using Kyverno's privileged service account, which is a complete RBAC bypass in multi-tenant clusters.

**Affected Features / Interoperability:** The ConfigMap context loader used by Kyverno policies, prior to 1.17.2. Any policy that resolves a ConfigMap at evaluation time is affected, and Kyverno's service account becomes an escalation path to cluster-wide configuration and any secret material stored in ConfigMaps. Downstream, admission decisions in every namespace can be influenced by data an untrusted tenant should not be able to read.

**Source:** https://github.com/kyverno/kyverno/commit/bbf3e5c01391d612968440659028ae98e565a777 · https://github.com/kyverno/kyverno/security/advisories/GHSA-cvq5-hhx3-f99p

**Actions:**
- Fix: Upgrade to Kyverno 1.17.2.
- Workaround: Restrict who can create or modify Kyverno policies, and trim Kyverno's ClusterRole so its service account cannot read ConfigMaps in tenant namespaces.
- Tradeoff: Policies that depend on cross-namespace ConfigMap lookups will fail to resolve context, which can cause admission errors or unexpected policy failures if `failurePolicy` is set to `Fail`.

#### Kubernetes (DevSpace) — CVE-2026-42283 (CVSS 7.7 HIGH)
**Summary:** DevSpace's UI server WebSocket accepts connections from all origins by default, exposing several endpoints over it. A developer who runs the DevSpace UI while also browsing the web can be induced by a malicious site to let their own browser open a cross-origin WebSocket to `ws://127.0.0.1:8090`.

**Affected Features / Interoperability:** The local DevSpace UI server in versions prior to 6.3.21. This is a developer-workstation issue rather than a cluster control-plane issue, but the reachable endpoints act on the developer's Kubernetes context, so the blast radius is whatever that kubeconfig can do. The data does not enumerate which endpoints are exposed over the socket.

**Source:** https://github.com/devspace-sh/devspace/security/advisories/GHSA-hqwm-7x7x-8379

**Actions:**
- Fix: Upgrade to DevSpace 6.3.21.
- Workaround: Do not run the DevSpace UI on workstations that browse untrusted sites, or bind it to loopback only and block the port from browser-reachable contexts; use a dedicated browser profile with no access to the UI port.
- Tradeoff: Developers lose the DevSpace UI workflow, or must context-switch browsers, which is a real productivity cost for cluster debugging.

#### Kubernetes (Red Hat Advanced Cluster Security) — CVE-2026-9165 (CVSS 7.7 HIGH)
**Summary:** RHACS Central does not limit the depth of GraphQL queries on its authenticated GraphQL API. A user holding a valid API token can submit deeply nested queries that consume excessive resources in Central, producing a denial of service against the management plane.

**Affected Features / Interoperability:** The authenticated GraphQL API of RHACS Central. Downstream, the management plane is what the ACS console, policy enforcement, CI/CD image scanning integrations, and notification pipelines depend on — a Central outage degrades visibility and admission-time policy decisions cluster-wide. Authentication is required, so the exposure is limited to token holders and their blast radius.

**Source:** https://access.redhat.com/errata/RHSA-2026:36207 · https://access.redhat.com/errata/RHSA-2026:36319 · https://access.redhat.com/errata/RHSA-2026:36625

**Actions:**
- Fix: Apply the fixes from RHSA-2026:36207, RHSA-2026:36319, or RHSA-2026:36625 as appropriate for your installation.
- Workaround: Scope API tokens to the minimum needed, audit and prune stale tokens, and place a proxy in front of Central that caps request body size, query depth, and request rate.
- Tradeoff: Aggressive depth or rate caps can break legitimate dashboards and complex CI queries, and token tightening may break existing automation that assumes broad read access.

#### Kubernetes (Eclipse BaSyx Helm Charts) — CVE-2026-123047 (CVSS 7.5 HIGH)
**Summary:** In `basyx` chart versions 3.0.0-rc.1 through 3.12.1, the `keycloak-init-config.yaml` template renders `keycloak.initialization.users`, including each user's `credentials[].value`, as `users.json` into the persistent ConfigMap `<release>-basyx-keycloak-init-config`. By default this includes the bootstrap administrator, which holds the `admin` role with a non-temporary password, stored in cleartext.

**Affected Features / Interoperability:** The bundled Keycloak initialization path of the Eclipse BaSyx `basyx` chart. Because that bootstrap admin governs the Keycloak realm, anyone who can read ConfigMaps in the namespace gains identity-provider administration and, through it, access to every BaSyx application that federates to this Keycloak. Downstream: Asset Administration Shell identity, and any relying-party integration trusting the realm.

**Source:** https://github.com/eclipse-basyx/charts/pull/106 · https://github.com/eclipse-basyx/charts/releases/tag/basyx-3.12.2 · https://github.com/eclipse-basyx/charts/security/advisories/GHSA-6438-759f-6f8v

**Actions:**
- Fix: Upgrade the chart to basyx-3.12.2.
- Workaround: Restrict ConfigMap read RBAC in the namespace to only the principals that need it, rotate the bootstrap administrator password out-of-band, and externalize Keycloak to a managed identity provider.
- Tradeoff: Tightening ConfigMap RBAC can break controllers and dashboards that enumerate ConfigMaps, and an external IdP adds integration and lifecycle work.

#### Kubernetes (Eclipse BaSyx Helm Charts) — CVE-2026-123059 (CVSS 7.5 HIGH)
**Summary:** In `aas-basyx-v2-full` chart version 2.2.0, the `basyx-keycloak-realm.yaml` template substitutes the `basyx-technical-user` OAuth2 client secret into the Keycloak realm-import JSON, which is stored in a ConfigMap. **Affected Features / Interoperability:** The realm-import path of the `aas-basyx-v2-full` chart, ConfigMap `<keycloak.fullnameOverride>-realm...`. Downstream impact mirrors the previous entry: realm administration and every service that trusts the technical user's token. The duplication also means secret rotation must be applied in two places or the ConfigMap copy silently goes stale.

**Source:** https://github.com/eclipse-basyx/charts/pull/46 · https://github.com/eclipse-basyx/charts/releases/tag/aas-basyx-v2-full-2.2.0 · https://github.com/eclipse-basyx/charts/security/advisories/GHSA-6438-759f-6f8v

- Workaround: Restrict ConfigMap read RBAC in the namespace, rotate the `basyx-technical-user` client secret, and confirm the realm-import ConfigMap no longer contains it.

#### Kubernetes (Flannel) — CVE-2026-32241 (CVSS 7.5 HIGH)
**Summary:** Flannel's experimental Extension backend passes attacker-controlled data from the `flannel.alpha.coreos.com/backend-data` node annotation to `SubnetAddCommand` and `SubnetRemoveCommand` via stdin without adequate handling, yielding command injection. An attacker who can set Kubernetes Node annotations achieves root-level arbitrary command execution on every Flannel node in the cluster.

**Affected Features / Interoperability:** The Flannel Extension backend in versions prior to 0.28.2. This is the CNI, so compromise means root on all nodes and therefore control of pod networking cluster-wide — network policy enforcement, service routing, and inter-node traffic all become attacker-controlled. The prerequisite is write access to Node objects or their annotations, which is a meaningful but not exotic permission in many clusters.

**Source:** https://github.com/flannel-io/flannel/releases/tag/v0.28.2 · https://github.com/flannel-io/flannel/security/advisories/GHSA-vchx-5pr6-ffx2

**Actions:**
- Fix: Upgrade Flannel to 0.28.2.
- Workaround: Do not use the experimental Extension backend, remove `nodes` update/patch and `nodes/status` permissions from all but the core controllers, and add an admission policy that blocks writes to the `flannel.alpha.coreos.com/backend-data` annotation.
- Tradeoff: Admission policies on Node objects can interfere with legitimate node-labeling automation and cluster-autoscaler or upgrade tooling, so scope the rule narrowly to the one annotation.

#### Kubernetes (AAP Gateway Operator) — CVE-2026-126643 (CVSS 6.5 MEDIUM)
**Summary:** When reconciling an AutomationController, the AAP Gateway Operator reads the protected resource-server Secret (`Secret/<aap-name>-resource-server`, key `controller_resource_server_secret`) and copies its plaintext value into the generated AutomationController custom resource under `spec.extra_settings` (`RESOURCE_SERVER.SECRET_KEY`). The operator uses `no_log` to keep the value out of its own logs, but serializing it into the CR exposes it to any principal able to read the CR without permission to read the backing Secret.

**Affected Features / Interoperability:** The AAP Gateway Operator's AutomationController reconciliation. The leak surface is broader than RBAC alone: custom resources commonly end up in GitOps repositories, etcd backups, audit logs, and `kubectl get -o yaml` output pasted into tickets. Downstream, the resource-server secret is the trust anchor between Automation Controller and the gateway.

**Source:** https://access.redhat.com/security/cve/CVE-2026-126643 · https://bugzilla.redhat.com/show_bug.cgi?id=2571730

**Actions:**
- Fix: No fixed operator version is stated in the provided data; track the Red Hat CVE page and Bugzilla 2571730.
- Workaround: Restrict `get`/`list`/`watch` RBAC on AutomationController custom resources to the operator and named administrators, keep these CRs out of Git and shared backups, and rotate `controller_resource_server_secret`.
- Tradeoff: Operators lose the ability to inspect CRs for troubleshooting, and GitOps-managed AutomationControllers cannot be reconciled from a repository without reintroducing the exposure.

#### Kubernetes (Traefik) — CVE-2026-41174 (CVSS 6.4 MEDIUM)
**Summary:** With `providers.kubernetesCRD.allowCrossNamespace=false`, Traefik correctly rejects direct cross-namespace middleware references from IngressRoute objects but does not apply the same restriction to middleware references nested inside a Chain middleware's `spec.chain.middlewares[]`. An actor who can create or update Traefik CRDs in their own namespace can use that gap to reach middleware in other namespaces.

**Affected Features / Interoperability:** The Kubernetes CRD provider's cross-namespace isolation enforcement, in versions prior to 2.11.43, 3.6.14, and 3.7.0-rc.2. Downstream, tenants can pull another tenant's authentication, header-rewrite, rate-limit, or IP-allowlist middleware into their own routes — which breaks the isolation guarantee that shared Traefik deployments rely on and can silently change how requests are authenticated or transformed.

**Source:** https://github.com/traefik/traefik/commit/df00d82fc7f12e07199551832b54de6d0e55414d · https://github.com/traefik/traefik/releases/tag/v2.11.43 · https://github.com/traefik/traefik/releases/tag/v3.6.14

**Actions:**
- Fix: Upgrade to Traefik 2.11.43, 3.6.14, or later (3.7.0-rc.2 also contains the fix).
- Workaround: Add an admission policy that rejects Chain middlewares containing references to a namespace other than the Chain's own, and keep `allowCrossNamespace=false` in place.
- Tradeoff: Chains that legitimately compose shared platform middleware from a central namespace will be rejected and need those middlewares duplicated per tenant.

#### Kubernetes (Kyverno) — CVE-2026-44245 (CVSS 6.1 MEDIUM)

**Affected Features / Interoperability:** The Kyverno policy-detail UI component in versions prior to 2.5.2. Impact is a cross-site scripting path in the browser of whoever reviews policies and reports, so it targets the platform engineering role rather than the cluster directly. The provided description is truncated at the point where it names the Kubernetes resource that supplies the data, so the exact source object is not stated.

**Source:** https://github.com/kyverno/kyverno/security/advisories/GHSA-q98m-7w8c-w388

**Actions:**

#### AWS (FrodoBots EarthRover Mini+) — CVE-2026-121686 (CVSS 9.8 CRITICAL)
**Summary:** FrodoBots EarthRover Mini+ firmware (version `6.2.4_6.2.5_0.614.0`) contains a firmware method that accepts arbitrary shell commands delivered over AWS IoT MQTT and executes them as root. **Actions:**
- Fix: No patched firmware version is provided in the data. Engage FrodoBots and monitor CERT/CC VU#188754 for a corrected release.
- Workaround: Isolate the fleet onto a dedicated AWS IoT account and VPC with no route to production, restrict the IoT policy to the minimum topic set, and treat all device telemetry as untrusted input.
- Tradeoff: Fleet isolation limits the operational data and remote-management reach your teams currently rely on, and tightening topic policies can break device-to-cloud command flows that assume wildcard publish/subscribe.
