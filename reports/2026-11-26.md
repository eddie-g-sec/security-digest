# Security Digest — 2026-11-26

## Cloud Security

Today's formal data covers two systems — Kubernetes (8 entries) and Docker (5 entries), all shown, none truncated — and contains **no CISA KEV-confirmed entries**, so nothing here carries confirmed-exploitation weight. The single most urgent item is **CVE-2026-112788 (CVSS 9.8, CRITICAL)** in Apache Texera (incubating): the Python virtual environment (PVE) management endpoints of a computing unit are entirely unauthenticated, and in local JVM and single-node Docker Compose deployments — which put no authenticating gateway in front of the services — they are reachable by anyone who can reach the network, giving unauthenticated code execution in a computing unit. It is closely followed by **CVE-2026-10059 (9.1, CRITICAL)** in the Red Hat Multicluster Engine for Kubernetes, where a namespace-scoped tenant administrator can mint a cluster-admin ServiceAccount token and take full control of the cluster. Note that the KEV additions reported in today's news feed (Mitel, Juniper, Vates, Danfoss, GeoServer) are not represented in the formal vulnerability data for this scope and are therefore not treated as confirmed-exploited here.

### Formal Vulnerabilities

#### Kubernetes — CVE-2026-112788 (CVSS 9.8 CRITICAL)
**Summary:** Missing authentication for a critical function in Apache Texera (incubating), affecting 1.1.0 through 1.2 (the advisory text provided is truncated mid-version). The Python virtual environment (PVE) management endpoints of a computing unit are not authenticated by the application itself, so in local JVM and single-node Docker Compose deployments — which place no authenticating gateway in front of the services — they are reachable without any credentials. Network-reachable and unauthenticated; only the Kubernetes deployment gates these endpoints at the gateway and thus provides the full security model described in SECURITY.md.

**Affected Features / Interoperability:** The PVE management endpoints of a Texera computing unit. Downstream, this is the control plane for workflow execution and code running inside computing units; the raw data does not enumerate specific integrations or client drivers affected. The data does state that the security model documented in SECURITY.md only holds for the Kubernetes deployment, so non-Kubernetes deployments should be treated as out of that model.

**Source:** https://lists.apache.org/thread/txzwrypygzpk004m90mg83lonbq3mgvb , http://www.openwall.com/lists/oss-security/2026/11/23/20

**Actions:**
- Fix: the provided advisory text is truncated before the fixed version; the companion Texera advisory for the same affected range (CVE-2026-96298, 1.1.0–1.2.0) states that upgrading to **1.3.0** fixes the issue. Confirm against the Apache advisory before scheduling.
- Workaround: place an authenticating gateway in front of the services, as the Kubernetes deployment does, and restrict network reachability to the PVE endpoints.
- Tradeoff: added gateway configuration and an extra hop; tooling or scripts that call the PVE endpoints directly will break and need to be re-pointed.

#### Kubernetes — CVE-2026-10059 (CVSS 9.1 CRITICAL)
**Summary:** A flaw in the Multicluster Engine for Kubernetes ClusterCurator controller. A tenant administrator holding only namespace-scoped privileges can create a namespaced ClusterCurator, which inadvertently grants the ability to mint a token for a ServiceAccount with cluster-wide administrative authority — a privilege escalation to full cluster control. Authentication is required, but only at the low-privilege tenant-administrator level.

**Affected Features / Interoperability:** The ClusterCurator controller and its ServiceAccount token minting. Downstream impact is on multi-tenant isolation and RBAC boundaries: namespace-scoped delegation no longer contains a tenant administrator. The raw data does not specify which other components or integrations are affected.

**Source:** https://access.redhat.com/errata/RHSA-2026:59556 , https://access.redhat.com/errata/RHSA-2026:59557 , https://access.redhat.com/errata/RHSA-2026:59558

**Actions:**
- Fix: apply the Red Hat errata listed above (RHSA-2026:59556 / 59557 / 59558).
- Workaround: remove or tightly limit tenant administrators' ability to create ClusterCurator resources, and audit existing ClusterCurator objects and recently minted ServiceAccount tokens.
- Tradeoff: breaks tenant self-service cluster curation workflows and requires manual handling by the platform team.

#### Kubernetes — CVE-2026-137480 (CVSS 8.7 HIGH)
**Summary:** Traefik 3.7.15 before 3.7.18 and 3.8.0-rc.1 before 3.8.0-rc.2 contain a client certificate authentication bypass in the Kubernetes Ingress NGINX provider. On hosts shared by multiple Ingresses using `auth-tls-secret`, the `Ssl-Client-*` headers are built per Ingress while the TLS handshake uses the first Ingress's settings, so unauthenticated remote attackers can obtain `Ssl-Client-Verify: SUCCESS` with a client-chosen subject and issuer for an unverified certificate, or inject `Ssl-Client-*` headers directly. No credentials are needed; the target is network-reachable.

**Affected Features / Interoperability:** Traefik's Kubernetes Ingress NGINX provider and its `auth-tls-secret` mutual-TLS handling. Downstream, any backend that trusts the proxy's `Ssl-Client-*` headers for identity or authorization will accept forged identities; the raw data does not list specific backends or integrations.

**Source:** https://github.com/traefik/traefik/security/advisories/GHSA-ccgh-9g52-6vwg , https://www.vulncheck.com/advisories/traefik-3.7.15-before-3.7.18-client-certificate-verification-bypass-via-ssl-client-headers

**Actions:**
- Fix: upgrade to Traefik **3.7.18**, or **3.8.0-rc.2** on the 3.8 release-candidate line.
- Workaround: avoid sharing a host across Ingresses that use differing `auth-tls-secret` settings, and stop having backends trust `Ssl-Client-*` headers (strip or ignore them at the backend).
- Tradeoff: loses host consolidation across Ingresses and requires backend authorization logic to be reworked to not depend on proxy-supplied identity headers.

#### Kubernetes — CVE-2026-96298 (CVSS 8.1 HIGH)
**Summary:** Missing authorization in the computing unit workflow websocket of Apache Texera (incubating), affecting 1.1.0 through 1.2.0. An authenticated user can view workflow results, control workflow executions, and run code in a computing unit they have not been granted. In local JVM and single-node Docker Compose deployments this is possible directly; in Kubernetes deployments it is possible from code running inside another computing unit in the cluster.

**Affected Features / Interoperability:** The computing unit workflow websocket. Downstream, this breaks the isolation guarantee between computing units and allows cross-unit code execution; in Kubernetes the attack path runs through code already executing inside a cluster computing unit. The raw data does not enumerate other affected integrations.

**Source:** https://lists.apache.org/thread/d45hrydn9dpqvdnjpnkx9t6q8fcyzl7y , http://www.openwall.com/lists/oss-security/2026/11/23/26

**Actions:**
- Fix: upgrade to **1.3.0**, which the advisory states fixes the issue.
- Workaround: restrict which authenticated users can reach the workflow websocket, and segment computing units so that code in one unit cannot reach another's websocket.
- Tradeoff: segmentation and access restriction reduce the shared-computing-unit model Texera is designed around and add operational overhead.

#### Kubernetes — CVE-2026-103314 (CVSS 7.4 HIGH)
**Summary:** A flaw in Red Hat Advanced Cluster Security for Kubernetes (RHACS): the Central SAML authentication ACS endpoint does not retain used SAML assertion or response identifiers, so replay is not prevented. An attacker who obtains a valid, unexpired signed SAML response can submit it multiple times and receive distinct Central authentication tokens for the mapped identity. Exploitation requires possession of a signed response and network access to the Central endpoint.

**Affected Features / Interoperability:** RHACS Central's SAML single-sign-on authentication path and the identity mapping it performs. Downstream, SSO-based login to Central and any workflow relying on Central token issuance are affected; the raw data does not specify other integrations.

**Source:** https://access.redhat.com/errata/RHSA-2026:85932 , https://access.redhat.com/errata/RHSA-2026:92342 , https://access.redhat.com/security/cve/CVE-2026-103314

**Actions:**
- Fix: apply RHSA-2026:85932 and/or RHSA-2026:92342.
- Workaround: shorten SAML assertion validity lifetimes at the identity provider, monitor Central for repeated assertion submissions, and consider temporarily disabling SAML SSO in favor of another authentication method.
- Tradeoff: shorter assertion lifetimes increase IdP round-trips and can cause login failures; disabling SAML SSO breaks federated login and forces local accounts.

#### Kubernetes — CVE-2026-136451 (CVSS 6.8 MEDIUM)
**Summary:** A flaw in the Keycloak Operator: deterministic hashes derived from Kubernetes Secrets are published in generated StatefulSet metadata and in `KeycloakOIDCClient` status. A user with read access to those resources may be able to recover a low-entropy credential referenced by a Secret, even when Kubernetes RBAC denies that user access to the Secret itself. Authentication and read access to the affected resources are required.

**Affected Features / Interoperability:** The Keycloak Operator's generated StatefulSet metadata and `KeycloakOIDCClient` status fields. Downstream, this undermines RBAC as a control for Secret confidentiality and affects any tooling or dashboard that reads those resources; the raw data does not name specific integrations.

**Source:** https://access.redhat.com/security/cve/CVE-2026-136451 , https://bugzilla.redhat.com/show_bug.cgi?id=2583677

**Actions:**
- Fix: no patched version is stated in the provided data; track the linked Red Hat Bugzilla for the fix.
- Workaround: restrict read access to the affected StatefulSets and `KeycloakOIDCClient` status objects, and replace low-entropy credentials referenced by Secrets with high-entropy ones so hash recovery is not practical.
- Tradeoff: restricting read access degrades operator observability and debugging, and credential rotation requires coordinated Keycloak client updates.

#### Kubernetes — CVE-2023-6476 (CVSS 6.5 MEDIUM)
**Summary:** A flaw in CRI-O involving an experimental annotation that leads to a container being unconfined. A pod can use it to specify and obtain any amount of memory or CPU, circumventing the Kubernetes scheduler and potentially causing a denial of service on the node. Exploitation requires the ability to create pods on the affected node.

**Affected Features / Interoperability:** CRI-O's experimental annotation handling and, downstream, scheduler-enforced resource accounting and node stability for all workloads on that node. The raw data does not name other affected components.

**Source:** https://access.redhat.com/errata/RHSA-2024:0195 , https://access.redhat.com/errata/RHSA-2024:0207 , https://access.redhat.com/security/cve/CVE-2023-6476

**Actions:**
- Fix: apply RHSA-2024:0195 and/or RHSA-2024:0207.
- Workaround: do not enable the experimental annotation, and block untrusted workloads from setting it (policy enforcement at admission).
- Tradeoff: admission blocking adds policy complexity and can reject legitimate workloads that rely on the annotation.

#### Kubernetes — CVE-2026-137573 (CVSS 4.3 MEDIUM)
**Summary:** KodeRover Zadig before 5.1.0 contains a missing authorization flaw in the aslan environment `kube.go` handlers. An authenticated user can supply arbitrary `clusterID` and `namespace` values to `/api/aslan/environment/kube/` routes to query Kubernetes clusters belonging to other projects, enumerating namespaces, nodes, deployments, workloads, canary mappings, and resource names. Authentication is required; the flaw is cross-project information disclosure rather than direct cluster takeover.

**Affected Features / Interoperability:** Zadig's aslan environment API (`/api/aslan/environment/kube/` routes). Downstream, project-level isolation in Zadig is broken and cluster topology details leak to other tenants; the raw data does not list further integrations.

**Source:** https://github.com/koderover/zadig/blob/v5.0.0/pkg/microservice/aslan/core/environment/handler/kube.go#L283-L288 , https://github.com/koderover/zadig/commit/4dad9e13d45297d72e35200bdb362994b8b36246 , https://github.com/koderover/zadig/issues/5038

**Actions:**
- Fix: upgrade to Zadig **5.1.0** (the advisory covers versions before 5.1.0; the fix commit is linked above).
- Workaround: restrict network access to the Zadig API to trusted users and review which users hold Zadig accounts across projects.
- Tradeoff: tighter API access limits self-service developer workflows and may require a bastion or VPN path.

#### Docker — CVE-2026-112788 (CVSS 9.8 CRITICAL)
**Summary:** Same Apache Texera (incubating) missing-authentication flaw described under Kubernetes above, and the single-node Docker Compose deployment is called out explicitly as affected: with no authenticating gateway in front of the services, the PVE management endpoints of a computing unit are reachable without credentials. Affected range is 1.1.0 through 1.2 (advisory text truncated). Unauthenticated and network-reachable.

**Affected Features / Interoperability:** The PVE management endpoints of a Texera computing unit in Docker Compose deployments; downstream this is unauthenticated control of workflow execution and code execution in the unit. The data notes only the Kubernetes deployment provides the full SECURITY.md security model, so Compose deployments are outside it.

**Source:** https://lists.apache.org/thread/txzwrypygzpk004m90mg83lonbq3mgvb , http://www.openwall.com/lists/oss-security/2026/11/23/20

**Actions:**
- Fix: the provided text is truncated before the fixed version; the companion advisory for the same range (CVE-2026-96298) states **1.3.0** fixes it — verify against the Apache advisory.
- Workaround: front the Compose services with an authenticating gateway and restrict network exposure of the PVE endpoints to localhost or a trusted network.
- Tradeoff: added gateway configuration and an extra hop; direct local tooling against the PVE endpoints will break.

#### Docker — CVE-2026-77230 (CVSS 8.1 HIGH)
**Summary:** Camunda 8.8.0 before 8.8.47, 8.9.0 before 8.9.29, 8.10.0 before 8.10.10, and 8.11.0-alpha1 contain an insecure deserialization flaw in the persistent web session feature, which stores session attributes as Java-serialized data in secondary storage and deserializes them via an `ObjectInputStream` without an `ObjectInputFilter`. An attacker with write access to the web session index — for example an unauthenticated Elasticsearch cluster deployed via Camunda's own docker-compose files — can plant a crafted serialized object and trigger deserialization by presenting a matching session cookie. The provided description is truncated mid-sentence, so the full impact chain is not stated.

**Affected Features / Interoperability:** Camunda's persistent web session feature and its secondary-storage (Elasticsearch) session index. Downstream, the docker-compose reference deployments ship an unauthenticated Elasticsearch, which is the practical write path; session handling and any integration reading that index are affected.

**Source:** https://github.com/camunda/camunda/commit/5870c91d4ec8c2dae96db60f3261daed2273baf2 , https://github.com/camunda/camunda/commit/82b490cd41a685118b63a378d8963334711b7d8d , https://github.com/camunda/camunda/commit/aaf0498ec37dc9b43dbbab2616f3bf5303f911ce

**Actions:**
- Fix: upgrade to **8.8.47**, **8.9.29**, or **8.10.10** as appropriate for your line; the data lists 8.11.0-alpha1 as affected but does not state the fixed 8.11 build.
- Workaround: secure the Elasticsearch instance backing web sessions — enable authentication and restrict network access so it is not reachable unauthenticated.
- Tradeoff: securing the bundled Elasticsearch breaks the out-of-the-box docker-compose demo flow and requires credential management.

#### Docker — CVE-2026-120676 (CVSS 7.2 HIGH)
**Summary:** The Forminator Forms – Contact Form, Payment Form & Custom Form Builder WordPress plugin is vulnerable to stored cross-site scripting via the `upload-1` parameter (the File Upload field's `element_id`) in all versions up to and including 1.58.4, due to insufficient input sanitization and output escaping. Unauthenticated attackers can inject arbitrary web scripts that execute whenever a user accesses an injected page. The advisory notes this is an incomplete fix for CVE-2024-1794 and that exploitation requires the form's File Upload field to be left at a particular setting — the provided text is truncated there, so the exact precondition is not stated. No fixed version is given in the provided data.

**Affected Features / Interoperability:** The Forminator plugin's File Upload field. Downstream, any page embedding a Forminator form with that field is a stored-XSS sink affecting admins and other visitors; the raw data does not name other affected components. Note this entry appears under Docker in the source grouping, presumably reflecting a containerized WordPress deployment; the data does not say so explicitly.

**Source:** https://plugins.trac.wordpress.org/browser/forminator/tags/1.58.4/library/abstracts/abstract-class-field.php#L2420 , https://plugins.trac.wordpress.org/browser/forminator/tags/1.58.4/library/fields/upload.php#L399 , https://plugins.trac.wordpress.org/browser/forminator/tags/1.58.4/library/fields/upload.php#L403

**Actions:**
- Fix: no fixed version is stated in the provided data; check the plugin's changelog and WordPress.org advisory for the patched release.
- Workaround: remove the File Upload field from Forminator forms, or restrict who can submit and view those forms, and deploy a WAF rule for the `upload-1` parameter.
- Tradeoff: removing the File Upload field breaks file-collection forms; WAF rules add latency and can produce false positives.

#### Docker — CVE-2026-137472 (CVSS 6.8 MEDIUM)
**Summary:** SiYuan from 3.6.2 before 3.8.10 contains a path traversal flaw: the `globalCopyFiles` and `workspaceCopyFiles` denylists omit `/home`, `/mnt`, `/media`, and `/snap`, so an admin token holder can read files outside the workspace. An attacker can copy other users' SSH `authorized_keys`, Docker and AWS configs, or mounted files into the workspace and retrieve them via the `getFile` API. An admin token is required, so this is authenticated but high-impact credential theft.

**Affected Features / Interoperability:** SiYuan's `globalCopyFiles` / `workspaceCopyFiles` features and the `getFile` API. Downstream, host-mounted secrets — SSH keys, Docker and AWS configuration — are exposed to any admin token holder; the raw data does not list further integrations.

**Source:** https://github.com/siyuan-note/siyuan/security/advisories/GHSA-wg79-89vp-f9vw , https://www.vulncheck.com/advisories/siyuan-3.6.2-before-3.8.10-path-traversal-via-globalcopyfiles-denylist-gaps

**Actions:**
- Fix: upgrade to SiYuan **3.8.10**.
- Workaround: limit who holds an admin token, and remove or relocate sensitive host files (SSH keys, Docker and AWS configs) from paths mounted into the SiYuan workspace.
- Tradeoff: relocating credentials breaks existing tooling that expects them at the standard paths, and restricting admin tokens limits legitimate administration.
