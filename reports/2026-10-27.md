# Security Digest — 2026-10-27

## Cloud Security

The most urgent finding this cycle is a cluster of **CVSS 10.0 (Critical) authentication bypasses** affecting Kubernetes identity and configuration components — notably CVE-2026-46389 in UDS Identity Config (Keycloak client secret overwrite) and CVE-2026-83938 in Azure Kubernetes Configuration Service (missing authentication for critical function). Both allow unauthenticated network attackers to elevate privileges or impersonate clients, directly compromising cluster control planes. No CISA KEV entries appear in today’s feed, so these confirmed-critical vulnerabilities take top priority. Additional critical-severity issues span Docker (hardcoded JWT secret, unauthenticated RCE), Terraform (webhook signature bypass), and multiple Kubernetes operators (Argo CD, Burrito, Local Path Provisioner). Patching or mitigating these should be the immediate focus for any environment running the affected versions.

### Formal Vulnerabilities

#### AWS — CVE-2026-115418 (CVSS 7.3 HIGH)
**Summary:** SQL injection exists in the `@aws-cdk/aws-redshift-alpha` module (before v2.274.0-alpha.0) within custom resource handlers for database queries. An attacker who can influence construct property values (e.g., crafted usernames, comments, or passwords) can execute arbitrary SQL with Redshift superuser privileges, including granting access to all cluster users. Exploitation requires the ability to supply input to CDK construct properties, typically during infrastructure deployment or update.

**Affected Features / Interoperability:** The `@aws-cdk/aws-redshift-alpha` construct library (alpha tier). Downstream impact includes any CDK stacks that deploy Redshift clusters using this module; superuser-level SQL execution could modify permissions, exfiltrate data, or disrupt cluster operations.

**Source:** https://aws.amazon.com/security/security-bulletins/2026-151-aws/, https://github.com/aws/aws-cdk/releases#release-v2.274.0, https://github.com/aws/aws-cdk/security/advisories/GHSA-25hh-xvj4-2cqv

**Actions:**
- Fix: Upgrade to `@aws-cdk/aws-redshift-alpha` v2.274.0-alpha.0 or later.
- Workaround: Review and revoke any overly broad `GRANT` statements to `PUBLIC` on existing clusters; restrict who can modify CDK construct inputs.
- Tradeoff: No significant tradeoff for the upgrade; the workaround may require auditing existing permissions.

#### Microsoft Azure — CVE-2026-45108 (CVSS 8.4 HIGH)
**Summary:** Himmelblau (an interoperability suite for Azure Entra ID and Intune) versions 2.0.0 through 3.1.4 and 2.3.11 contain an authentication bypass in the Device Authorization Grant flow. A user within the same Entra ID domain can obtain a local Unix session as another user by presenting their own valid credentials, because the `token_validate` function fails to verify that the local part of the authenticated user’s UPN matches the requested account.

**Affected Features / Interoperability:** Himmelblau’s Device Authorization Grant flow, used for Linux/Unix device login via Entra ID. Impacts any system relying on Himmelblau for Azure-joined device authentication.

**Source:** https://github.com/himmelblau-idm/himmelblau/security/advisories/GHSA-pmxh-j4r6-88mv

**Actions:**
- Fix: Upgrade to Himmelblau v3.1.5 or v2.3.12 (patched versions).
- Workaround: Restrict local account mappings or disable Himmelblau login until patched.
- Tradeoff: Disabling Himmelblau breaks Entra ID-based device login for Linux endpoints.

#### Microsoft Azure — CVE-2026-24899 (CVSS 7.5 HIGH)
**Summary:** Fleet (open-source device management) before v4.82.0 accepts Azure AD tokens from any tenant during Windows MDM enrollment. The JWT validation uses Microsoft’s multi-tenant JWKS endpoint but does not enforce `aud` (audience) or `iss` (issuer) claims, allowing any Microsoft-signed token with expected scopes to authenticate to Fleet’s MDM endpoints.

**Affected Features / Interoperability:** Fleet’s Windows MDM enrollment flow. Any Fleet instance with Windows MDM enabled is exposed; an attacker with access to any Azure AD tenant can obtain a valid token and enroll devices or access MDM APIs.

**Source:** https://github.com/fleetdm/fleet/releases/tag/fleet-v4.82.0, https://github.com/fleetdm/fleet/security/advisories/GHSA-ffg9-j72f-j6xm

**Actions:**
- Fix: Upgrade to Fleet v4.82.0 or later.
- Workaround: Disable Windows MDM enrollment if not required; otherwise, restrict network access to Fleet’s MDM endpoints.
- Tradeoff: Disabling Windows MDM prevents legitimate device enrollment.

#### Microsoft Azure — CVE-2026-42316 (CVSS 6.5 MEDIUM)

**Actions:**
- Fix: Upgrade to `kafka-sink-azure-kusto` v5.2.3 or later.
- Workaround: Restrict write access to the connector configuration; validate mapping entries manually before deployment.
- Tradeoff: Manual validation adds operational overhead; restricting config writes may impede legitimate updates.

#### Kubernetes — CVE-2026-46389 (CVSS 10.0 CRITICAL)
**Summary:** UDS Identity Config (versions 0.11.0 through 0.26.0) contains a logic error in the `client-kubernetes-secret` Keycloak client authenticator. The submitted `client_secret` is overwritten with a mounted Kubernetes secret before comparison, allowing any attacker who can reach the Keycloak token endpoint and knows a `client_id` using this authenticator to authenticate as that client with any `client_secret` value.

**Affected Features / Interoperability:** UDS Identity Config’s Keycloak client authenticator (`client-kubernetes-secret`), consumed by UDS Core’s Identity deployment. Compromise allows full impersonation of any client using this authenticator, potentially granting administrative access to the identity provider and downstream services.

**Source:** https://github.com/defenseunicorns/uds-identity-config/releases/tag/v0.26.1, https://github.com/defenseunicorns/uds-identity-config/security/advisories/GHSA-8mg2-6588-r4hw

**Actions:**
- Fix: Upgrade UDS Identity Config to v0.26.1 or later.
- Workaround: Restrict network access to the Keycloak token endpoint to trusted clients only; rotate all client secrets after upgrade.
- Tradeoff: Network restriction may break legitimate service-to-service authentication; secret rotation requires coordinated rollout.

#### Docker — CVE-2026-42869 (CVSS 10.0 CRITICAL)
**Summary:** SOCFortress CoPilot before v0.1.57 ships a hardcoded JWT signing secret as a fallback in `backend/app/auth/utils.py:28` and in `.env.example`. Any deployment where `JWT_SECRET` is not explicitly set (including the default Docker Compose setup) signs all authentication tokens with this publicly known value. An unauthenticated attacker can forge arbitrary admin-scoped JWTs and gain full control of the application and every security tool it manages.

**Affected Features / Interoperability:** SOCFortress CoPilot authentication system (JWT token signing). Default Docker Compose deployments are vulnerable; any deployment without an explicit `JWT_SECRET` environment variable.

**Source:** https://github.com/socfortress/CoPilot/commit/4640511a0cf2e7b144a71375b5b349a8318cb186, https://github.com/socfortress/CoPilot/pull/814, https://github.com/socfortress/CoPilot/security/advisories/GHSA-4gxj-hw3c-3x2x

**Actions:**
- Fix: Upgrade to SOCFortress CoPilot v0.1.57 or later.
- Workaround: Immediately set a strong, unique `JWT_SECRET` environment variable in all deployments; rotate any existing tokens.
- Tradeoff: Setting a secret requires redeployment; token rotation invalidates existing sessions.
