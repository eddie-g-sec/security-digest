# Security Digest — 2026-11-20

## Cloud Security

The most urgent item is **Dokploy CVE-2026-129316 (CVSS 9.9, CRITICAL)**, an authorization-binding flaw in Dokploy 0.29.13 through 0.31.0 that can let a low-privileged member reach unrelated containers, obtain a root shell in the Dokploy panel container, read other tenants’ logs and statistics, and potentially compromise the host through the mounted Docker socket; upgrade to Dokploy 0.31.0 immediately. No CISA KEV-confirmed entries are present in the supplied data, so this item is prioritized by confirmed critical severity and direct host-compromise impact over other high-severity findings.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-129509 (CVSS 7.5 HIGH)
**Summary:** In Apache Airflow Microsoft Azure provider 10.2.0 through 15.3.0, `S3ToAzureBlobStorageOperator` turned off TLS certificate verification for its connection to Amazon S3 by default (`s3_verify=False`), regardless of the AWS connection’s own verification settings. An attacker positioned on the network between an Airflow worker and S3 could intercept traffic, read signed requests, and alter listed object keys or copied file contents; affected deployments use the operator without setting `s3_verify`.

**Affected Features / Interoperability:** Apache Airflow Microsoft Azure provider and S3-to-Azure Blob copy workflows; downstream data pipelines that copy objects from AWS S3 into Azure Blob Storage could be exposed to interception or tampering. The raw data does not specify other affected integrations.

**Source:** https://github.com/apache/airflow/pull/76222, https://lists.apache.org/thread/z6o61d0h81o1f9bgdrn4d9jl24o7shmh, http://www.openwall.com/lists/oss-security/2026/11/17/30

**Actions:**
- Fix: Upgrade Apache Airflow to a patched release; the supplied advisory text truncates the exact fixed version.
- Workaround: Set `s3_verify=True` for the AWS connection used by the operator, or avoid `S3ToAzureBlobStorageOperator` until patched.
- Tradeoff: Enforcing certificate verification can break S3 access if certificates or CA trust are misconfigured.

#### Kubernetes — CVE-2026-85594 (CVSS 9.8 CRITICAL)
**Summary:** Traefik v3.7.1 fails to enforce `crossProviderNamespaces` restrictions on the `traefik.ingress.kubernetes.io/service.middlewares` Service annotation in the Kubernetes Ingress provider. A namespace-limited tenant excluded from the allowlist can attach an operator-owned middleware to its Service, and if that middleware injects backend credentials, recover them at a controlled backend.

**Affected Features / Interoperability:** Traefik Kubernetes Ingress provider, cross-namespace middleware references, and Service middleware annotations; multi-tenant ingress isolation and middleware chains that inject credentials could be bypassed or broken.

**Source:** https://github.com/traefik/traefik/security/advisories/GHSA-m6wx-622r-48r9, https://www.vulncheck.com/advisories/traefik-3.7.1-crossprovidernamespaces-bypass-via-service-middleware

**Actions:**
- Fix: Apply the Traefik security update referenced by the advisory; the supplied data does not state the exact fixed version.
- Workaround: Restrict tenant ability to create or modify Services/Ingress objects with middleware annotations, and enforce namespace allowlists through admission policy.
- Tradeoff: May block legitimate cross-namespace middleware reuse or require additional policy maintenance.

#### Kubernetes — CVE-2026-85596 (CVSS 9.8 CRITICAL)
**Summary:** Traefik versions >= v3.7.0 and < v3.7.11 contain an authentication bypass in the Kubernetes Ingress NGINX provider. The TLS option generated for an Ingress carrying `nginx.ingress.kubernetes.io/auth-tls-secret` was named after the Ingress namespace and name, so two Ingress objects sharing the same host, client CA secret, and client-authentication mode could produce a TLS options conflict and fall back to the entry point’s default TLS configuration, which does not request a client certificate.

**Affected Features / Interoperability:** Traefik Kubernetes Ingress NGINX provider, TLS option generation, and client-certificate authentication; downstream services relying on mutual TLS or client-certificate validation could be exposed to authentication bypass.

**Source:** https://github.com/traefik/traefik/security/advisories/GHSA-j994-9gqj-9hwq, https://www.vulncheck.com/advisories/traefik-3.7-authentication-bypass-via-tls-option-conflict

**Actions:**
- Fix: Upgrade to Traefik 3.7.11 or later; the affected range ends before 3.7.11.
- Workaround: Avoid multiple Ingress objects sharing the same host, client CA secret, and client-authentication mode; consolidate them or enforce unique hostnames.
- Tradeoff: May require ingress redesign or cause routing/configuration changes.

#### Kubernetes — CVE-2026-88877 (CVSS 9.8 CRITICAL)
**Summary:** Traefik versions >= v3.7.0 and <= v3.7.11 mishandle Ingresses that carry both an authentication annotation and `nginx.ingress.kubernetes.io/from-to-www-redirect`. For such Ingresses, Traefik creates an additional sibling router matching on the host alone, carrying only the RedirectRegex middleware and still pointing at the parent router’s protected backend; because RedirectRegex is not a terminal handler, requests not matching the redirect pattern can be forwarded to the backend and bypass authentication.

**Affected Features / Interoperability:** Traefik Kubernetes ingress-nginx provider, authentication annotations, `from-to-www-redirect`, and routing behavior; downstream protected backend services could be reachable without the intended authentication.

**Source:** https://github.com/traefik/traefik/security/advisories/GHSA-cjr6-pf59-jq29, https://www.vulncheck.com/advisories/traefik-3.7.0-authentication-bypass-via-from-to-www-redirect

**Actions:**
- Fix: Upgrade to a Traefik release later than 3.7.11; the exact fixed version is not stated in the supplied data.
- Workaround: Remove `nginx.ingress.kubernetes.io/from-to-www-redirect` from authenticated Ingresses or handle redirects outside Traefik.
- Tradeoff: May break www-to-non-www redirect behavior or require external redirect handling.

#### Kubernetes — CVE-2026-66297 (CVSS 8.0 HIGH)
**Summary:** Livebook allows command injection into generated deployment setup commands. `LivebookWeb.Hub.Teams.DeploymentGroupAgentComponent.docker_instructions/2` and `fly_instructions/4` interpolate deployment group environment variable values into generated Docker and Fly.io setup commands without shell escaping; an attacker able to control those values can inject operating-system commands.

**Affected Features / Interoperability:** Livebook Teams deployment group agent Docker and Fly.io setup instructions; downstream deployment automation and host command execution could be impacted. The raw data does not specify the exact privilege required beyond control of deployment group configuration values.

**Source:** https://cna.erlef.org/cves/CVE-2026-66297.html, https://github.com/livebook-dev/livebook/commit/0c2487326bbb37cb1eb43bb2f76eb93ad9f8fd6b, https://github.com/livebook-dev/livebook/commit/7cf4af5c10ec645f55a10f30e5661c54f6a6b319

**Actions:**
- Fix: Apply the referenced Livebook commits or upgrade to a release containing them; the exact release is not stated in the supplied data.
- Workaround: Restrict who can edit deployment group environment variables and avoid using untrusted values in Docker or Fly.io setup commands.
- Tradeoff: May limit deployment configuration flexibility.

#### Kubernetes — CVE-2026-132239 (CVSS 7.6 HIGH)
**Summary:** In JetBrains TeamCity before 2026.1.3 and 2025.11.7, missing authorization in the Kubernetes integration allowed project viewers to use stored credentials. Authenticated project viewers could access or use Kubernetes credentials beyond their intended permissions.

**Affected Features / Interoperability:** TeamCity Kubernetes integration, stored credentials, and project-level authorization; downstream Kubernetes cluster access could be exposed to unauthorized project viewers.

**Source:** https://www.jetbrains.com/privacy-security/issues-fixed/

**Actions:**
- Fix: Upgrade to TeamCity 2026.1.3 or 2025.11.7.
- Workaround: Remove or restrict Kubernetes integration credentials in projects accessible to viewers, and tighten project permissions.
- Tradeoff: May prevent legitimate viewers from using Kubernetes integration features.
