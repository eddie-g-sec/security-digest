# Security Digest — 2026-11-01

## Cloud Security

The most urgent item today is CVE-2026-120306, a critical container escape vulnerability (CVSS 9.9) in the Beta9 build worker that affects both Kubernetes and Docker environments. It allows a tenant to break out of the build container and access the host filesystem, risking full infrastructure compromise. While no CISA KEV-confirmed entries are present this cycle, the severity and attack surface warrant immediate attention.

### Formal Vulnerabilities

#### Kubernetes — CVE-2026-120306 (CVSS 9.9 CRITICAL)
**Summary:** Beta9 turns tenant shell commands into Dockerfile RUN lines executed by Buildah on a shared build worker. Because the worker runs with `BUILDAH_ISOLATION=chroot` but without `--isolation`, the step only changes its filesystem root while retaining the worker’s PID, network, IPC, and user namespaces. Running as uid 0 with `CAP_DAC_OVERRIDE`, it can access the writable host filesystem via `/proc/1/root`, which contains the binaries used to start tenant containers. No authentication is required beyond the ability to submit a build job.

**Affected Features / Interoperability:** The vulnerability directly impacts the container build pipeline. Any tenant image definition can trigger it, compromising the build worker itself. Downstream, this undermines the isolation of all co-tenanted workloads and could affect orchestration controls, networking policies, and any security mechanisms that rely on the worker’s namespace boundaries.

#### Kubernetes — CVE-2026-120307 (CVSS 9.9 CRITICAL)
**Summary:** The Beta9 worker’s sandbox file API, which translates tenant container paths to worker paths, contains a path traversal flaw. By crafting a path that starts with a mount destination (e.g., `/tmp/.beta9`) followed by enough `../` sequences, an attacker can reference any absolute path on the worker host. If the path does not match a mount, it is opened in the worker’s own filesystem, enabling host file access. No authentication is required beyond the ability to call the file API.

**Affected Features / Interoperability:** The sandbox file API is the affected component. This flaw could allow a tenant to read or write arbitrary files on the worker, potentially exposing or modifying other tenants’ data, configuration, or secrets. It may also break the integrity of any shared storage or volume mounts that the worker manages.

#### Docker — CVE-2026-120203 (CVSS 8.8 HIGH)
**Summary:** ShowDoc versions before 3.9.6 contain a code injection vulnerability in its Mock feature. Authenticated users can store a mockjs template with escaped parentheses via `MockController::add`, then trigger it through `MockController::infoByKey` to execute shell commands with `eval()`. Because the official Docker image runs as root, this leads to remote code execution with elevated privileges.

**Affected Features / Interoperability:** The Mock feature and the underlying mockjs template engine are the affected components. Exploitation could allow an authenticated user to execute arbitrary commands on the host, potentially leading to full application compromise, data exfiltration, or lateral movement within the container network. Any integrations that rely on the Mock feature for API simulation or testing may be disrupted.

**Source:**  
- https://gist.github.com/LioTree/028af150fd991cf9924dd2c7d5912e54  
- https://github.com/star7th/showdoc  
- https://github.com/star7th/showdoc/blob/v3.9.5/mock/index.js#L42  

**Actions:**  
- Fix: Upgrade to ShowDoc 3.9.6 or later.  
- Workaround: Restrict access to the Mock feature to trusted users, and disable it if not actively needed.  
- Tradeoff: Disabling the Mock feature may break workflows that rely on automated API mocking or testing.
