# Security Digest — 2026-11-06

## Cloud Security

The most urgent issue this cycle is **CVE-2026-57566 (CVSS 9.3 CRITICAL) in Readest (Docker)**, an unauthenticated server-side request forgery in the OPDS proxy route that lets attackers fetch arbitrary URLs, follow redirects to internal metadata endpoints, and achieve remote code execution in default Docker deployments. No CISA KEV-confirmed vulnerabilities appear in today’s data, so the highest theoretical severity drives priority. Kubernetes also carries a cluster of high-severity authorization bypasses and credential leaks (CVE-2026-103002, CVE-2026-119572, CVE-2026-119115) that could compromise multi-tenant clusters, while Terraform tooling in JetBrains IDEs introduces code-execution risks in untrusted projects.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-112337 (CVSS 3.7 LOW)
**Summary:** Wazuh versions 3.7.0 through 4.14.8 contain a server-side request forgery in the Azure wodle’s `get_graph_events()` function. The code follows `@odata.nextLink` pagination URLs without validating the host or enforcing HTTPS, allowing an attacker who can influence the `nextLink` value to redirect the Wazuh manager’s requests to an attacker-controlled endpoint. This captures the reused Microsoft Graph bearer token and can reach internal services.

**Affected Features / Interoperability:** The Azure wodle (workload) component that pulls events from Microsoft Graph; impacts token reuse and potential access to internal network services reachable from the manager.

**Source:** https://github.com/wazuh/wazuh/releases/tag/v4.14.9, https://github.com/wazuh/wazuh/security/advisories/GHSA-qxg8-jrjm-w96h, https://www.vulncheck.com/advisories/wazuh-3.7.0-before-4.14.9-ssrf-via-azure-graph-nextlink-pagination

**Actions:**
- Fix: Upgrade Wazuh to version 4.14.9 or later.
- Workaround: No workaround specified in advisory.
- Tradeoff: No significant tradeoff.

#### Kubernetes — CVE-2026-103002 (CVSS 8.8 HIGH)
**Summary:** GPUStack versions 2.2.0 through 2.2.2 have an authorization bypass in the `cluster_apiserver_proxy`. An authenticated non-administrator can forward requests to a selected Kubernetes cluster using a reachable worker’s ServiceAccount credentials, without resource-level authorization checks. This allows reading sensitive resources, creating/modifying workloads, or deleting resources per that ServiceAccount’s permissions. Exploitation requires a Kubernetes-provider cluster with a reachable worker.

**Affected Features / Interoperability:** GPUStack’s cluster API server proxy; impacts any Kubernetes resources accessible via the worker’s ServiceAccount (workloads, secrets, RBAC).

**Source:** https://github.com/gpustack/gpustack/commit/363191fa1da7e1426c6041f78b3cf00aff2622fe, https://github.com/gpustack/gpustack/commit/cdd67467e0f314609dc82216e142940d321abfed, https://github.com/gpustack/gpustack/pull/5911

**Actions:**
- Fix: Upgrade GPUStack to version 2.2.3 or later (commit 363191fa1da7e1426c6041f78b3cf00aff2622fe).
- Workaround: No workaround specified in advisory.
- Tradeoff: No significant tradeoff.

#### Kubernetes — CVE-2026-119572 (CVSS 8.7 HIGH)
**Summary:** Traefik versions 3.7.0-ea.1 through 3.7.14 have an authentication bypass in the Kubernetes Ingress NGINX provider. When an Ingress declares a path on the same host without matching `auth-tls-secret` settings, Traefik silently disables mTLS and falls back to default TLS options, allowing unauthenticated attackers to reach backends that require client certificates.

**Affected Features / Interoperability:** Traefik’s Kubernetes Ingress NGINX provider mTLS enforcement via `auth-tls-secret` annotation; impacts any backend services relying on mutual TLS for authentication.

**Source:** https://github.com/traefik/traefik/security/advisories/GHSA-p8wx-ph99-xgcr, https://www.vulncheck.com/advisories/traefik-3.7.0-ea.1-before-3.7.15-mtls-bypass-via-ingress-nginx-provider

**Actions:**
- Fix: Upgrade Traefik to version 3.7.15 or later.
- Workaround: Ensure all Ingresses on a given host declare consistent `auth-tls-secret` annotations; avoid mixing mTLS and non-mTLS paths on the same host.
- Tradeoff: May require coordination across teams managing different Ingresses on shared hosts.

#### Kubernetes — CVE-2026-119115 (CVSS 8.5 HIGH)
**Summary:** AWS Private CA Connector for Kubernetes (aws-privateca-issuer) before v1.10.1 has incorrect authorization in issuer resolution logic. An authenticated remote user can obtain certificates (including subordinate CA certificates) signed by a cluster-scoped AWS Private CA issuer that their approval policy does not authorize.

**Affected Features / Interoperability:** Certificate issuance via `aws-privateca-issuer`; impacts PKI trust within the cluster and any workloads relying on issued certificates for authentication.

**Source:** https://aws.amazon.com/security/security-bulletins/2026-156-aws/, https://github.com/cert-manager/aws-privateca-issuer/releases/tag/v1.10.1, https://github.com/cert-manager/aws-privateca-issuer/security/advisories/GHSA-hjrh-q6pg-mh82

**Actions:**
- Fix: Upgrade `aws-privateca-issuer` to v1.10.1 or the EKS add-on to v1.10.1-eksbuild.1; update any CertificateRequest, Certificate, or Ingress annotations referencing the old issuer.
- Workaround: No workaround specified in advisory.
- Tradeoff: No significant tradeoff.

#### Kubernetes — CVE-2026-123047 (CVSS 7.5 HIGH)
**Summary:** Eclipse BaSyx Helm Charts `basyx` chart versions 3.0.0-rc.1 through 3.12.1 store Keycloak user passwords in cleartext in a Kubernetes ConfigMap when the bundled Keycloak is enabled. The bootstrap administrator user (with `admin` role and a non-temporary password) is included by default. Any principal with read access to the ConfigMap can obtain these credentials.

**Affected Features / Interoperability:** Helm chart’s Keycloak initialization ConfigMap (`<release>-basyx-keycloak-init-config`); impacts Keycloak admin access and any downstream services using those credentials.

**Source:** https://github.com/eclipse-basyx/charts/pull/106, https://github.com/eclipse-basyx/charts/releases/tag/basyx-3.12.2, https://github.com/eclipse-basyx/charts/security/advisories/GHSA-6438-759f-6f8v

**Actions:**
- Fix: Upgrade the `basyx` chart to version 3.12.2 or later.
- Workaround: Restrict read access to the ConfigMap via Kubernetes RBAC; rotate Keycloak passwords after upgrade.
- Tradeoff: Restricting ConfigMap access may break legitimate tooling that reads initialization data.

#### Kubernetes — CVE-2026-123059 (CVSS 7.5 HIGH)
**Summary:** Eclipse BaSyx Helm Charts `aas-basyx-v2-full` chart version 2.2.0 stores the `basyx-technical-user` OAuth2 client secret in cleartext in a Kubernetes ConfigMap (via Keycloak realm-import JSON) despite also writing it to a Secret. The client uses client-credentials grant and holds the realm `admin` role.

**Affected Features / Interoperability:** Helm chart’s Keycloak realm-import ConfigMap (`<keycloak.fullnameOverride>-realm-import`); impacts OAuth2 client credentials and admin-level access to Keycloak.

**Source:** https://github.com/eclipse-basyx/charts/pull/46, https://github.com/eclipse-basyx/charts/releases/tag/aas-basyx-v2-full-2.2.0, https://github.com/eclipse-basyx/charts/security/advisories/GHSA-6438-759f-6f8v

**Actions:**
- Fix: Upgrade the `aas-basyx-v2-full` chart to a version that removes the secret from the ConfigMap (check project releases).
- Workaround: Restrict read access to the ConfigMap via RBAC; rotate the client secret in Keycloak.
- Tradeoff: Restricting ConfigMap access may break realm-import automation.

#### Kubernetes — CVE-2026-88982 (CVSS 5.4 MEDIUM)
**Summary:** Kubeflow Pipelines before 2.18.0 has a cache isolation flaw in the legacy V1/raw-Argo execution cache. The cache mutating webhook and cache-server storage path hash use only the pipeline key without the Kubernetes namespace, and trust the mutable `pipelines.kubeflow.org/execution_cache_key` annotation. In multi-user deployments sharing a cache service, a tenant with workload-submission privileges can read another namespace’s cached outputs or seed matching cache entries.

**Affected Features / Interoperability:** Kubeflow Pipelines V1 execution cache; impacts multi-tenant data isolation and cache integrity.

**Source:** https://github.com/kubeflow/pipelines/commit/620d0cc89ae0d042a484a003f8ffe6e9a55d347e, https://github.com/kubeflow/pipelines/pull/14359, https://github.com/kubeflow/pipelines/releases/tag/2.18.0

**Actions:**
- Fix: Upgrade Kubeflow Pipelines to 2.18.0 or later.
- Workaround: Disable the legacy V1 cache or isolate cache services per namespace.
- Tradeoff: Disabling V1 cache may break existing pipelines relying on that execution path.

#### Kubernetes — CVE-2026-116472 (CVSS 2.7 LOW)
**Summary:** Ingress-nginx allows a user with permission to create an Ingress to cause denial of service of the ingress-nginx data plane or possibly redirect traffic from other Ingresses. The `mirror-target` annotation can target an unauthenticated configuration API within the controller, allowing write commands that corrupt the configuration and drop all traffic through ingress-nginx.

**Affected Features / Interoperability:** Ingress-nginx controller’s configuration API; impacts all ingress traffic in the cluster.

**Source:** https://github.com/kubernetes/kubernetes/issues/143852, http://www.openwall.com/lists/oss-security/2026/11/05/4

**Actions:**
- Fix: Upgrade ingress-nginx to a version that validates `mirror-target` annotations (check project releases).
- Workaround: Restrict Ingress creation permissions via RBAC; monitor for anomalous `mirror-target` usage.
- Tradeoff: Restricting Ingress creation may hinder developer self-service.

#### Docker — CVE-2026-57566 (CVSS 9.3 CRITICAL)
**Summary:** Readest before 0.11.10 has an unauthenticated SSRF in the `/api/opds/proxy` route. The route accepts an attacker-controlled URL, fetches it server-side without scheme restrictions, blocks private/loopback/link-local/metadata hosts, or revalidates destinations during redirects. It also accepts caller-controlled outbound headers and Authorization values and reflects upstream responses. A remote attacker can access internal metadata services, achieve RCE, and exfiltrate data.

**Affected Features / Interoperability:** Readest’s OPDS proxy API endpoint; impacts any Docker deployment exposing this route (default configuration exposes HTTP mode on 0.0.0.0:3000).

**Source:** https://github.com/readest/readest/commit/495783d04516d05b2eb10f8f8bad297d436b36de, https://github.com/readest/readest/pull/4638, https://github.com/readest/readest/releases/tag/v0.11.10

**Actions:**
- Fix: Upgrade Readest to v0.11.10 or later.
- Workaround: Block external access to the `/api/opds/proxy` endpoint via network policy or reverse proxy; disable the OPDS proxy feature if not needed.
- Tradeoff: Blocking the endpoint breaks legitimate OPDS federation functionality.

#### Docker — CVE-2026-57853 (CVSS 8.8 HIGH)
**Summary:** DataGerry before 3.3.0 has a server-side template injection (SSTI) in the DocAPI template rendering. Authenticated attackers with `base.docapi.template.add` permission can store arbitrary Jinja2 payloads via `POST /rest/docapi/template`, which are rendered in a non-sandboxed Jinja2 environment on `GET /rest/docapi/template/<id>/render/<object_id>`. This allows OS command execution as the DataGerry web process user (root in default Docker deployments).

**Affected Features / Interoperability:** DataGerry DocAPI template management and rendering; impacts host OS in Docker deployments running as root.

**Source:** https://docs.datagerry.com/en/latest/reference/changelog.html, https://github.com/DataGerry/DataGerry/releases/tag/3.3.0, https://www.vulncheck.com/advisories/datagerry-ssti-via-docapi-template-rendering

**Actions:**
- Fix: Upgrade DataGerry to 3.3.0 or later.
- Workaround: Remove `base.docapi.template.add` permission from untrusted users; run DataGerry container as non-root user.
- Tradeoff: Removing permission limits template creation; non-root may break file-system-dependent features.

#### Docker — CVE-2025-38369 (CVSS 7.8 HIGH)
**Summary:** In the Linux kernel, the IDXD DMA engine driver does not check workqueue availability before use when the parent process of a container with `/dev` mounted terminates. Docker may not properly propagate the mount replica back to the original mount point, causing a call trace or kernel panic when the user driver detaches and destroys the workqueue.

**Affected Features / Interoperability:** Linux kernel IDXD driver (`dmaengine: idxd`); impacts containers using IDXD workloads with `/dev` directory mounted.

**Source:** https://git.kernel.org/stable/c/17502e7d7b7113346296f6758324798d536c31fd, https://git.kernel.org/stable/c/98fd66c8ba77e3a7137575f610271014bc0e701f, https://git.kernel.org/stable/c/aee7a7439f8c0884da87694a401930204a57128f

**Actions:**
- Fix: Apply kernel patches from stable branches (commits listed).
- Workaround: Avoid mounting `/dev` into containers running IDXD workloads; use device-specific mounts instead.
- Tradeoff: Device-specific mounts reduce container flexibility for hardware access.

#### Docker — CVE-2026-63655 (CVSS 7.5 HIGH)
**Summary:** tsParticles before 4.3.1 has a denial-of-service in the HTTP mode of `@tsparticles/mcp-server`. The server accepts unauthenticated `POST /mcp` requests and accumulates request-body chunks in a `Buffer[]` without a cumulative size limit before `Buffer.concat` and `JSON.parse`. A remote attacker can stream an arbitrarily large body to exhaust Node.js process memory and terminate the service. The official Docker configuration exposes HTTP mode on 0.0.0.0:3000.

**Affected Features / Interoperability:** tsParticles MCP server HTTP endpoint; impacts availability of the particle animation service in Docker deployments.

**Source:** https://github.com/tsparticles/tsparticles/commit/25fb70e7f527a91568adaef576570289083f243b, https://github.com/tsparticles/tsparticles/commit/7b3a9488d4201fe9ddd5fec05f4a2ae65d3627ea, https://github.com/tsparticles/tsparticles/pull/5875

**Actions:**
- Fix: Upgrade tsParticles to 4.3.1 or later.
- Workaround: Implement a reverse proxy with request body size limits; disable HTTP mode if not needed.
- Tradeoff: Body size limits may break legitimate large payloads.
