# Security Digest — 2026-10-22

## Cloud Security

The most urgent issue is a critical privilege escalation in Azure Kubernetes Service (CVE-2026-50516, CVSS 9.4) that allows an authorized network attacker to elevate privileges, demanding immediate patching. This is followed by a cluster of high-severity Kubernetes-related vulnerabilities affecting Traefik ingress controllers, Argo CD, and Ansible Operators, all of which could lead to authentication bypass or remote code execution within containerized environments. Organizations running self-hosted Docker deployments should also prioritize addressing a hardcoded secret vulnerability in Trigger.dev that enables unauthenticated login bypass.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-50516 (CVSS 9.4 CRITICAL)
**Summary:** An authorized attacker can elevate privileges over a network in Azure Kubernetes Service (AKS). Exploitation requires existing authorization but no user interaction, making it remotely exploitable within the cluster's network boundary.

**Affected Features / Interoperability:** Impacts Azure Kubernetes Service (AKS) clusters. Could affect cluster node access, pod-level permissions, and any workloads relying on AKS-managed identities or role-based access control (RBAC).

**Source:** [https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516)

**Actions:**
- Fix: Apply the latest AKS security patch as specified in the Microsoft Security Response Center advisory.
- Workaround: Restrict network access to AKS API server endpoints and enforce strict RBAC policies until patched.
- Tradeoff: Network restrictions may limit administrative access or automation workflows dependent on AKS APIs.

#### Kubernetes — CVE-2026-113709 (CVSS 9.9 CRITICAL)
**Summary:** Argo CD versions from 2.1.0 up to 3.3.15, 3.4.10, 3.5.4, and 3.6.0-rc2 contain a vulnerability where enabling `--enable-helm` for kustomize build allows Helm to load a downloader plugin from a repository-controlled path. This leads to arbitrary code execution inside the `argocd-repo-server` pod when processing a malicious Helm chart.

**Affected Features / Interoperability:** Affects Argo CD deployments using Helm charts via kustomize. Impacts GitOps pipelines, CI/CD workflows, and any service relying on Argo CD for declarative deployment management.

**Source:** 
- [https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts](https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts)
- [https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c](https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c)
- [https://github.com/argoproj/argo-cd/releases/tag/v3.3.15](https://github.com/argoproj/argo-cd/releases/tag/v3.3.15)
- [https://github.com/argoproj/argo-cd/releases/tag/v3.4.10](https://github.com/argoproj/argo-cd/releases/tag/v3.4.10)

**Actions:**
- Fix: Upgrade to Argo CD v3.3.15, v3.4.10, v3.5.4, or later.
- Workaround: Disable `--enable-helm` for kustomize builds if not strictly required.
- Tradeoff: Disabling Helm support may break existing GitOps workflows dependent on Helm-based deployments.

#### Kubernetes — CVE-2026-114636 (CVSS 8.7 HIGH)
**Summary:** Traefik v3.7.13 before v3.7.14 contains an access-control bypass in the Kubernetes Ingress NGINX provider. SSL passthrough ingresses on non-TLS entry points fail to apply access-control annotations, allowing unauthenticated attackers to reach protected backends.

**Affected Features / Interoperability:** Impacts Traefik ingress controllers configured with NGINX-style ingress annotations. Affects routing rules, authentication middleware, and backend service exposure through Kubernetes ingress resources.

**Source:**
- [https://github.com/traefik/traefik/security/advisories/GHSA-qvj7-gq9c-hp7q](https://github.com/traefik/traefik/security/advisories/GHSA-qvj7-gq9c-hp7q)
- [https://www.vulncheck.com/advisories/traefik-3.7.13-authentication-bypass-via-ssl-passthrough-ingress-http-router](https://www.vulncheck.com/advisories/traefik-3.7.13-authentication-bypass-via-ssl-passthrough-ingress-http-router)

**Actions:**
- Fix: Upgrade to Traefik v3.7.14 or later.
- Workaround: Avoid using ssl-passthrough ingresses on non-TLS entry points; enforce TLS termination at the edge.
- Tradeoff: May require reconfiguration of ingress routing and TLS handling, potentially impacting service availability during transition.

#### Kubernetes — CVE-2026-114638 (CVSS 8.7 HIGH)
**Summary:** Traefik v3.7.0 before v3.7.14 improperly merges client certificate authorities (CAs) when `auth-tls-secret` names collide after dot-to-dash normalization. Attackers with certificates from one host’s CA can authenticate to another host requiring a different CA.

**Affected Features / Interoperability:** Affects mutual TLS (mTLS) configurations in Traefik ingress controllers. Impacts secure communication between services and external clients relying on certificate-based authentication.

**Source:**
- [https://github.com/traefik/traefik/security/advisories/GHSA-rv2h-qh7j-xrjw](https://github.com/traefik/traefik/security/advisories/GHSA-rv2h-qh7j-xrjw)
- [https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-client-ca-mix-up-via-auth-tls-secret-name-collision](https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-client-ca-mix-up-via-auth-tls-secret-name-collision)

**Actions:**
- Fix: Upgrade to Traefik v3.7.14 or later.
- Workaround: Ensure unique naming for `auth-tls-secret` across hosts to prevent collisions.
- Tradeoff: Renaming secrets may disrupt existing mTLS configurations and require updates to dependent services.

#### Kubernetes — CVE-2026-114640 (CVSS 8.7 HIGH)
**Summary:** Traefik v3.7.0 before v3.7.14 forwards client-supplied `Ssl-Client-*` headers on the plaintext HTTP router. With ssl-redirect disabled and `auth-tls-pass-certificate-to-upstream` enabled, unauthenticated attackers can spoof mTLS identities by sending forged headers.

**Affected Features / Interoperability:** Impacts Traefik ingress controllers using mTLS passthrough and HTTP routers. Affects backend services expecting trusted client identity headers.

**Source:**
- [https://github.com/traefik/traefik/security/advisories/GHSA-mwrr-6hp4-pxr6](https://github.com/traefik/traefik/security/advisories/GHSA-mwrr-6hp4-pxr6)
- [https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-mtls-header-spoofing-via-ingress-nginx-http-router](https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-mtls-header-spoofing-via-ingress-nginx-http-router)

**Actions:**
- Fix: Upgrade to Traefik v3.7.14 or later.
- Workaround: Disable `auth-tls-pass-certificate-to-upstream` and ensure ssl-redirect is enabled.
- Tradeoff: Disabling header forwarding may break backend logic dependent on client certificate information.

#### Kubernetes — CVE-2026-92982 (CVSS 8.5 HIGH)
**Summary:** Ansible Operator Plugins contain a Jinja2 template injection flaw. A low-privileged Kubernetes user can inject malicious Jinja2 expressions via custom resource specifications, leading to arbitrary code execution within the operator pod and potential privilege escalation.

**Affected Features / Interoperability:** Affects Kubernetes operators built using Ansible Operator SDK. Impacts custom controllers managing application lifecycles, especially those accepting user-defined CRs.

**Source:**
- [https://access.redhat.com/errata/RHSA-2026:87120](https://access.redhat.com/errata/RHSA-2026:87120)
- [https://access.redhat.com/errata/RHSA-2026:87124](https://access.redhat.com/errata/RHSA-2026:87124)
- [https://access.redhat.com/security/cve/CVE-2026-92982](https://access.redhat.com/security/cve/CVE-2026-92982)
- [https://bugzilla.redhat.com/show_bug.cgi?id=2522227](https://bugzilla.redhat.com/show_bug.cgi?id=2522227)

**Actions:**
- Fix: Update Ansible Operator SDK to a patched version as per Red Hat advisory.
- Workaround: Sanitize all user inputs passed to Jinja2 templates and restrict CR creation permissions.
- Tradeoff: Input sanitization may reduce flexibility in defining custom resources.

#### Kubernetes — CVE-2026-105311 (CVSS 7.7 HIGH)
**Summary:** The StreamsHub Console operator acts as a confused deputy, allowing a tenant with `console` custom resource creation rights to read KafkaUser secrets from other namespaces and expose them in their own namespace.

**Affected Features / Interoperability:** Impacts StreamsHub Console operators managing Kafka clusters. Affects multi-tenant environments where namespace isolation is critical for credential protection.

**Source:**
- [https://access.redhat.com/security/cve/CVE-2026-105311](https://access.redhat.com/security/cve/CVE-2026-105311)
- [https://bugzilla.redhat.com/show_bug.cgi?id=2510875](https://bugzilla.redhat.com/show_bug.cgi?id=2510875)

**Actions:**
- Fix: Apply vendor-provided patches or upgrade to a fixed version of StreamsHub Console.
- Workaround: Enforce strict namespace-level RBAC and audit console custom resource definitions.
- Tradeoff: Tightening RBAC may complicate legitimate administrative operations.

**Affected Features / Interoperability:** Affects OpenChoreo developer platform instances. Impacts workflow orchestration and project-level access controls within Kubernetes-native development environments.

**Affected Features / Interoperability:** Impacts Red Hat OpenShift AI dashboards integrating with NVIDIA NIM services. Affects access to NGC API keys and image pull secrets used for AI model serving.

#### Kubernetes — CVE-2026-87354 (CVSS 4.3 MEDIUM)
**Summary:** Oracle TimesTen In-Memory Database Kubernetes Operator contains an easily exploitable vulnerability allowing a low-privileged attacker with network access to perform unauthorized reads of database content via HTTPS.

**Affected Features / Interoperability:** Affects Oracle TimesTen deployments managed via Kubernetes Operator. Impacts database query results and potentially sensitive in-memory data stores.

**Source:** [https://www.oracle.com/security-alerts/cpuoct2026.html](https://www.oracle.com/security-alerts/cpuoct2026.html)

**Actions:**
- Fix: Upgrade to Oracle TimesTen Operator version 22.1.40.1 or 26.1.1.3 or later.
- Workaround: Enforce network segmentation and limit operator API exposure to trusted networks.
- Tradeoff: Network segmentation may complicate remote administration and monitoring.

#### Docker — CVE-2026-114087 (CVSS 8.1 HIGH)
**Summary:** Trigger.dev versions before 4.5.6 use hardcoded default secrets in self-hosted Docker Compose deployments, enabling unauthenticated attackers to forge magic link tokens and gain access to backend services like Postgres, Redis, and ClickHouse.

**Affected Features / Interoperability:** Affects self-hosted Trigger.dev deployments using default configuration files. Impacts authentication flows, database connectivity, and internal service communications.

**Source:**
- [https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x](https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x)
- [https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets](https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets)

**Actions:**
- Fix: Upgrade to Trigger.dev v4.5.6 or later and regenerate all secrets.
- Workaround: Replace default secrets in `.env` files with strong, randomly generated values.
- Tradeoff: Regenerating secrets requires updating all connected services and may cause temporary downtime.

#### Docker — CVE-2026-76304 (CVSS 4.3 MEDIUM)
**Summary:** Splunk SOAR versions below 8.7.0 allow authenticated users without Automation Broker edit permissions to download the Docker Compose configuration file containing deployment URLs, image locations, and version details.

**Affected Features / Interoperability:** Affects Splunk SOAR Automation Broker deployments. Impacts visibility into internal infrastructure and potential reconnaissance for further attacks.

**Source:** [https://advisory.splunk.com/advisories/SVD-2026-1010](https://advisory.splunk.com/advisories/SVD-2026-1010)

**Actions:**
- Fix: Upgrade to Splunk SOAR 8.7.0 or later.
- Workaround: Audit user roles and remove unnecessary access to Automation Broker settings.
- Tradeoff: Restricting access may delay troubleshooting and maintenance tasks.
