# Security Digest — 2026-10-22

## Cloud Security

The most urgent item is **CVE-2026-50516** in Microsoft Azure Kubernetes Service, a CVSS 9.4 CRITICAL incorrect authorization flaw that allows an authorized attacker to elevate privileges over a network. While not currently flagged as CISA KEV-confirmed, its criticality and direct impact on AKS privilege boundaries make it the top priority for immediate remediation.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-50516 (CVSS 9.4 CRITICAL)
**Summary:** An incorrect authorization vulnerability in Azure Kubernetes Service allows an authorized attacker to elevate privileges over a network. No authentication bypass is required, but the attacker must already have some level of authorized access within the AKS environment.

**Affected Features / Interoperability:** Impacts Azure Kubernetes Service (AKS) authorization mechanisms. Could affect role-based access control (RBAC), namespace isolation, and cluster-wide privilege boundaries. Downstream impacts may include unauthorized access to cluster resources, workloads, and potentially connected Azure services via managed identities.

**Source:** [https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516)

**Actions:**
- **Fix:** Apply the latest AKS security patch as specified in the Microsoft Security Response Center advisory.
- **Workaround:** Restrict network access to AKS API server and enforce stricter RBAC policies until patching is complete.
- **Tradeoff:** Network restrictions may impact legitimate administrative access and automation workflows.

#### Kubernetes — CVE-2026-113709 (CVSS 9.9 CRITICAL)
**Summary:** A critical vulnerability in Argo CD affects versions from 2.1.0 up to 3.3.15, 3.4.10, 3.5.4, and 3.6.0-rc2. When `--enable-helm` is enabled for kustomize build, an attacker can manipulate `helmGlobals.configHome` to point Helm's config and data directories at a repository-controlled location. This allows automatic loading and execution of a malicious downloader plugin inside the argocd-repo-server, leading to arbitrary code execution.

**Affected Features / Interoperability:** Impacts Argo CD deployments using Helm charts with kustomize builds. Affects the argocd-repo-server component, which processes Helm charts. Could lead to compromise of CI/CD pipelines, repository credentials, and downstream Kubernetes clusters managed by Argo CD.

**Source:** 
- [https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts](https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts)
- [https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c](https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c)
- [https://github.com/argoproj/argo-cd/releases/tag/v3.3.15](https://github.com/argoproj/argo-cd/releases/tag/v3.3.15)
- [https://github.com/argoproj/argo-cd/releases/tag/v3.4.10](https://github.com/argoproj/argo-cd/releases/tag/v3.4.10)

**Actions:**
- **Fix:** Upgrade Argo CD to v3.3.15, v3.4.10, or v3.5.4 depending on your version branch.
- **Workaround:** Disable `--enable-helm` for kustomize builds if not strictly required.
- **Tradeoff:** Disabling Helm support may break existing deployments relying on Helm-based configurations.

#### Kubernetes — CVE-2026-114636 (CVSS 8.7 HIGH)
**Summary:** Traefik versions from v3.7.0 before v3.7.14 contain an access-control bypass in the Kubernetes Ingress NGINX provider. SSL-passthrough Ingresses on non-TLS entry points fail to apply access-control annotations such as `auth-type`, `auth-url`, or `whitelist-source-range`. Unauthenticated attackers can access protected backends without detection.

**Affected Features / Interoperability:** Impacts Traefik ingress controllers configured with SSL passthrough and NGINX-style ingress annotations. Affects authentication and authorization layers for exposed services, potentially allowing unauthorized access to internal applications.

**Source:**
- [https://github.com/traefik/traefik/security/advisories/GHSA-qvj7-gq9c-hp7q](https://github.com/traefik/traefik/security/advisories/GHSA-qvj7-gq9c-hp7q)
- [https://www.vulncheck.com/advisories/traefik-3.7.13-authentication-bypass-via-ssl-passthrough-ingress-http-router](https://www.vulncheck.com/advisories/traefik-3.7.13-authentication-bypass-via-ssl-passthrough-ingress-http-router)

**Actions:**
- **Fix:** Upgrade Traefik to v3.7.14 or later.
- **Workaround:** Avoid using SSL passthrough on non-TLS entry points or enforce external authentication proxies.
- **Tradeoff:** Workarounds may require architectural changes and could impact service availability.

#### Kubernetes — CVE-2026-114638 (CVSS 8.7 HIGH)
**Summary:** Traefik versions from v3.7.0 before v3.7.14 have an improper authentication vulnerability in the Kubernetes Ingress NGINX provider. When `auth-tls-secret` names collide after dot-to-dash normalization, client CAs are merged incorrectly. Attackers with certificates from one host's CA can authenticate to another host requiring its own CA, while legitimate clients are rejected.

**Affected Features / Interoperability:** Affects mutual TLS (mTLS) authentication in Traefik ingress controllers. Impacts secure communication between clients and services protected by different CAs, potentially leading to unauthorized access and denial of service for legitimate users.

**Source:**
- [https://github.com/traefik/traefik/security/advisories/GHSA-rv2h-qh7j-xrjw](https://github.com/traefik/traefik/security/advisories/GHSA-rv2h-qh7j-xrjw)
- [https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-client-ca-mix-up-via-auth-tls-secret-name-collision](https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-client-ca-mix-up-via-auth-tls-secret-name-collision)

**Actions:**
- **Fix:** Upgrade Traefik to v3.7.14 or later.
- **Workaround:** Ensure unique naming for `auth-tls-secret` across hosts to prevent collisions.
- **Tradeoff:** Naming constraints may complicate certificate management at scale.

#### Kubernetes — CVE-2026-114640 (CVSS 8.7 HIGH)
**Summary:** Traefik versions from v3.7.0 before v3.7.14 forward client-supplied `Ssl-Client-*` headers on the plaintext HTTP router. When `ssl-redirect` is disabled and `auth-tls-pass-certificate-to-upstream` is enabled, unauthenticated attackers can spoof mTLS identities by sending forged headers like `Ssl-Client-Verify: SUCCESS`.

**Affected Features / Interoperability:** Impacts mTLS identity propagation in Traefik ingress controllers. Affects backend services relying on forwarded client certificate information for authorization decisions, potentially allowing impersonation of trusted clients.

**Source:**
- [https://github.com/traefik/traefik/security/advisories/GHSA-mwrr-6hp4-pxr6](https://github.com/traefik/traefik/security/advisories/GHSA-mwrr-6hp4-pxr6)
- [https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-mtls-header-spoofing-via-ingress-nginx-http-router](https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-mtls-header-spoofing-via-ingress-nginx-http-router)

**Actions:**
- **Fix:** Upgrade Traefik to v3.7.14 or later.
- **Workaround:** Disable `auth-tls-pass-certificate-to-upstream` or enable `ssl-redirect` to prevent header forwarding on HTTP.
- **Tradeoff:** Disabling features may break existing mTLS integrations or redirect handling.

**Summary:** A Jinja2 template injection vulnerability exists in Ansible Operator Plugins. A low-privileged Kubernetes user can craft malicious custom resource specifications that are processed by Ansible without sanitization, leading to arbitrary code execution within the operator pod and potential privilege escalation.

**Affected Features / Interoperability:** Affects Kubernetes operators built using Ansible Operator Plugins. Impacts custom resource validation and processing pipelines, potentially compromising operator service accounts with cluster-wide permissions.

#### Kubernetes — CVE-2026-105311 (CVSS 7.7 HIGH)
**Summary:** The StreamsHub Console operator acts as a confused deputy, allowing a Kubernetes tenant with permission to create Console custom resources to read Secrets from any namespace by setting `spec.kafkaClusters[].credentials.kafkaUser.namespace`. The operator, running with cluster-wide Secrets RBAC, copies sensitive credential material into the attacker's namespace.

**Affected Features / Interoperability:** Affects StreamsHub Console operator deployments. Impacts Kafka cluster credential management and cross-namespace Secret access, potentially exposing SASL credentials and TLS private keys.

**Source:**
- [https://access.redhat.com/security/cve/CVE-2026-105311](https://access.redhat.com/security/cve/CVE-2026-105311)
- [https://bugzilla.redhat.com/show_bug.cgi?id=2510875](https://bugzilla.redhat.com/show_bug.cgi?id=2510875)

**Actions:**
- **Fix:** Update StreamsHub Console operator to a patched version that enforces namespace scoping.
- **Workaround:** Restrict tenant permissions to create Console resources and audit existing custom resources.
- **Tradeoff:** Permission restrictions may limit operational flexibility for development teams.

#### Docker — CVE-2026-114087 (CVSS 8.1 HIGH)
**Summary:** Trigger.dev self-hosted Docker Compose deployments using default secrets from `hosting/docker/.env.example` allow authentication bypass. The hardcoded `MAGIC_LINK_SECRET` enables unauthenticated attackers to forge valid magic link tokens and log in as any email address, then access backend services with default credentials.

**Affected Features / Interoperability:** Affects Trigger.dev self-hosted deployments using default configuration. Impacts authentication, Postgres, Redis, and ClickHouse access, potentially compromising all tenant data.

**Source:**
- [https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x](https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x)
- [https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets](https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets)

**Actions:**
- **Fix:** Upgrade Trigger.dev to version 4.5.6 or later.
- **Workaround:** Replace all default secrets in `.env` files and regenerate `MAGIC_LINK_SECRET`.
- **Tradeoff:** Secret rotation requires updating all dependent services and may cause temporary session disruptions.
