# Security Digest — 2026-10-22

## Cloud Security

The most urgent formal issue is **CVE-2026-113709 in Argo CD**, a critical 9.9 vulnerability that can enable repository-controlled Helm plugin execution in `argocd-repo-server`, potentially exposing repository credentials and enabling further compromise. The Azure Kubernetes Service authorization flaw (**CVE-2026-50516**, CVSS 9.4) and the Traefik Ingress NGINX authentication-bypass issues are also critical priorities; no formal entry in this dataset is explicitly marked as CISA KEV-confirmed.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-50516 (CVSS 9.4 CRITICAL)
**Summary:** Incorrect authorization in Microsoft Azure Kubernetes Service allows an authorized attacker to elevate privileges over the network. The flaw requires an attacker to already possess some authorized access, but can be exploited over the network to increase privileges within AKS.

**Affected Features / Interoperability:** The affected component is Microsoft Azure Kubernetes Service authorization. The specific affected AKS control-plane or workload permissions, and any downstream cluster, workload, or secret-access implications, are not detailed in the supplied data.

**Source:**
- https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516

**Actions:**
- **Fix:** No patched release or version is specified in the supplied data; follow the Microsoft Security Response Center guidance for CVE-2026-50516.
- **Workaround:** Restrict access to affected AKS management and workload interfaces to trusted principals, and review Azure RBAC and Kubernetes authorization changes for suspicious privilege escalation activity.
- **Tradeoff:** Narrowing management-plane access may reduce administrative convenience and require more tightly controlled operational workflows.

#### Kubernetes — CVE-2026-113709 (CVSS 9.9 CRITICAL)
**Summary:** Argo CD versions 2.1.0 through 3.3.15, 3.4.10, 3.5.4, and 3.6.0-rc2 are affected when an operator has enabled `--enable-helm` for Kustomize builds. A repository-controlled `helmGlobals.configHome` can cause Helm to load and execute a downloader plugin inside `argocd-repo-server`; the command runs as the repo-server user and may read repository credentials.

**Affected Features / Interoperability:** The affected components are Argo CD’s Kustomize/Helm integration, Helm plugin loading, and the `argocd-repo-server` execution environment. Repository credentials and Argo CD GitOps deployment workflows may be exposed or compromised.

**Source:**
- https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts
- https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c
- https://github.com/argoproj/argo-cd/pull/6059
- https://github.com/argoproj/argo-cd/releases/tag/v3.3.15
- https://github.com/argoproj/argo-cd/releases/tag/v3.4.10

**Actions:**
- **Fix:** Upgrade to the listed fixed releases: Argo CD 3.3.15, 3.4.10, 3.5.4, or 3.6.0-rc2, as applicable.
- **Workaround:** Disable `--enable-helm` for Kustomize builds and review repository configuration for attacker-controlled `helmGlobals.configHome` values. Treat repository credentials and other secrets accessible to `argocd-repo-server` as potentially exposed and rotate them where appropriate.
- **Tradeoff:** Disabling Helm support for Kustomize reduces GitOps deployment flexibility and may require changing release or chart-management workflows.

**Summary:** Incorrect authorization in Microsoft Azure Kubernetes Service allows an authorized attacker to elevate privileges over the network. The vulnerability requires an authorized attacker but can be exploited remotely to obtain higher privileges.

**Affected Features / Interoperability:** The affected component is Microsoft Azure Kubernetes Service authorization. Specific affected AKS resources and downstream effects are not described in the supplied data.

**Source:**

#### Kubernetes — CVE-2026-114636 (CVSS 8.7 HIGH)
**Summary:** Traefik v3.7.13 before v3.7.14 contains an access-control bypass in the Kubernetes Ingress NGINX provider. For SSL-passthrough Ingresses on non-TLS entry points, the generated HTTP router does not apply access-control annotations, allowing unauthenticated attackers who reach the HTTP entry point and present the Ingress host to access protected backends without the expected logging.

**Affected Features / Interoperability:** Affected functionality is the Kubernetes Ingress NGINX provider’s handling of SSL-passthrough Ingress resources and generated HTTP routers. Backends protected by `auth-type`, `auth-url`, or `whitelist-source-range` annotations may be exposed through the plaintext HTTP entry point.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-qvj7-gq9c-hp7q
- https://www.vulncheck.com/advisories/traefik-3.7.13-authentication-bypass-via-ssl-passthrough-ingress-http-router

**Actions:**
- **Fix:** Upgrade Traefik to v3.7.14 or later.
- **Workaround:** Prevent direct access to the affected HTTP entry points, disable SSL-passthrough where practical, and enforce equivalent network-level access controls in front of protected backends.
- **Tradeoff:** Blocking or removing HTTP entry points may disrupt clients that rely on plaintext HTTP or alter intended ingress routing.

#### Kubernetes — CVE-2026-114638 (CVSS 8.7 HIGH)
**Summary:** Traefik v3.7.0 before v3.7.14 has an improper authentication flaw in the Kubernetes Ingress NGINX provider. When `auth-tls-secret` names collide after dot-to-dash normalization, client CAs can be merged, allowing attackers with certificates signed by another host’s CA to access a host requiring its own client CA while legitimate clients are rejected.

**Affected Features / Interoperability:** The affected component is the Kubernetes Ingress NGINX provider’s `auth-tls-secret` handling and client-CA trust configuration. Mutual-TLS enforcement, client-certificate authentication, and host-specific access decisions may be compromised for affected Ingress resources.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-rv2h-qh7j-xrjw
- https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-client-ca-mix-up-via-auth-tls-secret-name-collision

**Actions:**
- **Fix:** Upgrade Traefik to v3.7.14 or later.
- **Workaround:** Review `auth-tls-secret` names for normalization collisions, rename affected secrets where operationally possible, and verify that client-CA bundles contain only intended CAs.
- **Tradeoff:** Renaming or separating client-CA Secrets requires configuration changes and coordinated reloads of affected Ingress resources.

#### Kubernetes — CVE-2026-114640 (CVSS 8.7 HIGH)
**Summary:** Traefik v3.7.0 before v3.7.14 contains an authentication bypass in the Kubernetes Ingress-NGINX provider. When `ssl-redirect` is disabled and `auth-tls-pass-certificate-to-upstream` is enabled, client-supplied `Ssl-Client-*` headers are forwarded on the plaintext HTTP router, allowing unauthenticated attackers to spoof an mTLS identity by sending `Ssl-Client-Verify: SUCCESS` with a chosen subject and issuer.

**Affected Features / Interoperability:** The affected component is plaintext HTTP routing combined with `auth-tls-pass-certificate-to-upstream`. Upstream applications or services that trust forwarded client-certificate headers may incorrectly treat unauthenticated requests as mTLS-authenticated.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-mwrr-6hp4-pxr6
- https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-mtls-header-spoofing-via-ingress-nginx-http-router

**Actions:**
- **Fix:** Upgrade Traefik to v3.7.14 or later.
- **Workaround:** Enable `ssl-redirect`, remove `auth-tls-pass-certificate-to-upstream` from affected plaintext routes, and ensure upstream services do not trust client-supplied `Ssl-Client-*` headers without independent validation.
- **Tradeoff:** Enforcing redirects or removing certificate forwarding can break clients that require HTTP access or depend on upstream certificate-based identity.

#### Kubernetes — CVE-2026-92982 (CVSS 8.5 HIGH)
**Summary:** A low-privileged Kubernetes user can exploit a Jinja2 template injection in Ansible Operator Plugins by placing malicious expressions in custom-resource specification values. The values are processed by Ansible inside the operator pod, potentially enabling arbitrary code execution and privilege escalation through the operator’s service account, which may have cluster-wide permissions.

**Affected Features / Interoperability:** Affected components include Ansible Operator Plugins, custom-resource processing, and the operator pod’s service account and Kubernetes API permissions. Malicious resources could result in code execution, service-account compromise, and access to cluster-wide resources.

**Source:**
- https://access.redhat.com/errata/RHSA-2026:87120
- https://access.redhat.com/errata/RHSA-2026:87124
- https://access.redhat.com/security/cve/CVE-2026-92982
- https://bugzilla.redhat.com/show_bug.cgi?id=2522227

**Actions:**
- **Fix:** Apply the referenced Red Hat security advisories RHSA-2026:87120 and RHSA-2026:87124, or otherwise update the affected Ansible Operator Plugins to a vendor-fixed release.
- **Workaround:** Restrict creation and modification of affected custom resources to trusted administrators, reduce the operator service account’s permissions, and inspect operator logs and pod activity for suspicious template execution.
- **Tradeoff:** Restricting custom-resource use and operator privileges can reduce self-service automation and require additional review for tenant workflows.

#### Kubernetes — CVE-2026-105311 (CVSS 7.7 HIGH)
**Summary:** The StreamsHub Console operator acts as a confused deputy. A Kubernetes tenant permitted to create a Console custom resource can set `spec.kafkaClusters[].credentials.kafkaUser.namespace` to another namespace, causing the operator to read that namespace’s KafkaUser Secret and copy plaintext SASL credentials or TLS private keys into a Secret in the attacker’s namespace.

**Affected Features / Interoperability:** The affected components are the StreamsHub Console operator, Console custom-resource authorization, and the operator’s cluster-wide Secrets RBAC. KafkaUser Secrets, SASL credentials, TLS private keys, and related Kafka authentication integrations are at risk.

**Source:**
- https://access.redhat.com/security/cve/CVE-2026-105311
- https://bugzilla.redhat.com/show_bug.cgi?id=2510875

**Actions:**
- **Fix:** No fixed release is identified in the supplied data; apply the Red Hat guidance for CVE-2026-105311 when available.
- **Workaround:** Prevent tenants from creating Console custom resources or restrict their ability to specify `kafkaUser.namespace`; reduce the operator’s Secret read permissions and monitor for Secrets copied across namespaces.
- **Tradeoff:** Tightening Console permissions may prevent legitimate multi-namespace Kafka integrations and require administrator-mediated configuration.

#### Kubernetes — CVE-2026-86332 (CVSS 6.5 MEDIUM)
**Summary:** The `odh-dashboard` backend in Red Hat OpenShift AI lacks authorization on the `GET /api/nim-serving/:nimResource` route. Any authenticated dashboard user can retrieve the full Secret object, including `.data`, containing the cluster NVIDIA NGC API key and NIM image-pull Secret; creation and deletion of the same credentials are administrator-gated, but reads are not.

**Affected Features / Interoperability:** The affected component is the OpenShift AI dashboard’s NIM-serving API and its use of the dashboard service account to read Kubernetes Secrets. NVIDIA NGC API keys, NIM image-pull credentials, NIM serving deployments, and associated model-serving functionality may be exposed.

**Source:**
- https://access.redhat.com/errata/RHSA-2026:86891
- https://access.redhat.com/security/cve/CVE-2026-86332
- https://bugzilla.redhat.com/show_bug.cgi?id=2529287

**Actions:**
- **Fix:** Apply RHSA-2026:86891 and follow the Red Hat remediation guidance for CVE-2026-86332.
- **Workaround:** Restrict access to the NIM-serving API, remove unnecessary dashboard service-account access to the relevant Secrets, rotate exposed NVIDIA NGC API keys and image-pull credentials, and monitor for unauthorized reads.
- **Tradeoff:** Restricting dashboard access to NIM credentials can limit legitimate viewing and management of NIM resources for non-administrators.

#### Docker — CVE-2026-114087 (CVSS 8.1 HIGH)
**Summary:** Trigger.dev self-hosted Docker Compose deployments before 4.5.6 that use the default secrets from `hosting/docker/.env.example` allow authentication bypass because a hardcoded `MAGIC_LINK_SECRET` lets anyone forge valid magic-link tokens. An unauthenticated attacker can then log in as any email address and reach Postgres, Redis, and ClickHouse using default credentials from runner containers on infrastructure networks.

**Affected Features / Interoperability:** Affected components are Trigger.dev’s self-hosted Docker Compose configuration, magic-link authentication, runner containers, and the infrastructure-network access paths to Postgres, Redis, and ClickHouse. Tenant data and the availability or integrity of those backing services may be compromised.

**Source:**
- https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x
- https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets

**Actions:**
- **Fix:** Upgrade Trigger.dev to 4.5.6 or later.
- **Workaround:** Replace the hardcoded `MAGIC_LINK_SECRET` and all default database, Redis, and ClickHouse credentials with unique high-entropy secrets; ensure these services are not exposed beyond required trusted networks.
- **Tradeoff:** Rotating credentials requires synchronized updates across Trigger.dev and all runner containers, and secret rotation may invalidate existing sessions or integrations until completed.

**Source:**
