# Security Digest — 2026-10-22

## Cloud Security

The most urgent formal issue is **CVE-2026-113709 in Argo CD (CVSS 9.9)**: a malicious GitOps repository can trigger command execution in the repository server when Helm support is enabled for Kustomize builds. No supplied entry is confirmed as CISA KEV-exploited, so urgency is based on the critical CVSS score, network-exposed repository configuration, and potential credential theft and code execution. Other priorities include the Azure Kubernetes Service authorization flaw, three independently exploitable Traefik ingress authentication bypasses, and a Trigger.dev deployment flaw that permits unauthenticated account takeover and access to backing data stores.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-50516 (CVSS 9.4 CRITICAL)
**Summary:** Incorrect authorization in Microsoft Azure Kubernetes Service lets an authorized attacker elevate privileges over the network. The issue requires an attacker who already has some authorized access to the affected AKS environment; the supplied data does not provide a CISA KEV status or remediation due date.

**Affected Features / Interoperability:** Microsoft Azure Kubernetes Service authorization and privilege boundaries are affected. Successful exploitation could compromise cluster workloads or other resources available to the elevated identity; the raw data does not identify specific affected API versions, add-ons, or Kubernetes configurations.

**Source:** https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516

**Actions:**
- Fix: Consult the Microsoft Security Response Center advisory for the applicable AKS mitigation or upgrade; no patched version is specified in the supplied data.
- Workaround: Review AKS RBAC, role assignments, and workload identities for excessive privilege, and remove unnecessary authorization until Microsoft guidance can be applied.
- Tradeoff: Restricting RBAC and workload identities can interrupt legitimate cross-resource or cross-namespace workflows.

#### Kubernetes — CVE-2026-113709 (CVSS 9.9 CRITICAL)
**Summary:** Argo CD versions 2.1.0 through 3.3.15, 3.4.10, 3.5.4, and 3.6.0-rc2 contain a Helm plugin-loading vulnerability when the operator enables `--enable-helm` for Kustomize builds. A repository-controlled `helmGlobals.configHome` can cause a downloader plugin to be loaded and executed inside `argocd-repo-server`, allowing malicious repository content to expose credentials and execute commands as that service account.

**Affected Features / Interoperability:** Argo CD's Kustomize/Helm integration, Helm configuration and data directories, and repository-server plugin execution are affected. Repository credentials and other secrets accessible to the repository-server service account may be exposed; the supplied description was truncated before identifying all possible downstream impact.

**Source:**
- https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts
- https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c
- https://github.com/argoproj/argo-cd/pull/6059
- https://github.com/argoproj/argo-cd/releases/tag/v3.3.15
- https://github.com/argoproj/argo-cd/releases/tag/v3.4.10

**Actions:**
- Fix: Upgrade to Argo CD 3.3.15, 3.4.10, 3.5.4, or 3.6.0-rc2 as applicable to the deployed branch.
- Workaround: Disable `--enable-helm` for Kustomize builds and prevent repositories from controlling `helmGlobals.configHome`.
- Tradeoff: Disabling Helm support removes or limits Helm-backed Kustomize chart workflows and may require changes to affected deployment repositories.

#### Kubernetes — CVE-2026-114636 (CVSS 8.7 HIGH)
**Summary:** Traefik 3.7.13 before 3.7.14 fails to apply access-control annotations to the HTTP router generated for SSL-passthrough ingresses on non-TLS entry points. An unauthenticated attacker who can reach the HTTP entry point and provide the Ingress host can bypass `auth-type`, `auth-url`, or source-range protections, with the access not logged.

**Affected Features / Interoperability:** The Traefik Kubernetes Ingress NGINX provider and SSL-passthrough ingress routing are affected. Authentication and source-whitelist enforcement for protected backends can fail, exposing those backends to unauthorized requests.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-qvj7-gq9c-hp7q
- https://www.vulncheck.com/advisories/traefik-3.7.13-authentication-bypass-via-ssl-passthrough-ingress-http-router

**Actions:**
- Fix: Upgrade Traefik to 3.7.14 or later.
- Workaround: Block direct access to the affected non-TLS HTTP entry point or require TLS before traffic can reach affected ingress routes.
- Tradeoff: Blocking or restricting the HTTP entry point may reduce availability for clients that depend on plaintext access or SSL passthrough.

#### Kubernetes — CVE-2026-114638 (CVSS 8.7 HIGH)
**Summary:** Traefik versions 3.7.0 through 3.7.13 can merge client certificate authorities when authentication TLS secret names collide after dot-to-dash normalization. A remote attacker holding a certificate issued by another host's CA may access a host that requires its own client CA, while legitimate clients are denied.

**Affected Features / Interoperability:** The Traefik Kubernetes Ingress NGINX provider's `auth-tls-secret` handling and client-certificate authentication are affected. Mutual-TLS isolation between hosts may fail, and legitimate client access may be disrupted.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-rv2h-qh7j-xrjw
- https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-client-ca-mix-up-via-auth-tls-secret-name-collision

**Actions:**
- Fix: Upgrade Traefik to 3.7.14 or later.
- Workaround: Use unique authentication TLS secret names that cannot collide after dot-to-dash normalization.
- Tradeoff: Renaming secrets requires updating the affected Ingress resources and TLS secret references.

#### Kubernetes — CVE-2026-114640 (CVSS 8.7 HIGH)
**Summary:** Traefik versions 3.7.0 through 3.7.13 may forward client-supplied `Ssl-Client-*` headers on the plaintext HTTP router. When SSL redirect is disabled and certificate details are forwarded upstream, an unauthenticated attacker can spoof an mTLS identity by supplying headers such as `Ssl-Client-Verify: SUCCESS`.

**Affected Features / Interoperability:** The Traefik Kubernetes Ingress NGINX provider, plaintext HTTP routing, and forwarding of `Ssl-Client-*` headers are affected. Upstream applications that trust those headers for client-certificate identity or authorization may admit unauthenticated attackers.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-mwrr-6hp4-pxr6
- https://www.vulncheck.com/advisories/traefik-3.7.0-before-3.7.14-mtls-header-spoofing-via-ingress-nginx-http-router

**Actions:**
- Fix: Upgrade Traefik to 3.7.14 or later.
- Workaround: Require TLS on affected routes and ensure upstream applications never trust client-supplied `Ssl-Client-*` headers on plaintext connections.
- Tradeoff: Requiring TLS can affect plaintext clients and requires cooperation from upstream services that rely on the forwarded headers.

#### Kubernetes — CVE-2026-92982 (CVSS 8.5 HIGH)
**Summary:** Ansible Operator Plugins process attacker-controlled custom resource values through Jinja2 without adequate sanitization. A low-privileged Kubernetes user can inject template expressions that execute inside an operator pod, potentially obtaining the operator service account's cluster-wide permissions.

**Affected Features / Interoperability:** Ansible Operator Plugins, custom-resource value rendering, and operator-pod execution are affected. An exploited operator may gain access to cluster resources permitted to its service account, potentially enabling broader privilege escalation.

**Source:**
- https://access.redhat.com/errata/RHSA-2026:87120
- https://access.redhat.com/errata/RHSA-2026:87124
- https://access.redhat.com/security/cve/CVE-2026-92982
- https://bugzilla.redhat.com/show_bug.cgi?id=2522227

**Actions:**
- Fix: Apply the affected Red Hat updates in RHSA-2026:87120 or RHSA-2026:87124, as applicable.
- Workaround: Restrict creation and modification of custom resources handled by vulnerable operators to highly trusted administrators and remove unnecessary RBAC permissions from the operator service account.
- Tradeoff: Restricting custom-resource access slows tenant self-service and reducing operator RBAC may break legitimate automation.

#### Kubernetes — CVE-2026-105311 (CVSS 7.7 HIGH)
**Summary:** A tenant permitted to create a StreamsHub Console custom resource can point `spec.kafkaClusters[].credentials.kafkaUser.namespace` at another namespace. Using cluster-wide Secret RBAC, the operator reads that namespace's KafkaUser secret and copies the plaintext SASL credentials or TLS private key into the attacker's namespace.

**Affected Features / Interoperability:** The StreamsHub Console operator, KafkaUser Secret access, and tenant namespace isolation are affected. Cross-namespace Kafka credentials—including SASL secrets and TLS private keys—may be exposed, while the operator's cluster-wide Secret permissions make the cross-namespace behavior possible.

**Source:**
- https://access.redhat.com/security/cve/CVE-2026-105311
- https://bugzilla.redhat.com/show_bug.cgi?id=2510875

**Actions:**
- Fix: No fixed release is identified in the supplied data; monitor the Red Hat CVE and bugzilla entries for remediation.
- Workaround: Remove the operator's broad cross-namespace Secret access, enforce namespace restrictions, and deny Console creation to untrusted tenants.
- Tradeoff: Narrowing operator permissions may prevent legitimate integrations spanning multiple namespaces.

Any authenticated dashboard user may obtain the cluster NVIDIA NGC API-key Secret and NIM image-pull Secret.

**Affected Features / Interoperability:** The `odh-dashboard` backend-for-frontend API for NIM serving, dashboard service-account Secret access, and NIM credential handling are affected. Administrative controls prevent creation and deletion of the credentials but do not protect the read path.

**Source:**
- https://access.redhat.com/errata/RHSA-2026:86891
- https://access.redhat.com/security/cve/CVE-2026-86332
- https://bugzilla.redhat.com/show_bug.cgi?id=2529287

**Actions:**
- Fix: Apply RHSA-2026:86891 for the affected OpenShift AI deployment.
- Workaround: Restrict access to the dashboard and remove unnecessary dashboard service-account access to the affected Secrets.
- Tradeoff: Reduced dashboard access can impair NIM workflows for legitimate users.

**Affected Features / Interoperability:** The TimesTen Kubernetes Operator and the subset of TimesTen data accessible through it are affected. The raw data does not identify specific operator commands, services, or downstream database integrations.

**Actions:**

- Workaround: Restrict HTTPS access to the TimesTen Kubernetes Operator to trusted low-privileged users and networks.
- Tradeoff: Network and account restrictions can limit legitimate operator access.

#### Docker — CVE-2026-114087 (CVSS 8.1 HIGH)
**Summary:** Trigger.dev self-hosted Docker Compose deployments using the default secrets from `hosting/docker/.env.example` contain a hardcoded magic-link secret. An unauthenticated attacker can forge valid tokens for any email address, log in as that user, and use default credentials to reach Postgres, Redis, and ClickHouse on runner infrastructure networks.

**Affected Features / Interoperability:** Trigger.dev authentication, magic-link tokens, and the self-hosted Docker Compose deployment are affected. Postgres, Redis, and ClickHouse instances reachable from runner containers may expose all tenant data to an unauthenticated attacker.

**Source:**
- https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x
- https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets

**Actions:**
- Fix: Upgrade Trigger.dev to 4.5.6 or later.
- Workaround: Replace every default secret, including `MAGIC_LINK_SECRET` and backing database credentials; prevent runner containers from using default credentials.
- Tradeoff: Secret rotation requires coordinated updates across the Trigger.dev deployment and may invalidate existing sessions or integrations until all components are synchronized.

#### Docker — CVE-2026-76304 (CVSS 4.3 MEDIUM)
**Summary:** In Splunk SOAR versions below 8.7.0, an authenticated user without Automation Broker edit permission can download the Automation Broker Docker Compose configuration. The file reveals the SOAR instance URL, container image location, and broker version.

**Affected Features / Interoperability:** Splunk SOAR Automation Broker configuration download and authorization are affected. The disclosed metadata can aid reconnaissance but does not by itself provide direct access to the SOAR instance or broker.

**Source:** https://advisory.splunk.com/advisories/SVD-2026-1010

**Actions:**
- Fix: Upgrade Splunk SOAR to 8.7.0 or later.
- Workaround: Restrict access to Automation Broker configuration downloads to roles authorized to edit brokers.
- Tradeoff: Tightening role permissions may prevent legitimate users from reviewing broker deployment settings.
