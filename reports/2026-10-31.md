# Security Digest — 2026-10-31

## Cloud Security

The most urgent issue in this batch is CVE-2026-102649 (CVSS 9.9 CRITICAL) in Burrito, a Terraform Automation Collaboration Software (TACoS) Kubernetes operator, which appears under both Kubernetes and Terraform: prior to 0.13.0, the `POST /api/webhook` endpoint accepts unsigned GitHub and GitLab events when a `TerraformRepository`'s `webhookSecret` is omitted or empty, so anyone who can reach the `burrito-server` endpoint and knows a tracked repository URL can forge events to create or delete Terraform pull requests with no authentication beyond network reachability. None of the entries in this batch are flagged as CISA KEV-confirmed, so this critical network-reachable flaw takes priority over the remaining issues, which include AWS EC2 AMI credential exposure (CVE-2012-3427), unscored Google Cloud Identity Platform and Application Integration flaws, multiple Kubernetes ecosystem authorization and SAML replay issues, and Docker-related agent/sandbox escapes in PraisonAI, praktor, and sigstore-js.

### Formal Vulnerabilities

#### AWS — CVE-2012-3427 (CVSS 5.5 MEDIUM)
**Summary:** A flaw in JBoss Enterprise Application Platform (EAP) and the EC2 Amazon Machine Image (AMI) sets incorrect permissions (755) on `/var/cache/jboss-ec2-eap/`, allowing a local user to read sensitive files, including AWS credentials. It is triggered locally and requires local access to the EC2 instance.
**Affected Features / Interoperability:** The `/var/cache/jboss-ec2-eap/` directory on JBoss EAP EC2 AMIs; exposure of AWS credentials could compromise any workload or IAM identity tied to the affected instance.
**Source:** http://rhn.redhat.com/errata/RHSA-2012-1376.html, http://secunia.com/advisories/51016, http://www.osvdb.org/86409
**Actions:**
- Fix: Apply Red Hat errata RHSA-2012-1376; a specific patched version is not stated in the data.
- Workaround: Restrict filesystem permissions on `/var/cache/jboss-ec2-eap/` so only authorized accounts can read it, and limit local access to the EC2 instance.
- Tradeoff: Tighter permissions may break legitimate local processes or scripts that expect world-readable access to that cache directory.

#### Google Cloud Platform — CVE-2026-85268 (CVSS UNSCORED)
**Summary:** A cross-site scripting (XSS) vulnerability in the auth/handler of Google Cloud Identity Platform and Firebase Authentication on iOS, prior to 2026-08-14, lets an unauthenticated remote attacker execute arbitrary JavaScript using a malicious iOS bundle ID. No patch due date is stated in the data.
**Affected Features / Interoperability:** Google Cloud Identity Platform and Firebase Authentication auth/handler on iOS; downstream authentication flows for iOS apps could be compromised.
**Source:** https://firebase.google.com/support/releases#auth-helper-fix
**Actions:**
- Fix: Update to Google Cloud Identity Platform / Firebase Authentication version 2026-08-14 or later.
- Workaround: No workaround is provided in the data.
- Tradeoff: No significant tradeoff.

#### Google Cloud Platform — CVE-2026-93327 (CVSS UNSCORED)
**Summary:** A deserialization of untrusted data vulnerability in the SubWorkflow task in Google Cloud Application Integration, prior to 2026-09-11, lets an authenticated attacker execute arbitrary code using a maliciously crafted serialized object. The vulnerability was patched on 11 September 2026, and no customer action is needed.
**Affected Features / Interoperability:** Google Cloud Application Integration SubWorkflow task; as a managed service component, customer integrations relying on SubWorkflow tasks are affected until the provider patch is applied.
**Source:** https://docs.cloud.google.com/support/bulletins
**Actions:**
- Fix: Patched by Google on 11 September 2026; no customer action needed (managed service update).
- Workaround: None required; the vendor-managed patch is already applied.
- Tradeoff: No significant tradeoff.

#### Kubernetes — CVE-2026-102649 (CVSS 9.9 CRITICAL)
**Summary:** Burrito, a Terraform Automation Collaboration Software (TACoS) Kubernetes operator, accepts unsigned GitHub and GitLab events at `POST /api/webhook` prior to 0.13.0 when a `TerraformRepository`'s credentials omit `webhookSecret` or set it to an empty value. Anyone who can reach `burrito-server`'s endpoint and knows a tracked repository's URL can forge events to create or delete Terraform pull requests; no authentication is required beyond network reachability.
**Affected Features / Interoperability:** `burrito-server` `POST /api/webhook` endpoint and `TerraformRepository` credentials in Kubernetes; GitHub/GitLab webhook integration and Terraform pull request creation/deletion could be abused or disrupted.
**Source:** https://github.com/padok-team/burrito/commit/1d48432a4a0126429c99f5fa42567bf3711d1ca1, https://github.com/padok-team/burrito/releases/tag/v0.13.0, https://github.com/padok-team/burrito/security/advisories/GHSA-7m68-72r6-3jx8
**Actions:**
- Fix: Upgrade Burrito to 0.13.0 or later.
- Workaround: Set a non-empty `webhookSecret` on all `TerraformRepository` credentials and restrict network access to the `burrito-server` endpoint.
- Tradeoff: Requires reconfiguring existing webhook credentials and may break integrations that rely on empty or omitted secrets.

#### Kubernetes — CVE-2026-119115 (CVSS 8.5 HIGH)
**Summary:** Incorrect authorization in the issuer resolution logic in AWS Private CA Connector for Kubernetes (`aws-privateca-issuer`) before v1.10.1 might allow an authenticated remote user to obtain certificates, including subordinate CA certificates, signed by a cluster-scoped AWS Private CA issuer that their approval policy does not authorize.
**Affected Features / Interoperability:** `aws-privateca-issuer` / AWS Private CA Connector for Kubernetes; certificate issuance, Certificate resources, Ingress annotations, and the EKS add-on could be affected.
**Source:** https://aws.amazon.com/security/security-bulletins/2026-156-aws/, https://github.com/cert-manager/aws-privateca-issuer/releases/tag/v1.10.1, https://github.com/cert-manager/aws-privateca-issuer/security/advisories/GHSA-hjrh-q6pg-mh82
**Actions:**
- Fix: Upgrade `aws-privateca-issuer` to v1.10.1 or the AWS Private CA Connector for Kubernetes EKS add-on to v1.10.1-eksbuild.1.
- Workaround: Review and tighten certificate approval policies and cluster-scoped issuer RBAC until the upgrade is applied.
- Tradeoff: Stricter approval policies may block legitimate certificate requests.

#### Kubernetes — CVE-2025-2241 (CVSS 8.2 HIGH)
**Summary:** A flaw in Hive, a component of Multicluster Engine (MCE) and Advanced Cluster Management (ACM), exposes vCenter credentials in the ClusterProvision object after provisioning a vSphere cluster. Users with read access to ClusterProvision objects can extract sensitive credentials without direct Kubernetes Secret access, leading to unauthorized vCenter access, cluster management, and privilege escalation.
**Affected Features / Interoperability:** Hive ClusterProvision objects in MCE/ACM; vSphere cluster provisioning, vCenter credentials, and Kubernetes Secrets isolation could be affected.
**Source:** https://access.redhat.com/security/cve/CVE-2025-2241, https://bugzilla.redhat.com/show_bug.cgi?id=2351350, https://github.com/openshift/hive/pull/2612
**Actions:**
- Fix: A patched version is not stated in the data; apply the relevant Red Hat errata/update for Hive/MCE/ACM.
- Workaround: Restrict read access to ClusterProvision objects and review RBAC bindings.
- Tradeoff: Limiting read access may break monitoring or tooling that needs ClusterProvision visibility.

#### Kubernetes — CVE-2026-103314 (CVSS 7.4 HIGH)
**Summary:** Red Hat Advanced Cluster Security for Kubernetes (RHACS) Central SAML authentication ACS endpoint does not retain used SAML assertion or response identifiers to prevent replay. An attacker who obtains a valid, unexpired signed SAML response can submit it multiple times and receive distinct Central authentication tokens for the mapped identity.
**Affected Features / Interoperability:** RHACS Central SAML authentication ACS endpoint; Central authentication tokens and SAML-based identity mapping could be abused.
**Source:** https://access.redhat.com/errata/RHSA-2026:85932, https://access.redhat.com/errata/RHSA-2026:92342, https://access.redhat.com/security/cve/CVE-2026-103314
**Actions:**
- Fix: Apply Red Hat errata RHSA-2026:85932 and/or RHSA-2026:92342; a specific patched version is not stated.
- Workaround: Enforce short SAML response validity windows and monitor Central authentication logs for repeated assertion use.
- Tradeoff: Shorter validity windows may cause legitimate SAML logins to fail if clock skew exists.

#### Kubernetes — CVE-2026-118760 (CVSS 6.5 MEDIUM)
**Summary:** Kubeflow Pipelines frontend artifact routes from 0.5.1 until 2.17.0 did not check whether an authenticated user was authorized for the requested namespace. A user who can reach the frontend and knows an artifact location can read another tenant's namespace artifacts, or omit the namespace to reach an unguarded direct handler, exposing datasets, models, or pipeline outputs. This applies to multi-user deployments relying on Kubeflow Pipelines authorization for tenant isolation.
**Affected Features / Interoperability:** Kubeflow Pipelines frontend artifact routes; multi-user tenant isolation and artifact/pipeline output access could be broken.
**Source:** https://github.com/kubeflow/pipelines/commit/fb69119c997402ebddab4f6410c617cb3d3634ba, https://github.com/kubeflow/pipelines/issues/9889, https://github.com/kubeflow/pipelines/pull/12860
**Actions:**
- Fix: Upgrade Kubeflow Pipelines to 2.17.0 or later.
- Workaround: Restrict frontend access to trusted users and review namespace authorization controls.
- Tradeoff: Broader access restrictions may disrupt legitimate cross-namespace workflows.

#### Kubernetes — CVE-2026-63121 (CVSS 6.3 MEDIUM)
**Summary:** Kubewarden policies `trusted-repos-policy` (before 2.1.2) compares an image's `registry` hostname against reject and allow lists case-sensitively even though registry DNS names are case-insensitive. An image with an uppercase or mixed-case registry hostname can miss a rejection rule for the equivalent lowercase host, so the admission policy accepts a resource whose container runtime pulls the same prohibited image.
**Affected Features / Interoperability:** Kubewarden `trusted-repos-policy` admission controller; image allow/reject list enforcement and container runtime image pulls could be affected.
**Source:** https://github.com/kubewarden/policies/commit/bc5597fcbbb0bc464b714ca7ff645c9743dea41b, https://github.com/kubewarden/policies/security/advisories/GHSA-8p62-9vh2-272p, https://github.com/kubewarden/policies/tree/trusted-repos-policy/v2.1.2
**Actions:**
- Fix: Upgrade Kubewarden policies to 2.1.2 or later.
- Workaround: Normalize registry hostnames to lowercase in reject/allow lists and audit existing policies.
- Tradeoff: List normalization requires updating all policy rules and may miss already-cased entries.

#### Kubernetes — CVE-2026-119573 (CVSS 4.4 MEDIUM)
**Summary:** Traefik 3.7.11 before 3.7.15 contains an authorization bypass in the Kubernetes Ingress NGINX provider that skips the cross-namespace check on the `auth-tls-secret` annotation when a cached client authentication TLS option is reused. Users who can create Ingresses can reference another namespace's CA secret already used by another Ingress, enforcing it on their own routes and learning whether it exists, without disclosure of its contents.
**Affected Features / Interoperability:** Traefik Kubernetes Ingress NGINX provider `auth-tls-secret` annotation; cross-namespace secret reference behavior and Ingress routing could be affected.
**Source:** https://github.com/traefik/traefik/security/advisories/GHSA-28hp-c82p-8vqj, https://www.vulncheck.com/advisories/traefik-3.7.11-before-3.7.15-cross-namespace-authorization-bypass-via-auth-tls-secret
**Actions:**
- Fix: Upgrade Traefik to 3.7.15 or later.
- Workaround: Avoid reusing cached client authentication TLS options across namespaces and restrict Ingress creation permissions.
- Tradeoff: Restricting Ingress creation may block legitimate deployment pipelines.

#### Kubernetes — CVE-2026-62284 (CVSS UNSCORED)
**Summary:** OSAC operator console-proxy `RemoteConfigResolver` parses Kubernetes Secret kubeconfig data with `clientcmd.RESTConfigFromKubeConfig` without sanitizing the resulting `rest.Config`. An attacker who can create or modify a Secret labeled `osac.openshift.io/remote-cluster-kubeconfig: "true"` in a namespace where the proxy's RoleBinding grants Secret read access can supply `users[].user.exec`, leading to exec credential invocation when building an HTTP transport for an upstream WebSocket connection.
**Affected Features / Interoperability:** OSAC operator console-proxy and remote cluster kubeconfig Secret handling; WebSocket connections to upstream clusters could be hijacked.
**Source:** https://github.com/osac-project/osac-operator/commit/7e4222b6ab465fc00606c8cfed980b226820cb1b, https://github.com/osac-project/osac-operator/commit/86466378aa3603253dca7fa2f59a2733af0dc092, https://github.com/osac-project/osac-operator/pull/321
**Actions:**
- Fix: A patched version is not stated in the data; apply the OSAC operator commits/fixes.
- Workaround: Restrict who can create or modify `osac.openshift.io/remote-cluster-kubeconfig` Secrets and review RoleBindings granting Secret read access.
- Tradeoff: Tighter Secret RBAC may break legitimate remote cluster onboarding.

#### Docker — CVE-2026-57117 (CVSS 8.8 HIGH)
**Summary:** PraisonAI `LocalManagedAgent` / `SandboxedAgent` compute bridging (versions 4.6.10 to before 4.6.59) wraps `read_file`, `list_files`, and `write_file` into shell command strings using raw path arguments sent to shell-backed compute providers. An attacker who can influence a file-tool path argument can break out of the quoted path and execute arbitrary shell commands in the compute environment; with `compute="local"`, commands execute through the local subprocess.
**Affected Features / Interoperability:** PraisonAI file-tool bridging (`read_file`/`list_files`/`write_file`) and compute providers; local subprocess execution and sandbox isolation could be broken.
**Source:** https://github.com/MervinPraison/PraisonAI/security/advisories/GHSA-w6h2-fr4q-xvxv
**Actions:**
- Fix: Upgrade PraisonAI to 4.6.59 or later.
- Workaround: Do not attach untrusted compute providers and restrict file-tool path arguments from untrusted users.
- Tradeoff: Disabling compute bridging breaks agent file-operation functionality.

#### Docker — CVE-2026-62331 (CVSS 8.2 HIGH)
**Summary:** praktor prior to 0.9.1 concatenates attacker-controlled Telegram document filenames into destination paths without sanitization, and `path.Join` collapses parent-directory traversal. A remote Telegram user who can message the bot can write outside `uploads/` within the persistent agent workspace mounted at `/workspace/agent`; because `allow_from: []` permits all senders by default, no prior authentication or privilege is needed.
**Affected Features / Interoperability:** praktor Telegram upload handling and the `/workspace/agent` persistent workspace; file write isolation and agent workspace integrity could be broken.
**Source:** https://github.com/mtzanidakis/praktor/commit/c3731eeda01c0b3ec1dbd13cccd5a147c3182141, https://github.com/mtzanidakis/praktor/pull/228, https://github.com/mtzanidakis/praktor/releases/tag/v0.9.1
**Actions:**
- Fix: Upgrade praktor to 0.9.1 or later.
- Workaround: Restrict Telegram bot senders (configure `allow_from`) and validate/sanitize document filenames.
- Tradeoff: Restricting senders blocks legitimate Telegram users not on the allow list.

#### Docker — CVE-2026-118763 (CVSS 7.4 HIGH)
**Summary:** sigstore-js prior to 0.7.2 stores registry Authorization and Docker configuration headers as defaults on a shared HTTP client in `RegistryClient.signIn()`, while `RegistryClient.uploadBlob()` sends a fresh PUT to an absolute blob-upload `Location` supplied by the registry without checking that its origin or scheme matches the registry. A malicious or compromised registry can direct a user pushing an artifact through `attachArtifactToImage()` to an attacker-controlled host.
**Affected Features / Interoperability:** sigstore-js `RegistryClient.signIn()`/`uploadBlob()` and OCI registry artifact pushes; credential leakage and artifact integrity could be affected.
**Source:** https://github.com/sigstore/sigstore-js/commit/b855f46cfe81f26481c6d3f4b333dfd00f2fd1b1, https://github.com/sigstore/sigstore-js/commit/e4ca65c3ab3c675456ab9b0bd04217ceccad3558, https://github.com/sigstore/sigstore-js/pull/1762
**Actions:**
- Fix: Upgrade sigstore-js to 0.7.2 or later.
- Workaround: Only push to trusted registries and validate blob-upload `Location` origins before following redirects.
- Tradeoff: Restricting registries may break legitimate multi-registry workflows.
