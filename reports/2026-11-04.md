# Security Digest — 2026-11-04

## Cloud Security

The most urgent issue is **CVE-2026-105312** in Kubernetes (CVSS 9.9 CRITICAL), where a tenant with Console CR create permissions can deploy arbitrary container images that inherit a highly privileged ServiceAccount, granting cross-tenant read/write access to Strimzi Kafka resources. This is closely followed by **CVE-2026-12944** in Docker (CVSS 9.6 CRITICAL), allowing root-level code execution in IBM Langflow OSS via malicious component imports, enabling AWS credential theft and lateral movement. No CISA KEV-confirmed exploits are present in this dataset, so priority is driven by confirmed critical-severity vulnerabilities with clear exploitation paths. Google Cloud Platform, Docker, and Terraform also have notable unscored or high-severity issues requiring attention.

### Formal Vulnerabilities

#### Google Cloud Platform — CVE-2026-85299 (CVSS UNSCORED UNSCORED)
**Summary:** A missing authorization check in the `disks.createSnapshot` and `regionDisks.createSnapshot` APIs in Google Compute Engine (versions prior to 2026-08-31) allows an authenticated attacker to exfiltrate disk data across projects. The vulnerability was patched by Google on 31 August 2026 with no customer action required.

**Affected Features / Interoperability:** Compute Engine snapshot creation APIs (`disks.createSnapshot`, `regionDisks.createSnapshot`). Cross-project disk data confidentiality is impacted; no downstream service breakage is described.

**Source:** https://docs.cloud.google.com/compute/docs/security-bulletins#gcp-2026-073

**Actions:**
- Fix: Patched automatically by Google on 2026-08-31; no customer action needed.
- Workaround: None required.
- Tradeoff: No significant tradeoff.

#### Kubernetes — CVE-2026-105312 (CVSS 9.9 CRITICAL)
**Summary:** A Kubernetes tenant with permission to create Console custom resources can specify an arbitrary container image in `spec.containers.api.spec.image`. The operator deploys this image into a pod whose ServiceAccount is bound via ClusterRoleBinding to a ClusterRole with cluster-wide get/list/watch on all Strimzi CRDs (including KafkaUsers), patch on Kafkas/KafkaRebalances, and cluster-monitoring-view. The attacker's code reads the projected SA token and gains cross-tenant Strimzi control-plane read/write access.

**Affected Features / Interoperability:** StreamsHub Console operator (Strimzi/Kafka management). The vulnerable component is the Console CRD controller that deploys user-supplied images with overprivileged ServiceAccount permissions. Downstream impact: cross-tenant KafkaUser, Kafka, and KafkaRebalance resource manipulation, and cluster monitoring data access.

**Source:** https://access.redhat.com/security/cve/CVE-2026-105312, https://bugzilla.redhat.com/show_bug.cgi?id=2510863

**Actions:**
- Fix: No specific patched version mentioned in the data; monitor Red Hat/Strimzi advisories for operator updates.
- Workaround: Restrict Console CR create permissions to trusted tenants only; audit ClusterRoleBindings for excessive privileges on Strimzi CRDs.
- Tradeoff: Limiting Console CR creation may hinder self-service Kafka provisioning for legitimate tenants.

#### Kubernetes — CVE-2026-105311 (CVSS 7.7 HIGH)
**Summary:** The StreamsHub Console operator acts as a confused deputy: a tenant with Console CR create permission can set `spec.kafkaClusters[].credentials.kafkaUser.namespace` to any namespace. The operator, running with cluster-wide Secrets RBAC, reads the victim-namespace KafkaUser Secret (SASL credentials or TLS private keys) and writes the plaintext material into a Secret in the attacker's namespace. No same-namespace check or allowlist exists.

**Affected Features / Interoperability:** StreamsHub Console operator's Kafka cluster credential handling. Impacts secrecy of KafkaUser credentials (SASL/TLS) across namespaces. Downstream: unauthorized access to Kafka clusters using stolen credentials.

**Source:** https://access.redhat.com/security/cve/CVE-2026-105311, https://bugzilla.redhat.com/show_bug.cgi?id=2510875

**Actions:**
- Fix: No specific patched version mentioned; await operator update from Red Hat/Strimzi.
- Workaround: Restrict Console CR create permissions; implement namespace-scoped RBAC for operator's Secrets access if possible.
- Tradeoff: Namespace-scoped RBAC may require operator redesign; restricting Console CR creation limits tenant self-service.

#### Kubernetes — CVE-2026-91168 (CVSS 6.8 MEDIUM)
**Summary:** Warpgate (0.21.0–0.29.0) uses username, target_name, and client IP to key an authorized AdmittedTarget in its Kubernetes request correlator, rather than the immutable user UUID. `KubernetesSessionHandle::close` does not evict the entry. If an account is deleted and a different low-privilege account is created with the same username, the replacement account can reuse the predecessor's live correlation entry.

**Affected Features / Interoperability:** Warpgate's Kubernetes protocol correlator (`warpgate-protocol-kubernetes/src/correlator.rs`). Impacts authentication state management for Kubernetes bastion sessions. Downstream: potential session hijacking after account recreation.

**Source:** https://github.com/warp-tech/warpgate/commit/2f77f07b8335ff495068aa10d650d4b314bf4cc8, https://github.com/warp-tech/warpgate/releases/tag/v0.29.0, https://github.com/warp-tech/warpgate/security/advisories/GHSA-pw7m-635x-pmx7

**Actions:**
- Fix: Upgrade Warpgate to v0.29.0 or later.
- Workaround: Avoid reusing usernames for new accounts after deletion; enforce unique usernames permanently.
- Tradeoff: Username reuse prevention may complicate user lifecycle management.

#### Kubernetes — CVE-2026-118760 (CVSS 6.5 MEDIUM)
**Summary:** Kubeflow Pipelines (0.5.1–2.17.0) frontend artifact routes lack authorization checks for namespace access. An authenticated user who can reach the frontend and knows an artifact location can select another tenant's namespace or omit the namespace to access an unguarded direct handler, reading artifact contents (datasets, models, pipeline outputs). Affects multi-user deployments relying on Kubeflow Pipelines authorization for tenant isolation.

**Affected Features / Interoperability:** Kubeflow Pipelines frontend artifact serving routes. Impacts tenant isolation in multi-user Kubeflow deployments. Downstream: cross-tenant data leakage of ML artifacts.

**Source:** https://github.com/kubeflow/pipelines/commit/fb69119c997402ebddab4f6410c617cb3d3634ba, https://github.com/kubeflow/pipelines/issues/9889, https://github.com/kubeflow/pipelines/pull/12860

**Actions:**
- Fix: Upgrade to Kubeflow Pipelines 2.17.1 or later (implied by "until 2.17.0").
- Workaround: Deploy frontend behind a namespace-aware proxy or enforce network policies restricting cross-namespace frontend access.
- Tradeoff: Proxy/network policies add operational complexity and may break legitimate cross-namespace workflows.

#### Kubernetes — CVE-2026-91163 (CVSS 3.7 LOW)
**Summary:** Warpgate (prior to 0.29.0) Kubernetes protocol listener uses `AcceptAnyClientCert` at the TLS layer, deferring validation to an auth module that renders authentication/lookup failures verbatim in HTTP 500 response bodies. The Kubernetes application lacks the outer request-logging wrapper used by the HTTP protocol, potentially exposing sensitive error details.

**Affected Features / Interoperability:** Warpgate Kubernetes protocol listener (`warpgate-protocol-kubernetes/src/server/client_certs.rs` and `auth.rs`). Impacts error handling and information disclosure during client certificate authentication. Downstream: potential leakage of internal error details to unauthenticated clients.

**Source:** https://github.com/warp-tech/warpgate/commit/8426196a27c30fca521656653f9df1faf3df7523, https://github.com/warp-tech/warpgate/pull/2547, https://github.com/warp-tech/warpgate/releases/tag/v0.29.0

**Actions:**
- Fix: Upgrade Warpgate to v0.29.0 or later.
- Workaround: None specified; ensure TLS client certificate validation is enforced externally if possible.
- Tradeoff: No significant tradeoff.

#### Docker — CVE-2026-12944 (CVSS 9.6 CRITICAL)
**Summary:** IBM Langflow OSS 1.0.0 through 1.10.0 allows attackers to execute arbitrary Python code with root privileges (UID=0) by submitting components containing `socket` or `urllib` imports. This enables AWS credential theft via IMDSv1 SSRF (full IAM role permissions), arbitrary file exfiltration from the container filesystem, and lateral movement to internal services (PostgreSQL, Redis) within the Docker network. The scanner incorrectly returns "validated": true, providing a false security signal.

**Affected Features / Interoperability:** Langflow OSS component validation and execution sandbox. Impacts any deployment running untrusted components. Downstream: host/cloud credential compromise, container escape, internal network pivoting.

**Source:** https://www.ibm.com/support/pages/node/7278919

**Actions:**
- Fix: Upgrade Langflow OSS to version 1.10.1 or later (implied by "through 1.10.0").
- Workaround: Disable component submission from untrusted users; run Langflow in a restricted network without IMDS access; use seccomp/AppArmor profiles to block `socket`/`urllib` imports.
- Tradeoff: Disabling component submission breaks core Langflow functionality; network restrictions may hinder legitimate integrations.

#### Docker — CVE-2026-57853 (CVSS 8.8 HIGH)
**Summary:** DataGerry before 3.3.0 has a server-side template injection (SSTI) via the `template_data` field in POST `/rest/docapi/template`. Authenticated attackers with `base.docapi.template.add` permission can store arbitrary Jinja2 payloads, later rendered in a non-sandboxed environment via GET `/rest/docapi/template/<id>/render/<object_id>`. The `cycler.__init__.__globals__.os` gadget chain allows OS command execution as the DataGerry web process user (root in default Docker deployments).

**Affected Features / Interoperability:** DataGerry docapi template rendering endpoint. Impacts confidentiality/integrity of the DataGerry host. Downstream: full container compromise, potential host escape if running privileged.

**Source:** https://docs.datagerry.com/en/latest/reference/changelog.html, https://github.com/DataGerry/DataGerry/releases/tag/3.3.0, https://www.vulncheck.com/advisories/datagerry-ssti-via-docapi-template-rendering

**Actions:**
- Fix: Upgrade DataGerry to 3.3.0 or later.
- Workaround: Revoke `base.docapi.template.add` permission from untrusted users; deploy DataGerry as non-root user; enable Jinja2 sandbox if available.
- Tradeoff: Removing template permissions limits legitimate templating features; non-root deployment may require image rebuild.

#### Docker — CVE-2026-119119 (CVSS 7.5 HIGH)
**Summary:** Crawl4AI before 0.9.5 has a DoS vulnerability in the Docker API server where `_clamp_untrusted()` fails to cap `delay_before_return_html`, `mean_delay`, and `max_range` fields in untrusted `CrawlerRunConfig` bodies. Unauthenticated attackers can send huge values to `/crawl` or `/crawl/stream` to hold browser pages or stall the rate limiter, exhausting the page pool and blocking other crawls.

**Affected Features / Interoperability:** Crawl4AI Docker API server crawl endpoints. Impacts availability of the crawling service. Downstream: denial of service for all crawl jobs.

**Source:** https://github.com/unclecode/crawl4ai/security/advisories/GHSA-rhjm-7hj7-75fx, https://www.vulncheck.com/advisories/crawl4ai-before-0.9.5-denial-of-service-via-unbounded-crawlerrunconfig-delay-fields, https://github.com/unclecode/crawl4ai/security/advisories/GHSA-rhjm-7hj7-75fx

**Actions:**
- Fix: Upgrade Crawl4AI to 0.9.5 or later.
- Workaround: Implement input validation at API gateway/WAF to cap delay fields; rate-limit crawl endpoints.
- Tradeoff: Input validation at gateway may require custom rules; rate limiting may affect legitimate high-delay crawls.

#### Docker — CVE-2026-115714 (CVSS 7.4 HIGH)
**Summary:** Improper certificate validation (CWE-295) in the OS certificate bundle shipped in Docker images of multiple Elastic products (APM Server, Beats, Elastic Agent, Logstash, Elastic connectors, Universal Profiling, Elastic Maps Server). This third-party component dependency (CWE-1395) could allow an attacker to intercept or modify TLS-protected communications.

**Affected Features / Interoperability:** TLS connections using the OS certificate bundle in the listed Elastic Docker images. Impacts integrity/confidentiality of outbound TLS connections from these containers. Downstream: potential MITM on Elastic service communications.

**Source:** https://discuss.elastic.co/t/multiple-elastic-docker-images-8-19-24-9-4-9-9-5-6-security-update-esa-2026-237/391374

**Actions:**
- Fix: Update affected Elastic Docker images to patched versions (8.19.2, 9.4.0, 9.9.5, 9.9.6 per advisory ESA-2026-237).
- Workaround: Replace OS certificate bundle with a known-good bundle at container startup; pin trusted CAs.
- Tradeoff: Custom certificate bundles require image rebuild or runtime injection; may break if Elastic services expect specific bundle paths.

#### Docker — CVE-2026-103916 (CVSS UNSCORED UNSCORED)
**Summary:** Docker Sandboxes `sbx cp` does not safely confine host-side paths to a shared workspace. A malicious sandbox can create or replace a workspace symlink so that a later user-initiated copy reads a host file outside the workspace into the sandbox or writes sandbox-controlled data to a host path outside the workspace with the invoking user's permissions.

**Affected Features / Interoperability:** Docker Sandboxes `sbx cp` command (workspace file copy). Impacts host filesystem isolation guarantees. Downstream: arbitrary host file read/write with user permissions.

**Source:** https://docs.docker.com/ai/sandboxes/, https://docs.docker.com/ai/sandboxes/security/isolation/, https://github.com/docker/sbx-releases/releases/tag/v0.51.0

**Actions:**
- Fix: Update Docker Sandboxes to v0.51.0 or later (implied by release tag).
- Workaround: Avoid using `sbx cp` with untrusted sandboxes; mount workspaces read-only where possible.
- Tradeoff: Read-only mounts prevent legitimate write operations from sandbox to host.

#### Docker — CVE-2026-112917 (CVSS UNSCORED UNSCORED)
**Summary:** In Docker Desktop for Windows with WSL2 backend, an unprivileged Linux container can use 32-bit `socketcall` to bypass the default seccomp restriction on `AF_VSOCK`. This exposes host-facing services and Windows files accessible to the logged-in user. Affects x86-64 WSL2; LinuxKit backends unaffected. Fully fixed only with Docker Desktop 4.98.0+ and WSL 3.0.3+; Docker Desktop 4.98.0+ on older WSL remains affected.

**Affected Features / Interoperability:** Docker Desktop WSL2 backend seccomp filtering for VSOCK. Impacts container isolation on Windows hosts. Downstream: host service exposure, Windows file access.

**Source:** https://docs.docker.com/desktop/release-notes/#4980, https://github.com/microsoft/WSL/releases/tag/3.0.3, https://github.com/microsoft/WSL2-Linux-Kernel/releases/tag/linux-msft-wsl-6.18.54.1

**Actions:**
- Fix: Upgrade Docker Desktop to 4.98.0+ and WSL to 3.0.3+.
- Workaround: Use LinuxKit backend instead of WSL2; disable VSOCK in container runtime if not needed.
- Tradeoff: Switching backend may require reconfiguration; disabling VSOCK breaks legitimate VSOCK-dependent workloads.

#### Docker — CVE-2026-121541 (CVSS UNSCORED UNSCORED)
**Summary:** In Docker Buildx v0.19.0–v0.38.0, an untrusted Bake definition building multiple targets together may expose files accessible to the Buildx client without the expected `fs.read` approval. Filesystem paths from some targets are not verified against approved entitlements.

**Affected Features / Interoperability:** Docker Buildx Bake multi-target builds. Impacts filesystem entitlement enforcement during builds. Downstream: unauthorized host file read during build.

**Source:** https://github.com/docker/buildx/security/advisories/GHSA-xg6v-cv2h-2w5h

**Actions:**
- Fix: Upgrade Buildx to v0.38.1.
- Workaround: Avoid running untrusted Bake definitions; use single-target builds.
- Tradeoff: Single-target builds lose parallelization and caching benefits of multi-target Bake.

#### Docker — CVE-2026-121542 (CVSS UNSCORED UNSCORED)
**Summary:** In Docker Buildx v0.19.0–v0.38.0, an untrusted Bake definition may expose files accessible to the Buildx client without `fs.read` approval. Paths under the same parent directory as the current working directory whose names use the working directory's basename as a prefix can skip the filesystem entitlement check. Exploitation requires specific matching filenames next to the project directory.

**Affected Features / Interoperability:** Docker Buildx Bake filesystem entitlement checks. Impacts host file access during build. Downstream: unauthorized host file read.

**Source:** https://github.com/docker/buildx/security/advisories/GHSA-rghq-x9hf-hc3r

**Actions:**
- Fix: Upgrade Buildx to v0.38.1.
- Workaround: Avoid running untrusted Bake definitions; ensure no sibling directories match the CWD basename prefix pattern.
- Tradeoff: Directory naming restrictions may be impractical in shared CI environments.

#### Docker — CVE-2026-121614 (CVSS UNSCORED UNSCORED)
**Summary:** Docker Sandboxes 0.31.0–0.50.0 do not neutralize repository-controlled Git configuration when running host-side Git commands. An attacker who can modify a host repository's Git config (e.g., via direct-mode sandbox with read-write mount) can set `core.fsmonitor` or similar to invoke an external program. Git executes the program during a later clone-mode fetch or `sbx kit push` (v0.39.0+), running on the host with the invoking user's permissions outside the sandbox.

**Affected Features / Interoperability:** Docker Sandboxes Git integration (direct-mode, clone-mode, `sbx kit push`). Impacts host command execution via Git config injection. Downstream: arbitrary host command execution.

**Source:** https://docs.docker.com/ai/sandboxes/, https://docs.docker.com/ai/sandboxes/security/isolation/, https://github.com/docker/sbx-releases/releases/tag/v0.50.0

**Actions:**
- Fix: Upgrade Docker Sandboxes to v0.50.0 or later.
- Workaround: Mount repositories read-only in direct-mode sandboxes; avoid `sbx kit push` with untrusted repos.
- Tradeoff: Read-only mounts prevent legitimate sandbox writes to repo; disabling `sbx kit push` breaks kit publishing workflow.

#### Terraform — CVE-2026-64672 (CVSS UNSCORED UNSCORED)
**Summary:** Terragrunt prior to 1.1.1 derives a predictable per-repository catalog clone root under the shared system temporary directory and follows a symlink already placed at that path. A local attacker who can write to the temporary directory and predict the cataloged repository can redirect cleanup and cloning outside the intended root, causing an existing repository-named directory to be deleted and replaced in the victim's security context.

**Affected Features / Interoperability:** Terragrunt `catalog` command temporary directory handling. Impacts local filesystem integrity during catalog operations. Downstream: arbitrary directory deletion/replacement as the victim user.

**Source:** https://github.com/gruntwork-io/terragrunt/commit/668891c5a2ad2996f134bb8b00098754674ea94a, https://github.com/gruntwork-io/terragrunt/pull/6438, https://github.com/gruntwork-io/terragrunt/releases/tag/v1.1.1

**Actions:**
- Fix: Upgrade Terragrunt to v1.1.1 or later.
- Workaround: Run `terragrunt catalog` in a dedicated temporary directory with restricted permissions (e.g., `TMPDIR` set to a private path).
- Tradeoff: Custom TMPDIR may require wrapper scripts; no significant functional tradeoff.
