# Security Digest — 2026-11-05

## Cloud Security

No CISA KEV-confirmed exploitation was reported in this batch, so priority is driven by CVSS. The single most urgent item is Kubernetes CVE-2026-122310 (CVSS 9.9 CRITICAL): a Kyverno Policy context.apiCall path-validation bypass lets a namespace-scoped user who can create Policies reach cluster-scoped endpoints with Kyverno's ServiceAccount and effectively obtain cluster admin. Docker CVE-2026-97693 (CVSS 9.9 CRITICAL, Yuxi sandbox escape) is tied at the top and should be triaged with equal urgency where Yuxi is deployed. The batch also includes multiple CRITICAL and HIGH container-orchestration and supply-chain issues across Kyverno, AAP Controller, GPUStack, CRI-O, Telepresence, OpenHands, Readest, and DataGerry.

### Formal Vulnerabilities

#### Kubernetes — CVE-2026-122310 (CVSS 9.9 CRITICAL)
**Summary:** Kyverno versions 1.19.1 before 1.19.2 validate a Policy's context.apiCall urlPath after cleaning it but execute the raw path. A namespace-scoped user who can create a Policy can hide "../" segments behind a fragment ("#") or query string ("?") that the Kubernetes client discards, reaching cluster-scoped endpoints with Kyverno's ServiceAccount and effectively gaining cluster admin. Exploitation requires permission to create Policies in a namespace and access to the Kyverno admission controller.
**Affected Features / Interoperability:** Kyverno Policy context.apiCall feature and cluster-scoped Kubernetes API endpoints reachable via Kyverno's ServiceAccount. Full control-plane compromise could affect any workload or secret managed by the cluster; the source data does not enumerate specific downstream integrations.
**Source:** https://github.com/kyverno/kyverno/security/advisories/GHSA-3xfv-vq8x-qhg4, https://www.vulncheck.com/advisories/kyverno-1.19.1-before-1.19.2-privilege-escalation-via-policy-apicall-urlpath
**Actions:**
- Fix: Kyverno 1.19.2.
- Workaround: Restrict creation of Kyverno Policies using context.apiCall to trusted users via RBAC; do not allow untrusted namespace-scoped users to create or modify Policies.
- Tradeoff: Blocks legitimate self-service policy management by namespace teams.

#### Kubernetes — CVE-2026-12564 (CVSS 9.6 CRITICAL)
**Summary:** The AAP Controller's HashiCorp Vault credential plugin's kubernetes_auth() reads the controller pod's Kubernetes service account token and sends it to an attacker-controlled URL when a Vault Secret Lookup credential using kubernetes_role authentication is tested. An authenticated attacker with credential-creation privileges can exfiltrate the service account token and gain Kubernetes API access to control-plane namespaces, including full pod CRUD, secret reads, and database credentials.
**Affected Features / Interoperability:** AAP Controller HashiCorp Vault credential plugin (kubernetes_role authentication) and the credential testing flow. Compromise of the controller service account token could expose pod management, secrets, and database credential integrations across control-plane namespaces; specific downstream integrations are not detailed in the source data.
**Source:** https://access.redhat.com/errata/RHSA-2026:67279, https://access.redhat.com/errata/RHSA-2026:71113, https://access.redhat.com/errata/RHSA-2026:71114
**Actions:**
- Fix: Apply the patched AAP Controller release referenced by Red Hat errata RHSA-2026:67279, RHSA-2026:71113, and RHSA-2026:71114 (no specific version number is given in the source data).
- Workaround: Restrict creation of HashiCorp Vault credentials using kubernetes_role authentication to trusted administrators and disable credential testing by untrusted users.
- Tradeoff: Limits legitimate automation and self-service onboarding of Vault-backed credentials.

#### Kubernetes — CVE-2026-103002 (CVSS 8.8 HIGH)
**Summary:** GPUStack versions 2.2.0 until 2.2.2 forward an authenticated non-administrator's requests to a selected Kubernetes cluster through cluster_apiserver_proxy without a resource-level authorization check. The proxy uses a reachable worker's Kubernetes ServiceAccount credentials, so the caller can read sensitive resources, create or modify workloads, or delete resources according to that ServiceAccount's permissions. Exploitation requires a Kubernetes-provider cluster with a reachable worker and an authenticated GPUStack account.
**Affected Features / Interoperability:** GPUStack cluster_apiserver_proxy and its use of worker Kubernetes ServiceAccount credentials. Downstream workloads, secrets, and any integrations relying on the worker's service account permissions could be affected; the source data does not enumerate specific downstream features.
**Source:** https://github.com/gpustack/gpustack/commit/363191fa1da7e1426c6041f78b3cf00aff2622fe, https://github.com/gpustack/gpustack/commit/cdd67467e0f31460
