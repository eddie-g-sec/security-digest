Scoped Vulnerability Tracking

Cloud Security

No CISA KEV-confirmed exploits appear in this batch, so priority is driven by CVSS severity. The single most urgent item is CVE-2026-58490 in Tracecat (Docker scope), CVSS 9.8 CRITICAL: an unauthenticated attacker who can reach the SAML assertion consumer endpoint on Docker Compose deployments with SAML enabled can forge unsigned SAML responses, hijack existing user sessions, and take over superadmin accounts. A second CRITICAL, CVE-2026-85295 in Chartbrew, allows forged session JWTs when CB_SECRET is weak or shipped by default. The remainder of the batch covers Kubernetes (Kubeflow Pipelines, ingress-nginx, Temporal Server), additional Docker supply-chain and sandbox issues, and Terraform/IntelliJ and Terragrunt local issues; none are KEV-confirmed.

Formal Vulnerabilities

Microsoft AzureCVE-2026-112337CVSS 3.7 · LOW

Summary: Wazuh versions 3.7.0 before 4.14.9 contain a server-side request forgery in the Azure wodle get_graph_events() function. It follows @odata.nextLink without validating host or HTTPS, so an attacker who can influence the nextLink value can redirect manager requests to attacker-controlled endpoints, capture reused Microsoft Graph bearer tokens, and reach internal services. No authentication requirement is stated in the source data; the manager must be network-reachable to the attacker-controlled endpoint.

Affected Features / Interoperability: Wazuh Azure wodle module, specifically get_graph_events(); Microsoft Graph integration and bearer token reuse. The raw data does not detail downstream Azure service or integration breakage beyond potential access to internal services via captured tokens.

Source: https://github.com/wazuh/wazuh/releases/tag/v4.14.9, https://github.com/wazuh/wazuh/security/advisories/GHSA-qxg8-jrjm-w96h, https://www.vulncheck.com/advisories/wazuh-3.7.0-before-4.14.9-ssrf-via-azure-graph-nextlink-pagination

Actions:

  • Fix: Wazuh 4.14.9 or later
  • Workaround: Restrict outbound network access from the Wazuh manager to trusted Microsoft Graph endpoints only; no vendor workaround is provided in the source data
  • Tradeoff: Blocking outbound Graph access may break legitimate Azure log collection and alerting integration
KubernetesCVE-2026-88982CVSS 5.4 · MEDIUM

Summary: Kubeflow Pipelines before 2.18.0 has a cache isolation issue in the legacy V1/raw-Argo execution cache. The cache-server storage path hash and lookup key omit the Kubernetes namespace and trust a mutable pipelines.kubeflow.org/execution_cache_key annotation, so in multi-user deployments a tenant with workload-submission privileges can read another namespace's cached outputs or seed matching cache entries. Authenticated workload-submission privileges and a shared cache service are required.

Affected Features / Interoperability: Kubeflow Pipelines execution cache (legacy V1/raw-Argo), mutating webhook, cache-server storage path; cross-namespace cached ML outputs. The raw data does not specify downstream pipeline or orchestration breakage beyond tenant data isolation.

Source: https://github.com/kubeflow/pipelines/commit/620d0cc89ae0d042a484a003f8ffe6e9a55d347e, https://github.com/kubeflow/pipelines/pull/14359, https://github.com/kubeflow/pipelines/releases/tag/2.18.0

Actions:

  • Fix: Kubeflow Pipelines 2.18.0 or later
  • Workaround: Avoid shared cache services across tenant namespaces; restrict workload-submission permissions to trusted tenants; no vendor workaround is provided in the source data
  • Tradeoff: Segregating caches per namespace increases operational overhead and may reduce cache hit rates
KubernetesCVE-2026-116472CVSS 2.7 · LOW

Summary: ingress-nginx has a missing check on the mirror-target Ingress annotation, allowing a user with Ingress creation permission to target an unauthenticated configuration API within the controller and submit write commands. Corrupting that configuration can drop all traffic through ingress-nginx. Only clusters using ingress-nginx are affected; authenticated Ingress creation permission is required.

Affected Features / Interoperability: ingress-nginx controller data plane, mirror-target annotation, configuration API; all traffic routed through ingress-nginx. The raw data does not detail specific downstream integration breakage beyond dropped traffic.

Source: https://github.com/kubernetes/kubernetes/issues/143852, http://www.openwall.com/lists/oss-security/2026/11/05/4

Actions:

  • Fix: No patched version is specified in the source data
  • Workaround: Restrict Ingress creation permissions to trusted users; audit or disable mirror-target annotation usage if feasible; no vendor workaround is provided in the source data
  • Tradeoff: Restricting Ingress creation may block legitimate deployment workflows; annotation auditing adds operational overhead
KubernetesCVE-2026-120091UNSCORED

Summary: Temporal Server's Worker Controller Instance module (go.temporal.io/auto-scaled-workers) registers a k8s compute provider that builds its Kubernetes client from caller-supplied configuration rather than operator configuration. Two frontend operations reach the provider and could allow execution of a command of the caller's choosing on the Worker Service host under the server process account. Authenticated access to the relevant frontend operations is required; the source description is truncated.

Affected Features / Interoperability: Temporal Server Worker Service, auto-scaled workers k8s compute provider; Kubernetes worker management. The raw data does not specify downstream orchestration breakage beyond host command execution.

Source: https://github.com/temporalio/temporal-auto-scaled-workers/pull/165, https://github.com/temporalio/temporal/pull/12843, https://github.com/temporalio/temporal/releases/tag/v1.31.5

Actions:

  • Fix: Temporal v1.31.5 or later (per release reference)
  • Workaround: Restrict access to Temporal frontend operations that reach the k8s provider; run the Worker Service under a least-privilege service account; no vendor workaround is provided in the source data
  • Tradeoff: Least-privilege service accounts may break worker features requiring broader host or cluster permissions
KubernetesCVE-2026-88984UNSCORED

Summary: Kubeflow Pipelines before 2.16.1 treats the empty namespace used by shared or global pipelines as an authorization exception for modification and deletion operations. An authenticated user can modify or delete shared pipeline definitions and versions without required Kubernetes RBAC permissions. Read-only access to shared pipelines remains intentional; single-user deployments bypass multi-user checks. The source description is truncated.

Affected Features / Interoperability: Kubeflow Pipelines multi-user API server, shared/global pipeline definitions and versions; Kubernetes RBAC integration. The raw data does not specify downstream breakage beyond pipeline integrity and availability.

Source: https://github.com/kubeflow/pipelines/commit/186dd1f3b0403af841c9b4ea7ab94f405339ef6c, https://github.com/kubeflow/pipelines/pull/13288, https://github.com/kubeflow/pipelines/releases/tag/2.16.1

Actions:

  • Fix: Kubeflow Pipelines 2.16.1 or later
  • Workaround: Avoid shared/global pipelines in multi-user deployments; enforce namespace-scoped RBAC strictly; no vendor workaround is provided in the source data
  • Tradeoff: Disabling shared pipelines reduces cross-team pipeline reuse and collaboration
DockerCVE-2026-58490CVSS 9.8 · CRITICAL

Summary: Tracecat versions 0.37.0 until 1.0.0-beta.49 with Docker Compose and SAML enabled render SAML_SIGNED_ASSERTIONS and SAML_SIGNED_RESPONSES as empty values, overriding secure defaults and disabling signature requirements. An unauthenticated attacker who can reach the SAML assertion consumer endpoint can submit a forged unsigned response for an existing user email and obtain that user's session; targeting a superadmin enables superadmin account takeover. Unauthenticated and network-reachable.

Affected Features / Interoperability: Tracecat SAML authentication, assertion consumer endpoint, session issuance; Docker Compose deployments. The raw data does not detail downstream automation or AI agent breakage beyond session compromise.

Source: https://github.com/TracecatHQ/tracecat/commit/018258ba6a17c36cbfa7ca977526c34fb6afc35f, https://github.com/TracecatHQ/tracecat/commit/a97aafbfd667a6b9a3b7b524e1c1bfa9d8c59779, https://github.com/TracecatHQ/tracecat/commit/dab64eb7ac0eb2088783ca14f4cb2d058547bfff

Actions:

  • Fix: Tracecat 1.0.0-beta.49 or later
  • Workaround: Disable SAML if not required, or block unauthenticated access to the SAML assertion consumer endpoint at the network/edge layer; no vendor workaround is provided in the source data
  • Tradeoff: Disabling SAML breaks SSO login for existing users; edge-layer blocking may affect legitimate IdP-initiated flows
DockerCVE-2026-85295CVSS 9.8 · CRITICAL

Summary: Chartbrew before 5.2.3 accepts session tokens signed with CB_SECRET in four authentication helpers, including known, weak, or shipped-default values. A stock Docker Compose deployment retains a known/weak/default CB_SECRET, allowing an attacker to forge HS256 JWT tokens. The source description is truncated; exploitation requires knowledge or guessing of CB_SECRET and network access to the API/socket layer.

Affected Features / Interoperability: Chartbrew session JWT verification (verifyToken.js, verifyUser.js, getUserFromToken.js, socketManager.js), API and socket authentication; Docker Compose deployments. The raw data does not detail downstream breakage beyond account/session hijacking.

Source: https://github.com/chartbrew/chartbrew/commit/da8c71f156aaa13fbc7ead15a4726740fef2b3c5, https://github.com/chartbrew/chartbrew/releases/tag/v5.2.3, https://github.com/chartbrew/chartbrew/security/advisories/GHSA-qvv4-r3q6-8797

Actions:

  • Fix: Chartbrew 5.2.3 or later
  • Workaround: Rotate CB_SECRET to a strong, non-default value and restart; block untrusted access to the API/socket layer at the network edge; no vendor workaround is provided in the source data
  • Tradeoff: Rotating CB_SECRET invalidates all existing sessions, forcing users to re-authenticate
DockerCVE-2026-120203CVSS 8.8 · HIGH

Summary: ShowDoc 2.8.14 before 3.9.6 contains a code injection vulnerability in its Mock feature that allows authenticated users to execute shell commands through mockjs templates. Attackers can store a template via MockController::add with escaped parentheses that mockjs evaluates with eval(), then trigger it through MockController::infoByKey to run commands as root in the official Docker image. Authenticated user access is required.

Affected Features / Interoperability: ShowDoc Mock feature, MockController::add and infoByKey endpoints; official Docker image running as root. The raw data does not detail downstream breakage beyond host container command execution.

Source: https://gist.github.com/LioTree/028af150fd991cf9924dd2c7d5912e54, https://github.com/star7th/showdoc, https://github.com/star7th/showdoc/blob/v3.9.5/mock/index.js#L42

Actions:

  • Fix: ShowDoc 3.9.6 or later
  • Workaround: Disable the Mock feature if unused; restrict Mock access to trusted users; run the container as a non-root user; no vendor workaround is provided in the source data
  • Tradeoff: Disabling Mock removes template mocking functionality; non-root container execution may break features expecting root access
DockerCVE-2026-63655CVSS 7.5 · HIGH

Summary: tsParticles before 4.3.1, in the HTTP mode of @tsparticles/mcp-server, accepts unauthenticated POST /mcp requests and accumulates every request-body chunk in a Buffer[] without a cumulative size limit before Buffer.concat and JSON.parse. A remote attacker can stream an arbitrarily large body to exhaust Node.js process memory and terminate the service, including in the official Docker configuration exposing HTTP mode on 0.0.0.0:3000. Confidentiality and integrity are not affected. Unauthenticated and network-reachable.

Affected Features / Interoperability: @tsparticles/mcp-server HTTP mode, POST /mcp endpoint; official Docker configuration on 0.0.0.0:3000. The raw data does not detail downstream breakage beyond service termination.

Source: https://github.com/tsparticles/tsparticles/commit/25fb70e7f527a91568adaef576570289083f243b, https://github.com/tsparticles/tsparticles/commit/7b3a9488d4201fe9ddd5fec05f4a2ae65d3627ea, https://github.com/tsparticles/tsparticles/pull/5875
