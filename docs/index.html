Scoped Vulnerability Tracking

Cloud Security

The most urgent items this cycle are two CVSS 10.0 CRITICAL vulnerabilities: CVE-2026-46389 in UDS Identity Config (Keycloak client authenticator bypass allowing authentication with any secret) and CVE-2026-83938 in Azure Kubernetes Configuration Service (unauthenticated privilege escalation over the network). Both require immediate patching. No CISA KEV-confirmed exploitation is reported for any entry this cycle, so theoretical severity drives priority. Kubernetes, Docker, and Terraform each carry multiple CRITICAL-rated flaws affecting authentication, authorization, and supply-chain components; Azure and AWS have HIGH-severity issues in identity and CDK tooling; GCP entries are unscored but patched server-side with no customer action required.

Formal Vulnerabilities

AWSCVE-2026-115418CVSS 7.3 · HIGH

Summary: SQL injection in the `@aws-cdk/aws-redshift-alpha` module (before 2.274.0-alpha.0) allows a third party who can influence construct property values (e.g., crafted user names, comments, or passwords) to execute arbitrary SQL with Amazon Redshift superuser privileges, including granting access to all cluster users.

Affected Features / Interoperability: The `aws-redshift-alpha` CDK construct library; downstream impact includes any CloudFormation stacks or CDK apps that synthesize Redshift resources using vulnerable construct versions. Table grants to PUBLIC may have been altered.

Source: https://aws.amazon.com/security/security-bulletins/2026-151-aws/, https://github.com/aws/aws-cdk/releases#release-v2.274.0, https://github.com/aws/aws-cdk/security/advisories/GHSA-25hh-xvj4-2cqv

Actions:

  • Fix: Upgrade to `@aws-cdk/aws-redshift-alpha` version 2.274.0-alpha.0 or later.
  • Workaround: Restrict who can supply construct property values (e.g., limit CDK deployment permissions, validate inputs in CI/CD).
  • Tradeoff: No significant tradeoff for the upgrade; workaround may slow deployment velocity.
Microsoft AzureCVE-2026-45108CVSS 8.4 · HIGH

Summary: Himmelblau (interoperability suite for Entra ID and Intune) versions 2.0.0 through 3.1.4 and 2.3.11 contain an authentication bypass in the Device Authorization Grant flow. A user within the same Entra ID domain can obtain a local Unix session as another user by providing their own valid credentials, because the `token_validate` function fails to verify that the local part of the authenticated user's UPN matches the requested account.

Affected Features / Interoperability: Himmelblau's PAM/SSSD integration for Linux device login via Entra ID. Downstream: any Linux fleet using Himmelblau for Entra ID-joined authentication.

Source: https://github.com/himmelblau-idm/himmelblau/security/advisories/GHSA-pmxh-j4r6-88mv

Actions:

  • Fix: Upgrade to Himmelblau 3.1.5 or later (or 2.3.12 for the 2.3.x branch).
  • Workaround: Disable Himmelblau authentication or restrict local account mappings until patched.
  • Tradeoff: Workaround breaks Entra ID-based Linux login for affected hosts.
Microsoft AzureCVE-2026-24899CVSS 7.5 · HIGH

Summary: Fleet (open-source device management) before 4.82.0 accepts authentication tokens from any Azure AD tenant in its Windows MDM enrollment flow. The JWT signature is validated against Microsoft's multi-tenant JWKS endpoint, but `aud` and `iss` claims are not enforced, allowing any Microsoft-signed token with expected scopes to authenticate to Fleet's MDM endpoints.

Affected Features / Interoperability: Fleet's Windows MDM enrollment feature. Downstream: any Fleet deployment with Windows MDM enabled.

Source: https://github.com/fleetdm/fleet/releases/tag/fleet-v4.82.0, https://github.com/fleetdm/fleet/security/advisories/GHSA-ffg9-j72f-j6xm

Actions:

  • Fix: Upgrade to Fleet 4.82.0 or later.
  • Workaround: Disable Windows MDM enrollment if not required.
  • Tradeoff: Disabling MDM enrollment prevents Windows device management via Fleet.
Microsoft AzureCVE-2026-42316CVSS 6.5 · MEDIUM

Summary: The `kafka-sink-azure-kusto` Kafka Connect plugin (before 5.2.3) does not sanitize user-controlled values in the `kusto.tables.topics.mapping` configuration. Fields such as `db`, `table`, `mapping`, and `format` are interpolated directly into KQL management commands via `String.formatted(...)`, allowing an actor who can modify the connector configuration to inject arbitrary KQL commands.

Affected Features / Interoperability: Kafka Connect sink for Azure Data Explorer (Kusto). Downstream: data pipelines ingesting Kafka topics into Kusto clusters.

Source: https://github.com/Azure/kafka-sink-azure-kusto/pull/155, https://github.com/Azure/kafka-sink-azure-kusto/releases/tag/v5.2.3, https://github.com/Azure/kafka-sink-azure-kusto/security/advisories/GHSA-c9mr-mqvh-6wgj

Actions:

  • Fix: Upgrade to `kafka-sink-azure-kusto` 5.2.3 or later.
  • Workaround: Restrict write access to the connector configuration (e.g., Kafka Connect REST API, GitOps repo).
  • Tradeoff: No significant tradeoff for the upgrade.

KubernetesCVE-2026-46389CVSS 10.0 · CRITICAL

Summary: UDS Identity Config (versions 0.11.0 through 0.26.0) contains a logic error in the `client-kubernetes-secret` Keycloak client authenticator: the submitted `client_secret` is overwritten with the mounted Kubernetes secret before comparison. An attacker who can reach the Keycloak token endpoint and knows a `client_id` using this authenticator can authenticate as that client with any `client_secret` value, obtaining valid tokens.

Affected Features / Interoperability: UDS Identity Config's Keycloak client authenticator (`client-kubernetes-secret`), consumed by UDS Core's Identity deployment. Downstream: any UDS (Unified Defense Stack) deployment using Keycloak for OIDC/token issuance.

Source: https://github.com/defenseunicorns/uds-identity-config/releases/tag/v0.26.1, https://github.com/defenseunicorns/uds-identity-config/security/advisories/GHSA-8mg2-6588-r4hw

Actions:

  • Fix: Upgrade UDS Identity Config to 0.26.1 or later.
  • Workaround: Restrict network access to Keycloak token endpoint; rotate mounted Kubernetes secrets.
  • Tradeoff: Network restriction may break legitimate service-to-service auth; secret rotation requires coordinated rollout.
