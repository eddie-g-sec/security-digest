Scoped Vulnerability Tracking

Cloud Security

The most urgent issue this cycle is CVE-2026-57566 (CVSS 9.3 CRITICAL) in Readest (Docker), an unauthenticated server-side request forgery in the OPDS proxy route that lets attackers fetch arbitrary URLs, follow redirects to internal metadata endpoints, and achieve remote code execution in default Docker deployments. No CISA KEV-confirmed vulnerabilities appear in today’s data, so the highest theoretical severity drives priority. Kubernetes also carries a cluster of high-severity authorization bypasses and credential leaks (CVE-2026-103002, CVE-2026-119572, CVE-2026-119115) that could compromise multi-tenant clusters, while Terraform tooling in JetBrains IDEs introduces code-execution risks in untrusted projects.

Formal Vulnerabilities

Microsoft AzureCVE-2026-112337CVSS 3.7 · LOW

Summary: Wazuh versions 3.7.0 through 4.14.8 contain a server-side request forgery in the Azure wodle’s `get_graph_events()` function. The code follows `@odata.nextLink` pagination URLs without validating the host or enforcing HTTPS, allowing an attacker who can influence the `nextLink` value to redirect the Wazuh manager’s requests to an attacker-controlled endpoint. This captures the reused Microsoft Graph bearer token and can reach internal services.

Affected Features / Interoperability: The Azure wodle (workload) component that pulls events from Microsoft Graph; impacts token reuse and potential access to internal network services reachable from the manager.

Source: https://github.com/wazuh/wazuh/releases/tag/v4.14.9, https://github.com/wazuh/wazuh/security/advisories/GHSA-qxg8-jrjm-w96h, https://www.vulncheck.com/advisories/wazuh-3.7.0-before-4.14.9-ssrf-via-azure-graph-nextlink-pagination

Actions:

  • Fix: Upgrade Wazuh to version 4.14.9 or later.
  • Workaround: No workaround specified in advisory.
  • Tradeoff: No significant tradeoff.
KubernetesCVE-2026-103002CVSS 8.8 · HIGH

Summary: GPUStack versions 2.2.0 through 2.2.2 have an authorization bypass in the `cluster_apiserver_proxy`. An authenticated non-administrator can forward requests to a selected Kubernetes cluster using a reachable worker’s ServiceAccount credentials, without resource-level authorization checks. This allows reading sensitive resources, creating/modifying workloads, or deleting resources per that ServiceAccount’s permissions. Exploitation requires a Kubernetes-provider cluster with a reachable worker.

Affected Features / Interoperability: GPUStack’s cluster API server proxy; impacts any Kubernetes resources accessible via the worker’s ServiceAccount (workloads, secrets, RBAC).

Source: https://github.com/gpustack/gpustack/commit/363191fa1da7e1426c6041f78b3cf00aff2622fe, https://github.com/gpustack/gpustack/commit/cdd67467e0f314609dc82216e142940d321abfed, https://github.com/gpustack/gpustack/pull/5911

Actions:

  • Fix: Upgrade GPUStack to version 2.2.3 or later (commit 363191fa1da7e1426c6041f78b3cf00aff2622fe).
  • Workaround: No workaround specified in advisory.
  • Tradeoff: No significant tradeoff.
KubernetesCVE-2026-119572CVSS 8.7 · HIGH

Summary: Traefik versions 3.7.0-ea.1 through 3.7.14 have an authentication bypass in the Kubernetes Ingress NGINX provider. When an Ingress declares a path on the same host without matching `auth-tls-secret` settings, Traefik silently disables mTLS and falls back to default TLS options, allowing unauthenticated attackers to reach backends that require client certificates.

Affected Features / Interoperability: Traefik’s Kubernetes Ingress NGINX provider mTLS enforcement via `auth-tls-secret` annotation; impacts any backend services relying on mutual TLS for authentication.

Source: https://github.com/traefik/traefik/security/advisories/GHSA-p8wx-ph99-xgcr, https://www.vulncheck.com/advisories/traefik-3.7.0-ea.1-before-3.7.15-mtls-bypass-via-ingress-nginx-provider

Actions:

  • Fix: Upgrade Traefik to version 3.7.15 or later.
  • Workaround: Ensure all Ingresses on a given host declare consistent `auth-tls-secret` annotations; avoid mixing mTLS and non-mTLS paths on the same host.
  • Tradeoff: May require coordination across teams managing different Ingresses on shared hosts.
KubernetesCVE-2026-119115CVSS 8.5 · HIGH

Summary: AWS Private CA Connector for Kubernetes (aws-privateca-issuer) before v1.10.1 has incorrect authorization in issuer resolution logic. An authenticated remote user can obtain certificates (including subordinate CA certificates) signed by a cluster-scoped AWS Private CA issuer that their approval policy does not authorize.

Affected Features / Interoperability: Certificate issuance via `aws-privateca-issuer`; impacts PKI trust within the cluster and any workloads relying on issued certificates for authentication.

Source: https://aws.amazon.com/security/security-bulletins/2026-156-aws/, https://github.com/cert-manager/aws-privateca-issuer/releases/tag/v1.10.1, https://github.com/cert-manager/aws-privateca-issuer/security/advisories/GHSA-hjrh-q6pg-mh82

Actions:

  • Fix: Upgrade `aws-privateca-issuer` to v1.10.1 or the EKS add-on to v1.10.1-eksbuild.1; update any CertificateRequest, Certificate, or Ingress annotations referencing the old issuer.
  • Workaround: No workaround specified in advisory.
  • Tradeoff: No significant tradeoff.
KubernetesCVE-2026-123047CVSS 7.5 · HIGH

Summary: Eclipse BaSyx Helm Charts `basyx` chart versions 3.0.0-rc.1 through 3.12.1 store Keycloak user passwords in cleartext in a Kubernetes ConfigMap when the bundled Keycloak is enabled. The bootstrap administrator user (with `admin` role and a non-temporary password) is included by default. Any principal with read access to the ConfigMap can obtain these credentials.

Affected Features / Interoperability: Helm chart’s Keycloak initialization ConfigMap (`<release>-basyx-keycloak-init-config`); impacts Keycloak admin access and any downstream services using those credentials.

Source: https://github.com/eclipse-basyx/charts/pull/106, https://github.com/eclipse-basyx/charts/releases/tag/basyx-3.12.2, https://github.com/eclipse-basyx/charts/security/advisories/GHSA-6438-759f-6f8v

Actions:

  • Fix: Upgrade the `basyx` chart to version 3.12.2 or later.
  • Workaround: Restrict read access to the ConfigMap via Kubernetes RBAC; rotate Keycloak passwords after upgrade.
  • Tradeoff: Restricting ConfigMap access may break legitimate tooling that reads initialization data.
KubernetesCVE-2026-123059CVSS 7.5 · HIGH

Summary: Eclipse BaSyx Helm Charts `aas-basyx-v2-full` chart version 2.2.0 stores the `basyx-technical-user` OAuth2 client secret in cleartext in a Kubernetes ConfigMap (via Keycloak realm-import JSON) despite also writing it to a Secret. The client uses client-credentials grant and holds the realm `admin` role.

Affected Features / Interoperability: Helm chart’s Keycloak realm-import ConfigMap (`<keycloak.fullnameOverride>-realm-import`); impacts OAuth2 client credentials and admin-level access to Keycloak.
