Scoped Vulnerability Tracking

Cloud Security

No CISA KEV-confirmed entries appear in today's data, so nothing here carries a confirmed-exploitation mandate — but two Docker-delivered services sit at CVSS 10.0. The single most urgent item is CVE-2026-40281 in Gotenberg (10.0 CRITICAL): an unauthenticated newline injection into ExifTool metadata values lets a remote caller rename or move arbitrary files inside the processing container, and it is a working bypass of the incomplete fix shipped in v8.30.1. It ties on score with CVE-2026-33587 (Open Notebook SSTI, 10.0), which ranks just below it because it requires an authenticated application user. Gotenberg is the dominant theme of the day: five separate advisories (three critical, two high) covering unauthenticated RCE, SSRF to cloud metadata endpoints, and arbitrary file manipulation — treat the whole deployment as needing upgrade to 8.32.0 or later rather than patching individual CVEs. Kubernetes contributes a 9.9 Traefik Gateway API tenant-isolation bypass and a Kyverno RBAC bypass, both multi-tenancy boundary breaks. Note that the Kubernetes and Docker lists are each at the 10-entry cap, so they are not guaranteed complete.

Formal Vulnerabilities

Docker (Gotenberg)CVE-2026-40281CVSS 10.0 · CRITICAL

Summary: Gotenberg's metadata write endpoint validates metadata keys for control characters but leaves values unsanitized. A newline in a value splits the ExifTool stdin stream into a second argument, letting an unauthenticated remote caller inject ExifTool pseudo-tags such as `-FileName`, `-Directory`, `-SymLink`, and `-HardLink`, and thereby rename or move any PDF being processed to an arbitrary path inside the container. This is a bypass of the incomplete key-sanitization fix introduced in v8.30.1.

Affected Features / Interoperability: The PDF metadata write API (ExifTool-backed) in Gotenberg versions 8.30.1 and earlier. Downstream impact is on any service that exposes Gotenberg as a shared PDF endpoint and any file the container process can reach — including files staged for other tenants or jobs. The data does not state whether the container's own filesystem is the full blast radius or whether mounted volumes are affected.

Source: https://github.com/gotenberg/gotenberg/commit/405f1069c026bb08f319fb5a44e5c67c33208318 · https://github.com/gotenberg/gotenberg/security/advisories/GHSA-q7r4-hc83-hf2q

Actions:

  • Fix: No fixed version is stated in the provided data. Track advisory GHSA-q7r4-hc83-hf2q; the referenced commit indicates the corrective change.
  • Workaround: Disable or block the metadata write endpoint at the ingress/reverse proxy, and run Gotenberg in a read-only, non-root container with no host or shared-volume mounts.
  • Tradeoff: Metadata writing is unavailable to callers, and read-only rootfs may break Gotenberg's internal temp-file handling unless a scoped writable tmpfs is provided.
Docker (Open Notebook)CVE-2026-33587CVSS 10.0 · CRITICAL

Summary: Open Notebook v1.8.3 fails to sanitize user input in user-created transformations, allowing Server-Side Template Injection. An application user can escalate that SSTI to Python execution and then OS command execution inside the Docker container.

Affected Features / Interoperability: The user-created "transformations" feature of Open Notebook. Downstream exposure is whatever the container can reach — mounted note/document volumes, environment-supplied credentials, and the Docker host if the socket is mounted. The data does not enumerate which template engine or which container mounts are reachable.

Source: https://github.com/lfnovo/open-notebook/security/advisories/GHSA-f35w-wx37-26q7

Actions:

  • Fix: No fixed version is stated in the provided data; the advisory is the only reference given.
  • Workaround: Remove or restrict the transformations feature, require admin approval for transformation authoring, and run the container as non-root with no Docker socket and no host bind mounts.
  • Tradeoff: Transformations become unusable or bottlenecked on an administrator, and non-root operation may break any workflow that assumes write access to the default data paths.
Docker (Portabase)CVE-2026-67449CVSS 9.8 · CRITICAL

Summary: A path traversal in Portabase's TUS upload webhook handler (`app/api/tus/hooks/route.ts`) lets an unauthenticated attacker overwrite arbitrary files under the private data directory, including `/data/private/keys/master_key.bin`, the AES-256-GCM master key. Overwriting the master key compromises the confidentiality of every encrypted backup the tool manages.

Affected Features / Interoperability: The TUS resumable-upload webhook in Portabase prior to 1.21.2. Because Portabase backs up PostgreSQL, MySQL, MsSQL, MariaDB, Firebird, SQLite, MongoDB, Redis, files, and Docker volumes, the master key is the root of trust for all of those backup sets — its loss affects restore integrity and every downstream retention copy.

Source: https://github.com/Portabase/portabase/commit/8dcb406790728fbdbf758ec88bf000af79498fc1 · https://github.com/Portabase/portabase/pull/355 · https://github.com/Portabase/portabase/releases/tag/1.21.2

Actions:

  • Fix: Upgrade to Portabase 1.21.2.
  • Workaround: Block the TUS webhook path at the reverse proxy and restrict Portabase's network exposure to trusted backup clients only.
  • Tradeoff: Resumable uploads through the webhook stop working, so large or interrupted backup uploads may fail and need to be restarted whole.
Docker (Gotenberg)CVE-2026-42589CVSS 9.8 · CRITICAL

Summary: Prior to 8.31.0, Gotenberg's `/forms/pdfengines/metadata/write` endpoint passes JSON metadata keys straight to ExifTool with no character validation. A `\n` embedded in a key splits the ExifTool stdin stream into a new argument line, allowing injection of arbitrary ExifTool flags including `-if`, which evaluates Perl expressions — unauthenticated OS command execution in a single HTTP request that returns HTTP 200 with a valid PDF.

Affected Features / Interoperability: The PDF Engines metadata write endpoint and its `go-exiftool` integration. Any orchestration, workflow engine, or application that calls Gotenberg's metadata API is an entry point; the silent HTTP 200 means exploitation leaves no obvious error signal in caller logs.

Source: https://github.com/gotenberg/gotenberg/security/advisories/GHSA-rqgh-gxv4-6657

Actions:

  • Fix: Upgrade to Gotenberg 8.31.0 or later.
  • Workaround: Block the metadata write endpoint at the proxy layer and run Gotenberg with a read-only root filesystem, dropped capabilities, and no host mounts.

Affected Features / Interoperability: This is a third-party IoT device firmware flaw that uses AWS IoT Core MQTT as its transport — it is not a vulnerability in an AWS service, so AWS-side configuration changes will not fix it. The shared-credential design is the core problem: there is no per-device identity to revoke, so blast radius is the whole fleet at once. Downstream, anything that trusts telemetry or commands from these robots inherits the compromise.

Source: https://kb.cert.org/vuls/id/188754 · https://github.com/frodobots-org · https://www.frodobots.ai/

Actions:

  • Fix: No patched firmware version is provided in the data. Engage FrodoBots and monitor CERT/CC VU#188754 for a corrected release.
  • Workaround: Isolate the fleet onto a dedicated AWS IoT account and VPC with no route to production, restrict the IoT policy to the minimum topic set, and treat all device telemetry as untrusted input.
  • Tradeoff: Fleet isolation limits the operational data and remote-management reach your teams currently rely on, and tightening topic policies can break device-to-cloud command flows that assume wildcard publish/subscribe.
