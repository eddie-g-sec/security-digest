Scoped Vulnerability Tracking

Cloud Security

The most urgent issue is CVE-2026-113709 in Argo CD, rated CVSS 9.9 Critical. A repository-controlled Helm plugin can be executed during Kustomize builds when `--enable-helm` is enabled, potentially exposing repository credentials and enabling code execution in `argocd-repo-server`. No supplied entry is marked as confirmed exploited by CISA KEV; however, this flaw, together with the critical Azure Kubernetes Service authorization flaw, should be prioritized for immediate exposure review. Cloud and platform supply-chain incidents involving LiteLLM and PHP, as well as Google Cloud’s reported `europe-west2` outage, warrant additional operational attention.

Formal Vulnerabilities

Microsoft AzureCVE-2026-50516CVSS 9.4 · CRITICAL

Summary: An incorrect authorization flaw in Microsoft Azure Kubernetes Service allows an authorized attacker to escalate privileges over the network. Exploitation requires an attacker who already has some authorized access to the affected Azure environment and can reach the vulnerable service over the network.

Affected Features / Interoperability: Azure Kubernetes Service authorization and privilege management are affected. The supplied data does not specify particular AKS components, versions, or downstream integrations.

Source: https://msrc.microsoft.com/update-guide/vulnerability/CVE-2026-50516

Actions:

  • Fix: No patched version or release is identified in the supplied data; consult the MSRC advisory for the current remediation guidance.
  • Workaround: Review AKS role assignments and least-privilege policies, and restrict access to affected control-plane endpoints until a patch or vendor mitigation is available.
  • Tradeoff: Restricting authorized users and service accounts may interrupt legitimate Kubernetes administration and automation.
KubernetesCVE-2026-113709CVSS 9.9 · CRITICAL

Summary: Argo CD versions from 2.1.0 through 3.3.15, 3.4.10, 3.5.4, and 3.6.0-rc2 are affected when an operator has enabled `--enable-helm` for `kustomize build`. A repository-controlled Helm chart URL can cause Helm to load and execute a downloader plugin from a repository-controlled configuration directory inside `argocd-repo-server`, potentially exposing repository credentials; exploitation is associated with a malicious or compromised Git repository and does not require separate plugin installation.

Affected Features / Interoperability: Argo CD Kustomize builds, Helm chart handling, Git repository integrations, and the `argocd-repo-server` component are affected. The supplied data indicates that the command runs as the repo-server user and may read repository credentials.

Source:

  • https://argo-cd.readthedocs.io/en/stable/user-guide/kustomize/#kustomizing-helm-charts
  • https://github.com/argoproj/argo-cd/commit/b6d5c23bce2f8a46c52975ba438a3b93d242d96c
  • https://github.com/argoproj/argo-cd/pull/6059
  • https://github.com/argoproj/argo-cd/releases/tag/v3.3.15
  • https://github.com/argoproj/argo-cd/releases/tag/v3.4.10

Actions:

  • Fix: Upgrade Argo CD to a fixed release. The supplied references identify v3.3.15 and v3.4.10 as affected releases; the fix should be applied according to the upstream Argo CD advisory and release guidance.
  • Workaround: Disable `--enable-helm` for Kustomize builds and prevent Helm chart repository URLs from selecting untrusted downloader protocols; restrict repository and Argo CD access pending upgrade.
  • Tradeoff: Disabling Helm support breaks or reduces Kustomize workflows that depend on Helm chart rendering and may require alternative chart deployment procedures.

KubernetesCVE-2026-92982CVSS 8.5 · HIGH

Summary: A Jinja2 template-injection vulnerability in Ansible Operator Plugins allows a low-privileged Kubernetes user to execute embedded expressions through malicious custom-resource specification values. The resulting code executes within the operator pod and can lead to arbitrary code execution and privilege escalation under the operator’s service account.

Affected Features / Interoperability: Ansible Operator Plugins, custom-resource processing, and the operator pod are affected. The operator service account may have cluster-wide permissions, allowing escalation beyond the attacker’s original Kubernetes privileges.

Source:

  • https://access.redhat.com/errata/RHSA-2026:87120
  • https://access.redhat.com/errata/RHSA-2026:87124
  • https://access.redhat.com/security/cve/CVE-2026-92982

Actions:

  • Fix: Apply the referenced Red Hat security advisories, RHSA-2026:87120 and RHSA-2026:87124.
  • Workaround: Restrict creation and modification of affected custom resources and reduce the operator service account’s cluster-wide permissions until the affected packages are updated.
  • Tradeoff: Tighter custom-resource and RBAC controls can reduce operator functionality and may require additional approval workflows.
KubernetesCVE-2026-105311CVSS 7.7 · HIGH

Summary: The StreamsHub Console operator permits a tenant that can create a Console custom resource to reference a KafkaUser namespace other than its own. Because the operator has cluster-wide Secrets permissions, it can read KafkaUser Secrets from another namespace and copy plaintext SASL credentials or TLS private keys into the attacker’s namespace.

Affected Features / Interoperability: StreamsHub Console custom resources, KafkaUser Secrets, SASL credentials, TLS private keys, and cross-namespace tenant isolation are affected. The flaw can expose Kafka credentials and enable unauthorized access to Kafka services.

Source:

  • https://access.redhat.com/security/cve/CVE-2026-105311
  • https://bugzilla.redhat.com/show_bug.cgi?id=2510875

Actions:

  • Fix: No patched version is identified in the supplied data; apply the current Red Hat remediation guidance for CVE-2026-105311.
  • Workaround: Prevent untrusted tenants from creating or modifying StreamsHub Console resources, restrict the operator’s access to Secrets, and monitor for cross-namespace KafkaUser Secret references.
  • Tradeoff: Restricting Console resource creation or operator Secret access may reduce tenant functionality and require additional administrative intervention.

Affected Features / Interoperability: The OpenShift AI dashboard’s NIM serving API, Kubernetes Secret reads, NVIDIA NGC credentials, and NIM image pull credentials are affected. Credential disclosure could affect NIM services and image pulls across environments using those Secrets.

Source:

  • https://access.redhat.com/errata/RHSA-2026:86891

  • https://bugzilla.redhat.com/show_bug.cgi?id=2529287

Actions:

  • Workaround: Restrict access to the dashboard and the affected API route, audit dashboard service-account Secret permissions, and rotate exposed NGC API keys and NIM image pull Secrets.
  • Tradeoff: Narrowing dashboard permissions may prevent legitimate users from managing NIM resources; rotating credentials can interrupt existing NIM services until applications are updated.

DockerCVE-2026-114087CVSS 8.1 · HIGH

Summary: Self-hosted Trigger.dev Docker Compose deployments before 4.5.6 that use the default secrets from `hosting/docker/.env.example` allow authentication bypass because a hardcoded `MAGIC_LINK_SECRET` lets anyone forge magic-link tokens. An unauthenticated attacker can log in as any email address and reach Postgres, Redis, and ClickHouse using default runner credentials on infrastructure networks.

Affected Features / Interoperability: Trigger.dev authentication, magic-link tokens, Docker Compose deployments, and the default Postgres, Redis, and ClickHouse runner services are affected. Compromise may expose all tenant data and permit unauthorized access to backing data stores.

Source:

  • https://github.com/triggerdotdev/trigger.dev/security/advisories/GHSA-pqxw-g93w-hj9x
  • https://www.vulncheck.com/advisories/trigger-dev-before-4.5.6-authentication-bypass-via-hardcoded-default-secrets

Actions:

  • Fix: Upgrade Trigger.dev to 4.5.6 or later.
  • Workaround: Replace the default `MAGIC_LINK_SECRET` and all default database, Redis, and ClickHouse credentials with unique secrets; do not expose the affected services directly to untrusted networks.
  • Tradeoff: Changing credentials requires coordinated updates to Trigger.dev and all dependent runner containers and may invalidate existing sessions or connections.
