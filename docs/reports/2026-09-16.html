Scoped Vulnerability Tracking

Database

The most urgent item in today's digest is CVE-2024-58385 (CVSS 9.8 CRITICAL), an unauthenticated SQL injection in Yonyou U8 CRM that can lead to arbitrary command execution on Microsoft SQL Server deployments when `xp_cmdshell` is enabled, with exploitation evidence observed since February 2025. While no CISA KEV-confirmed entries appear in this dataset, this 9.8-score critical vulnerability outranks all others by severity and has confirmed in-the-wild exploitation. Healthcare environments running Yonyou U8 CRM backed by SQL Server should prioritize patching immediately, as the flaw requires no authentication and can result in full OS-level compromise.

Formal Vulnerabilities

MySQL

[Anyquery]CVE-2026-50006CVSS 9.1 · CRITICAL

Summary: Anyquery server forwards unauthenticated SQL from its MySQL-compatible server port to SQLite without restricting `ATTACH DATABASE` filesystem targets. A remote attacker can cause SQLite to create a database file at any path writable by the Anyquery process and place attacker-controlled table content there, enabling arbitrary file creation or overwrite, filesystem integrity loss, and denial of service. Remote code execution is possible only when another service interprets the written file or the process has a suitably privileged writable target.

Affected Features / Interoperability: The MySQL-compatible server port and SQLite `ATTACH DATABASE` functionality. Downstream integrations that rely on Anyquery as a SQL query gateway could experience data corruption or service disruption. Client drivers connecting via the MySQL wire protocol are affected.

Source:

  • https://github.com/julien040/anyquery/security/advisories/GHSA-xrcf-6jh3-ggvx
  • https://github.com/julien040/anyquery/releases/tag/0.4.5
  • https://github.com/julien040/anyquery/commit/27f84fc168310455eaf81ec4ba87eed20298670c

Actions:

  • Fix: Upgrade to version 0.4.5.
  • Workaround: Disable the MySQL-compatible server port if not actively used; restrict filesystem permissions on the Anyquery process to minimize writable paths.
  • Tradeoff: Disabling the MySQL-compatible port removes the ability to query Anyquery via MySQL wire protocol clients. Restricting filesystem permissions may break legitimate `ATTACH DATABASE` operations.
[Anyquery]CVE-2026-54628CVSS 8.6 · HIGH

Summary: Anyquery server exposes URL-capable SQLite virtual table modules such as `json_reader` and `log_reader` through its unauthenticated MySQL-compatible server port without restricting outbound destinations. A remote attacker can provide a loopback, private-network, or link-local cloud metadata URL, causing `go-getter` in the Anyquery server process to fetch the selected resource and expose its response as queryable table data, enabling internal network probing, access to internal APIs, and disclosure of cloud credentials.

Affected Features / Interoperability: SQLite virtual table modules (`json_reader`, `log_reader`) and the `go-getter` HTTP client within the Anyquery server process. Downstream functionality affected includes any integration relying on these virtual tables for data ingestion. Cloud metadata endpoints and internal APIs reachable from the server process are at risk of being probed or exfiltrated.

Source:

  • https://github.com/julien040/anyquery/security/advisories/GHSA-hwrq-8wxh-q4xv
  • https://github.com/julien040/anyquery/releases/tag/0.4.5
  • https://github.com/julien040/anyquery/commit/27f84fc168310455eaf81ec4ba87eed20298670c

Actions:

  • Fix: Upgrade to version 0.4.5.
  • Workaround: Restrict outbound network access from the Anyquery server process via firewall rules or network policies; disable virtual table modules that support URL fetching.
  • Tradeoff: Blocking outbound network access may break legitimate use cases that rely on fetching remote data via virtual tables. Disabling modules removes functionality for applications that depend on them.
[SPIP]CVE-2026-72708CVSS 7.5 · HIGH

Summary: SPIP before 4.4.18 contains an unauthenticated blind SQL injection vulnerability in the SQL escaping layer that allows unauthenticated attackers to inject arbitrary SQL by supplying a crafted `annee` parameter value matching a word character followed by an open parenthesis, which bypasses escaping for date-type columns across MySQL, SQLite, and PostgreSQL backends. Attackers can exploit the always-present `sitemap.xml.html` template's `annee` criterion to embed unescaped time-based or boolean payloads into database queries, enabling extraction of arbitrary database content including the `alea_ephemere` secret used to sign SPIP action nonces.

Affected Features / Interoperability: The SPIP SQL escaping layer and the `sitemap.xml.html` template's `annee` criterion. Affects MySQL, SQLite, and PostgreSQL backends. Downstream functionality impacted includes SPIP's authentication nonce system, potentially allowing session forgery. Any SPIP installation with the sitemap template active is reachable.

Source:

  • https://blog.lexfo.fr/casse-spip-sqli-to-rce.html
  • https://blog.spip.net/Mise-a-jour-critique-de-securite-sortie-de-SPIP-4-4-18.html
  • https://www.vulncheck.com/advisories/spip-unauthenticated-sql-injection-via-sitemap-annee-parameter

Actions:

  • Fix: Upgrade to SPIP version 4.4.18.
  • Workaround: Disable or remove the `sitemap.xml.html` template if not required; restrict access to the sitemap endpoint at the web server or reverse proxy level.
  • Tradeoff: Disabling the sitemap template removes a public-facing feature. Restricting the sitemap endpoint may break SEO or public content discovery.
[leapp-upgrade-el9toel10]CVE-2026-75092CVSS 7.3 · HIGH

Summary: A privilege escalation flaw exists in the `scan_mysql` actor of `leapp-upgrade-el9toel10`. During RHEL 9 to RHEL 10 upgrades, the actor runs `mysqld --validate-config --log-error-verbosity=2` directly as root in the Leapp actor context, bypassing the packaged MySQL systemd unit that normally starts the daemon as `User=mysql`. A process compromised as the mysql OS identity can write a malicious `mysqld-auto.cnf` and shared object into `/var/lib/mysql`, setting `plugin_dir` and `early_plugin_load` so MySQL loads the attacker-controlled object during configuration validation, executing code as UID 0 in an unconfined SELinux domain.

Affected Features / Interoperability: The `leapp-upgrade-el9toel10` migration tool's `scan_mysql` actor and MySQL's plugin loading mechanism (`mysqld-auto.cnf`, `plugin_dir`, `early_plugin_load`). Downstream functionality impacted includes RHEL 9-to-10 upgrade workflows that use Leapp. MySQL plugin loading and configuration validation are compromised. Ordinary SQL privileges alone are not sufficient — OS-level execution as the mysql service identity plus administrator invocation of Leapp is required.

Source:

  • https://access.redhat.com/errata/RHSA-2026:67608
  • https://access.redhat.com/errata/RHSA-2026:67609
  • https://access.redhat.com/security/cve/CVE-2026-75092
  • https://bugzilla.redhat.com/show_bug.cgi?id=2517499
  • https://github.com/oamg/leapp-repository

Actions:

  • Fix: Apply the latest RHEL errata updates for `leapp-repository` as referenced in RHSA-2026:67608 and RHSA-2026:67609.
  • Workaround: Before running Leapp upgrades, audit `/var/lib/mysql` for unauthorized `mysqld-auto.cnf` or shared object files; ensure the MySQL service runs with minimal filesystem write permissions; consider running Leapp in a confined SELinux domain if possible.
  • Tradeoff: Restricting `/var/lib/mysql` permissions may interfere with legitimate MySQL operation if the directory ownership or SELinux context is not correctly maintained. Auditing adds operational overhead to upgrade procedures.
[MikroORM]CVE-2026-84993CVSS 6.5 · MEDIUM

Summary: Prior to versions 6.6.16 and 7.1.7, MikroORM's shared SQL layer validates the field key of an `orderBy` clause but does not validate its direction value before concatenating it into an `ORDER BY` clause. Applications that bind attacker-controlled request data to the direction parameter in `em.find()`, `em.findOne()`, `em.findAndCount()`, `QueryBuilder.orderBy()`, or `QueryBuilderHelper.getQueryOrderFromObject()` can permit a raw SQL fragment that performs blind or boolean extraction of data available to the database account. Affects SQLite, PostgreSQL, MySQL, MariaDB, MSSQL, libSQL, and Oracle drivers; MongoDB is not affected.

Affected Features / Interoperability: MikroORM's `orderBy` direction parameter handling across the BaseMySqlPlatform, MsSqlPlatform, and all affected SQL drivers. Downstream functionality impacted includes any application using MikroORM's query builder with user-controlled sort directions. Client drivers for PostgreSQL, MySQL, MariaDB, MSSQL, SQLite, libSQL, and Oracle are all affected.

Source:

  • https://github.com/mikro-orm/mikro-orm/releases/tag/v6.6.16
  • https://github.com/mikro-orm/mikro-orm/commit/3aba926fd07156f5e1ebf06294fd77ee1215bad5
  • https://github.com/mikro-orm/mikro-orm/commit/89e5546bf8e10f8465682016a3bdf622ff55d8c5
  • https://github.com/mikro-orm/mikro-orm/pull/7996
  • https://github.com/mikro-orm/mikro-orm/pull/7997

Actions:

  • Fix: Upgrade to MikroORM versions 6.6.16 or 7.1.7.
  • Workaround: Validate and sanitize `orderBy` direction values at the application layer before passing them to MikroORM query builder methods; restrict allowed direction values to a whitelist (e.g., "ASC", "DESC").
  • Tradeoff: Application-layer validation adds development overhead and may require changes to API contracts. A strict whitelist may reject legitimate sort directions not in the allowed set.
[MISP]CVE-2026-91851UNSCORED

Summary: Affected versions of MISP incorrectly filter dashboard templates restricted to a specific permission flag due to MySQL numeric coercion. `restrict_to_permission_flag` is a varchar column, and MySQL performs numeric coercion when comparing against integer 0, causing strings like `perm_site_admin` to convert numerically to zero and match the unrestricted branch. This allows permission-restricted templates to be accessed. Affected version: ≤2.5.45.

Affected Features / Interoperability: MISP's `DashboardsController::listTemplates()` permission filtering and MySQL numeric coercion behavior. Downstream functionality impacted includes dashboard template access control — templates intended to be restricted to specific permission flags may be incorrectly exposed to users who should not have access.

Source:

  • https://github.com/MISP/MISP/commit/245b8d63a

Actions:

  • Fix: Upgrade to a patched MISP version (post-2.5.45); apply the referenced commit fix.
  • Workaround: Modify the `restrict_to_permission_flag` column to use an integer type or enforce strict type comparison in the application query to prevent numeric coercion.
  • Tradeoff: Changing the column type requires a database migration and may affect existing data. Enforcing strict type comparison in application code requires code changes and testing.

[Magistrala]CVE-2026-82028CVSS 8.8 · HIGH

Summary: Magistrala before 1.0.0 contains a SQL injection vulnerability in the `timescale-reader` and `postgres-reader` HTTP API services that allows authenticated attackers to inject arbitrary SQL by supplying a malicious `format` query parameter interpolated directly into the `FROM` clause without parameterization or identifier quoting. Attackers with a self-registered account can substitute arbitrary subqueries to achieve cross-tenant database reads, extract `pg_shadow` password hashes, read and write arbitrary files, and execute arbitrary code as the postgres OS user by loading attacker-supplied shared objects, with all injected SQL executing at superuser privilege due to the default PostgreSQL role configuration.

Affected Features / Interoperability: The `timescale-reader` and `postgres-reader` HTTP API services and their `format` query parameter handling. Downstream functionality impacted includes multi-tenant data isolation (cross-tenant reads), PostgreSQL authentication (`pg_shadow`), filesystem integrity, and OS-level security via the postgres superuser account. Any Magistrala deployment using default PostgreSQL role configuration is fully exposed.

Source:

  • https://github.com/absmach/magistrala/pull/3581
  • https://github.com/absmach/magistrala/releases/tag/v1.0.0
  • https://www.vulncheck.com/advisories/magistrala-sql-injection-via-format-parameter-in-reader-api

Actions:

  • Fix: Upgrade to Magistrala version 1.0.0.
  • Workaround: Restrict self-registration to prevent unauthenticated account creation; apply strict input validation on the `format` query parameter at the API gateway or reverse proxy level; ensure the PostgreSQL service account has minimal OS-level privileges.
  • Tradeoff: Restricting self-registration may impact user onboarding workflows. API gateway validation adds latency and operational complexity. Running PostgreSQL with a less-privileged OS account may break functionality that relies on superuser OS access.
