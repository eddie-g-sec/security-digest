The most urgent item is Dokploy CVE-2026-129316 (CVSS 9.9, CRITICAL), an authorization-binding flaw in Dokploy 0.29.13 through 0.31.0 that can let a low-privileged member reach unrelated containers, obtain a root shell in the Dokploy panel container, read other tenants’ logs and statistics, and potentially compromise the host through the mounted Docker socket; upgrade to Dokploy 0.31.0 immediately. No CISA KEV-confirmed entries are present in the supplied data, so this item is prioritized by confirmed critical severity and direct host-compromise impact over other high-severity findings.

Formal Vulnerabilities

Microsoft AzureCVE-2026-129509CVSS 7.5 · HIGH

Summary: In Apache Airflow Microsoft Azure provider 10.2.0 through 15.3.0, `S3ToAzureBlobStorageOperator` turned off TLS certificate verification for its connection to Amazon S3 by default (`s3_verify=False`), regardless of the AWS connection’s own verification settings. An attacker positioned on the network between an Airflow worker and S3 could intercept traffic, read signed requests, and alter listed object keys or copied file contents; affected deployments use the operator without setting `s3_verify`.

Affected Features / Interoperability: Apache Airflow Microsoft Azure provider and S3-to-Azure Blob copy workflows; downstream data pipelines that copy objects from AWS S3 into Azure Blob Storage could be exposed to interception or tampering. The raw data does not specify other affected integrations.

Source: https://github.com/apache/airflow/pull/76222, https://lists.apache.org/thread/z6o61d0h81o1f9bgdrn4d9jl24o7shmh, http://www.openwall.com/lists/oss-security/2026/11/17/30

Actions:

  • Fix: Upgrade Apache Airflow to a patched release; the supplied advisory text truncates the exact fixed version.
  • Workaround: Set `s3_verify=True` for the AWS connection used by the operator, or avoid `S3ToAzureBlobStorageOperator` until patched.
  • Tradeoff: Enforcing certificate verification can break S3 access if certificates or CA trust are misconfigured.

Affected Features / Interoperability: Google Cloud Dataform, BigQuery Studio, and Colab Enterprise workspace directory handling and Git integration; downstream repository operations, file access, and tenant isolation could be impacted. The raw data does not list specific external integrations.

Source: https://docs.cloud.google.com/bigquery/docs/release-notes#November_19_2026, https://docs.cloud.google.com/dataform/docs/release-notes#November_19_2026, https://docs.cloud.google.com/support/bulletins/#gcp-2026-084

Actions:

  • Workaround: None required per vendor statement.
  • Tradeoff: No significant tradeoff.
KubernetesCVE-2026-85594CVSS 9.8 · CRITICAL

Summary: Traefik v3.7.1 fails to enforce `crossProviderNamespaces` restrictions on the `traefik.ingress.kubernetes.io/service.middlewares` Service annotation in the Kubernetes Ingress provider. A namespace-limited tenant excluded from the allowlist can attach an operator-owned middleware to its Service, and if that middleware injects backend credentials, recover them at a controlled backend.

Affected Features / Interoperability: Traefik Kubernetes Ingress provider, cross-namespace middleware references, and Service middleware annotations; multi-tenant ingress isolation and middleware chains that inject credentials could be bypassed or broken.

Source: https://github.com/traefik/traefik/security/advisories/GHSA-m6wx-622r-48r9, https://www.vulncheck.com/advisories/traefik-3.7.1-crossprovidernamespaces-bypass-via-service-middleware

Actions:

  • Fix: Apply the Traefik security update referenced by the advisory; the supplied data does not state the exact fixed version.
  • Workaround: Restrict tenant ability to create or modify Services/Ingress objects with middleware annotations, and enforce namespace allowlists through admission policy.
  • Tradeoff: May block legitimate cross-namespace middleware reuse or require additional policy maintenance.
KubernetesCVE-2026-85596CVSS 9.8 · CRITICAL

Summary: Traefik versions >= v3.7.0 and < v3.7.11 contain an authentication bypass in the Kubernetes Ingress NGINX provider. The TLS option generated for an Ingress carrying `nginx.ingress.kubernetes.io/auth-tls-secret` was named after the Ingress namespace and name, so two Ingress objects sharing the same host, client CA secret, and client-authentication mode could produce a TLS options conflict and fall back to the entry point’s default TLS configuration, which does not request a client certificate.

Affected Features / Interoperability: Traefik Kubernetes Ingress NGINX provider, TLS option generation, and client-certificate authentication; downstream services relying on mutual TLS or client-certificate validation could be exposed to authentication bypass.
